# 遵循《重构》（Martin Fowler）

## 目的

本仓库遵循 Martin Fowler 意义上的 **《重构》** 所主张的纪律：
在 **不改变代码可观察行为** 的前提下改进其内部结构。

所有代码生成、编辑和评审都必须以下列目标为优化方向：
- 保持行为不变的小步改动
- 更清晰的命名和更简单的控制流
- 更少的重复
- 更小的职责单元
- 从糟糕设计向良好设计的显式移动
- 把持续的设计改进作为日常工作的一部分

本文件是一份有约束力的工程政策：`MUST`（必须）具有强制力，`SHOULD`（应当）是强默认值，`MUST NOT`（禁止）表示不得为之。

---

## 首要指令

修改既有代码时，**不要**以重写大片区域作为起点。
先做那个能让预期改动变得更容易的、下一个安全的结构性改进。

优先按此顺序：
1. 建立安全网
2. 做一次准备性重构
3. 做出功能性改动
4. 如有必要，再做一次重构

拒绝那种把大的功能改动与无关的结构性扰动捆在一起的变更。

---

## 什么算是重构

这里的重构指：
- 在不改变外部行为的前提下改变结构
- 施加小的、可组合的变换
- 在功能开发之前或过程中移除代码坏味道
- 让下一次改动更容易
- 改善可读性、局部性和可测试性

这里的重构 **不** 指：
- 大规模重写
- 未经验证的清理
- 行为影响不明的"现代化改造"
- 一次性重命名所有东西
- 把架构迁移、功能开发和清理混进一个失控的补丁里

---

## 不可协商的规则

1. **保持行为不变**
   - 重构必须保持可观察行为不变。
   - 如果行为必须改变，把行为变更与结构性重构隔离开。
   - 绝不把功能变更伪装成重构。

2. **以小步推进**
   - 优先做许多小而安全的编辑，而不是一次大变换。
   - 每一步都应可理解、可回退。
   - 如果一个补丁大到无法局部推理，就把它拆开。

3. **让系统保持可运行**
   - 除非被明确要求提交草稿，不要把代码留在损坏的中间状态。
   - 在可行处，每个重构序列都应维持可运行、可构建的状态。

4. **在功能开发前后都做重构**
   - 如果代码难以修改，先重塑它。
   - 功能落地之后，清理这次改动引入的剩余结构性债务。

5. **使用最简单且有帮助的重构手法**
   - 不要比实际需要更早地引入模式或抽象。
   - 优先做局部简化，再考虑大尺度抽象。

---

## 安全规则

### 测试与验证
1. 在有风险的重构之前，创建或找到一张安全网。
2. 在处理行为不明的既有代码时，优先使用特征测试。
3. 如果没有测试，就做尽可能小的改动，并先改善可测试性。
4. 让重构和测试更新都与"被保持的行为"保持一致。
5. 绝不为了完成一次重构而删掉一个失败的测试。

### 提交与补丁纪律
1. 只要可行，就把结构性编辑与行为变更分开。
2. 把相关的重构归为一组。
3. 避免那种一次性重命名、搬移、重新设计并改变逻辑的巨型混合提交。
4. 优先提供便于评审的变换序列。

### 准备性重构
在实现某个功能之前，先问：
- 是什么让这次改动变得别扭？
- 什么样的局部结构性改动能让它变得顺畅？
- 我能否先重命名、提取、搬移、拆分或内联？

在功能改动之前完成准备性重构。

## 代码坏味道政策

修改代码时，主动寻找以下坏味道。

### 重复代码
- 重复的逻辑是默认要消除的目标。
- 通过提取共享行为来消除重复，而不是引入含义模糊的工具类垃圾场。
- 不要对偶然的相似性做抽象。

### 过长函数
- 当函数混杂了多种职责、多个抽象层级或多个工作阶段时，把它拆开。
- 提取有意义的代码块，并用能解释意图的名字命名。
- 不要制造毫无解释价值的微方法噪声。

### 过长参数列表
- 在恰当之处，用参数对象或更丰富的领域对象替换反复出现的参数簇。
- 移除用于切换行为的布尔标志。
- 避免那种要求调用方背下参数顺序的签名。

### 全局数据与隐藏依赖
- 减少对全局变量、单例和隐式环境上下文的依赖。
- 在可能之处让依赖显式化。
- 朝注入、参数传递或清晰归属的方向重构。

### 发散式变化
- 如果一个类因许多不同原因而变化，拆分其职责。
- 把业务逻辑、格式化、传输、持久化和集成关注点分开。

### 霰弹式修改
- 如果一处改动迫使你修改许多文件，把这份知识集中起来。
- 引入一条更好的边界或更清晰的归属划分。

### 依恋情结
- 如果一个方法主要在操作另一个对象的数据，就把它搬移过去，或重塑模型。
- 把行为放在它所归属的数据或概念附近。

### 数据泥团与基本类型偏执
- 用有意义的类型替换反复出现的原始类型组合。
- 给反复出现的业务概念起名字并加上校验。

### switch 语句与条件判断
- 当多态、查找表、策略或更好的数据结构更契合时，减少按类型或模式重复分支的写法。
- 不要用不必要的间接层替换一个诚实的单一条件判断。

### 临时字段与古怪的生命周期
- 当一个独立对象或更清晰的阶段模型更好时，移除那些只为异常代码路径而存在的字段。
- 优先显式建模状态，而不是使用半初始化的对象。

### 中间人与推测性通用化
- 移除那些不增加任何价值的转发层。
- 删除那些"以防万一"创建的抽象，如果它们并未赚回其成本。

## 推荐的重构动作

### 命名类重构
- 重命名变量以揭示意图。
- 重命名函数以描述行为，而非机制。
- 重命名类型和模块，使其与问题域的术语对齐。
- 当糟糕的命名阻碍理解时，先重命名再做更深的重构。

### 提取类重构
- 当一个代码块具有连贯的用途时，提炼函数。
- 当一个表达式难以阅读时，提炼变量。
- 当一个类有多个变化原因时，提炼类。
- 当一个文件混杂了不相关的关注点时，提炼模块。

### 搬移类重构
- 把函数搬移到其数据或概念所在的模块或类型中。
- 当归属在别处更清晰时，搬移字段。
- 搬移语句以归拢相关操作，减少认知跳转。

### 简化类重构
- 内联那些偶然形成的抽象。
- 折叠掉不必要的分层。
- 在能改善清晰度之处，用卫语句替换嵌套的条件判断。
- 合并重复的条件片段。

### 数据类重构
- 封装可变状态。
- 用具名常量或领域类型替换魔数。
- 为反复出现的参数组引入参数对象。
- 当行为围绕某个集合不断累积时，用具名抽象替换裸集合。

## 重构目录索引

### 重新组织函数
- 当一个代码片段具有连贯用途且能起个有用的名字时，使用「提炼函数」（Extract Method）。
- 当方法体本身比它带来的间接层更清晰时，使用「内联函数」（Inline Method）。
- 当一个临时变量掩盖了一个直接的表达式时，使用「内联临时变量」（Inline Temp）。
- 当某个计算值值得拥有一个具名查询、且可以被安全复用时，使用「以查询取代临时变量」（Replace Temp with Query）。
- 当一个复杂表达式需要为其各部分命名时，使用「引入解释性变量」（Introduce Explaining Variable）。
- 当一个变量承载了多种含义时，使用「分解临时变量」（Split Temporary Variable）。
- 当对参数的修改掩盖了输入的含义时，使用「移除对参数的赋值」（Remove Assignments to Parameters）。
- 当局部状态妨碍了干净的提取时，使用「以函数对象取代函数」（Replace Method with Method Object）。
- 当一个更清晰的算法能在不改变行为的前提下替换纠缠的算法时，使用「替换算法」（Substitute Algorithm）。

### 在对象之间搬移特性
- 当行为或状态更自然地属于另一个对象时，使用「搬移函数」或「搬移字段」（Move Method / Move Field）。
- 当一个类有不止一个变化原因时，使用「提炼类」（Extract Class）。
- 当一个类已不再赚回其存在的合理性时，使用「内联类」（Inline Class）。
- 当客户端对某个对象的协作者了解过多时，使用「隐藏受托者」（Hide Delegate）。
- 当一个转发对象已不再隐藏任何有用的细节时，使用「移除中间人」（Remove Middle Man）。
- 仅当你无法修改本应拥有该行为的那个类时，才使用「引入外加函数」（Introduce Foreign Method）。
- 当反复出现的外加函数需要一个本地的、连贯的扩展点时，使用「引入本地扩展」（Introduce Local Extension）。

### 重新组织数据
- 当直接访问字段妨碍了灵活性时，使用「自封装字段」（Self Encapsulate Field）。
- 当某个原始类型承载了行为、校验或含义时，使用「以对象取代数据值」（Replace Data Value with Object）。
- 当标识和共享更新很重要时，使用「将值对象改为引用对象」（Change Value to Reference）。
- 当值语义能简化归属关系时，使用「将引用对象改为值对象」（Change Reference to Value）。
- 当集合中的位置具有名称或规则时，使用「以对象取代数组」（Replace Array with Object）。
- 仅当 UI 或框架的同步需求逼迫如此时，才使用「复制被监视的数据」（Duplicate Observed Data）；并让同步逻辑保持显式。
- 仅当确实需要双向遍历时，才使用「将单向关联改为双向关联」。
- 当其中一个方向只是不必要的耦合时，使用「将双向关联改为单向关联」。
- 当外部修改可能绕过不变式时，使用「封装集合」（Encapsulate Collection）。
- 当裸记录需要具名访问、且行为可以安全增长时，使用「以数据类取代记录」（Replace Record with Data Class）。
- 依据行为是否随类型而变，选择使用「以类取代类型码」、「以子类取代类型码」，或「以状态/策略取代类型码」。
- 当子类之间的差异只是数据时，使用「以字段取代子类」（Replace Subclass with Fields）。

### 简化调用与条件表达式
- 使用「分解条件表达式」、「合并条件表达式」和「合并重复的条件片段」，让分支意图变得可见。
- 当循环或条件的状态可以被直接表达时，使用「移除控制标记」（Remove Control Flag）。
- 当能澄清常规路径时，使用「以卫语句取代嵌套条件表达式」。
- 仅当反复出现的、基于类型的行为足以支撑时，才使用「以多态取代条件表达式」。
- 当反复出现的 null 处理具有稳定含义时，使用「引入空对象」（Introduce Null Object）。
- 当某个假设应当在开发期显式化时，使用「引入断言」（Introduce Assertion）。
- 使用「函数改名」、「添加参数」、「移除参数」、「参数化函数」或「以明确函数取代参数」，让调用方的意图更清晰。
- 当调用方传入了同一个对象的多个值时，使用「保持对象完整」（Preserve Whole Object）。
- 当接收者自己就能获得该值、且不引入隐藏耦合时，使用「以函数取代参数」（Replace Parameter with Method）。
- 当构造之后不应再允许修改时，使用「移除设值函数」（Remove Setting Method）。
- 当公开接口面暴露了不必要的操作时，使用「隐藏函数」（Hide Method）。
- 当创建意图或子类型选择需要一个名字时，使用「以工厂函数取代构造函数」。
- 当调用方不应负责向下转型的细节时，使用「封装向下转型」（Encapsulate Downcast）。
- 依据预期的失败模型，选择使用「以异常取代错误码」或「以测试取代异常」。

### 通用化与大型重构
- 当超类中确实存在重复行为时，使用「字段上移」、「函数上移」或「构造函数本体上移」。
- 当只有部分子类需要某个特性时，使用「函数下移」或「字段下移」。
- 仅当调用方或变化点足以支撑时，才使用「提炼子类」、「提炼超类」或「提炼接口」。
- 当继承已不再增加任何含义时，使用「折叠继承体系」（Collapse Hierarchy）。
- 当相似的算法只在受控的若干步骤上不同时，使用「塑造模板函数」（Form Template Method）。
- 当继承把不相关的职责耦合在一起时，使用「以委托取代继承」。
- 仅当子类型关系是真实且稳定的时，才使用「以继承取代委托」。
- 当一个继承体系混杂了多个变化维度时，使用「梳理并分解继承体系」（Tease Apart Inheritance）。
- 当数据和行为需要更清晰的归属时，使用「将过程式设计转化为对象设计」。
- 当 UI 与策略纠缠在一起时，使用「将领域和表现分离」。
- 当若干类型共享行为、且变化点有实质意义时，使用「提炼继承体系」（Extract Hierarchy）。

## 函数级规则

1. 一个函数通常应当只完成一件连贯的事。
2. 让函数内部的抽象层级保持一致。
3. 移除隐藏的副作用，除非该函数的用途本就是制造这些副作用。
4. 当卫语句能澄清主流程时，优先用它而非深层嵌套的条件判断。
5. 当解析、校验、计算和 I/O 混在一起时，把这些阶段拆开。
6. 让变量作用域收紧。
7. 删除死代码，而不是把它注释掉。

---

## 类与模块规则

1. 一个类或模块应当只有一个狭窄的变化原因。
2. 把策略与表现、I/O、持久化和框架细节分开。
3. 优先用小而聚焦的单元做组合，而不是上帝对象。
4. 删除或内联那些已不再赚回成本的抽象。
5. 不要把创建 `utils`、`helpers` 或 `common` 模块当作应对重复的默认反应。
6. 围绕概念和行为来组织模块，而不是围绕遗留下来的便利性。

---

## 处理条件表达式的规则

1. 在有帮助时，用更强的建模替换按类型或状态重复分支的写法。
2. 对稳定的映射逻辑使用查找表。
3. 当能降低分支复杂度时，用卫语句、提取出的谓词或策略，替换嵌套的 if/else 金字塔。
4. 当条件判断简单而诚实时，就保留显式的条件判断。
5. 绝不为了回避一个小的局部条件判断而引入多态。

---

## 数据与状态修改规则

1. 封装状态修改。
2. 把写权限收窄到最小的有用范围。
3. 用揭示意图的操作替换随意的状态修改。
4. 通过集中管理状态转换来消除重复的更新逻辑。
5. 当不可变的中间值能简化推理时，优先使用它们。

---

## 错误处理规则

1. 重构错误处理，使主流程变得可见。
2. 不要让清理、校验和恢复逻辑淹没核心行为。
3. 当类似的错误路径在结构上重复时，把它们标准化。
4. 除非有意改变行为，否则保持既有的错误语义不变。

---

## 评审规则

评审或生成改动时，主动寻找：
- 重复的逻辑
- 过长的函数
- 过长的类
- 纠缠的控制流
- 混杂的抽象层级
- 依恋情结
- 霰弹式修改
- 发散式变化
- 纯转发的分层
- 推测性通用化
- 隐藏的副作用
- 对全局状态的依赖
- 需要过多上下文才能安全修改的代码

---

## 禁用模式

除非被明确要求且有充分理由，不要生成或保留以下模式。

### 大爆炸式重写
- 为了"清理一下"而整体替换一个能正常工作的子系统
- 在理解当前行为之前就重写
- 在一次巨大的动作中同时改变结构和行为

### 意图混杂的补丁
- 功能开发与大量无关的重命名混在一起
- 行为变更被藏在清理工作里
- 让评审变得不可能的代码搬移

### 过早抽象
- 在第二个真实需求出现之前就引入接口或策略继承体系
- 为一个调用方创建公共库
- 用含义不清的共享代码替换可理解的重复

### 重构表演
- 只重命名，而更深层的设计问题原封不动
- 引入模式，而不是消除复杂度
- 制造出更多文件、分层或包装器，却没有改善可变更性

### 无测试的结构手术
- 在没有任何安全网的情况下做大型重构
- 对脆弱代码做没有验证策略的"清理"
- 在行为其实并不显而易见时假定它显而易见

## 代码生成规则

当被要求修改既有代码时，采用以下默认顺序：
1. 理解当前行为
2. 找出所要求的改动面临的摩擦
3. 如有必要，补上或改善安全网
4. 执行准备性重构
5. 实现行为变更
6. 执行收尾清理
7. 当设计明显更好时就停手

推荐的首选动作：
- 重命名那些命名糟糕的东西
- 提取出连贯的函数
- 隔离副作用
- 拆开混杂的职责
- 把行为搬到更靠近其归属概念的地方
- 消除重复
- 简化条件判断

推荐避免：
- 不必要的框架迁移
- 无端的 API 重新设计
- 引入庞大的继承体系
- 仅因为旧代码难看就用新代码替换掉全部旧代码

---

## 测试规则

1. 当行为不明确时，在有风险的编辑之前补上特征测试。
2. 让测试聚焦于外部可见的行为。
3. 只有当行为是有意改变时才更新测试。
4. 不要让测试对私有实现细节的耦合超出必要程度。
5. 当测试变得嘈杂或重复时，也对测试做重构。
6. 让测试数据保持有表现力且最小化。

---

## 停止规则

在以下情况下停止重构：
- 所要求的改动已经容易实现
- 阻碍改动的主要坏味道已被移除
- 进一步的清理已变得带有推测性
- 下一个抽象还不具备充分理由
- 可读性和局部可变更性明显改善

---

## 评审检查清单

在最终定稿任何改动之前，核实：
- 重构期间我们是否保持了可观察行为不变？
- 在可行处，我们是否把结构变更与行为变更分开了？
- 我们是否至少消除了一处真实的摩擦源？
- 代码是否比之前更易阅读？
- 代码是否比之前更易测试或更易修改？
- 我们是否减少了重复或偶然复杂度？
- 我们是否避免了推测性抽象？
- 我们是否避免了巨型混合补丁？
- 命名是否改善了？
- 控制流是否变得更简单？
- 职责划分是否变得更清晰？

如果任何一项答案为否，在交付前先修订。

---

## 最终指令

当不确定时，选择下一个 **小的、保持行为不变的变换**，
它能让所要求的改动更容易，也让代码更易理解。
拒绝那些押注于大规模重写、或一次混入过多意图的做法。
