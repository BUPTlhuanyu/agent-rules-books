# 遵循《软件设计哲学》（John Ousterhout）

## 目的

本仓库遵循 John Ousterhout 意义上的 **《软件设计哲学》**：
直接对抗复杂度——把模块设计得有深度、接口整洁、信息隐藏充分、认知负担低。

所有代码生成、编辑和评审都必须以下列目标为优化方向：
- 更低的复杂度
- 更深的模块
- 更简单的接口
- 更强的信息隐藏
- 更少的特例
- 接口与实现之间清晰的分离
- 战略性设计优于战术性打补丁

本文件是一份有约束力的工程政策：`MUST`（必须）具有强制力，`SHOULD`（应当）是强默认值，`MUST NOT`（禁止）表示不得为之。

---

## 首要指令

复杂度是指任何让软件难以理解或难以修改的东西。

当不确定时，优先选择这样的设计：
1. 减少读者必须同时了解的事项数量
2. 把更多细节隐藏在一个稳定的接口之后
3. 消除例外情况和别扭的情形
4. 造就一个更深而非更浅的模块
5. 降低未来的认知负担，而不只是当下的键入量

如果复杂度会因此上升，就不要为更短的文件、更少的行数或精巧的紧凑写法做优化。

---

## 核心复杂度规则

### 复杂度的症状
把以下现象视为架构层面的警报：
- 变更放大
- 认知负担
- 未知的未知
- 隐藏的依赖
- 信息散落在许多地方
- 需要读者在脑中重建的时序耦合

### 默认应对方式
当某个功能让人感觉别扭时，先问：
- 接口是不是太宽了？
- 行为是不是散落各处？
- 是不是有本该隐藏的细节在泄漏？
- 是不是有太多特例？
- 我们是不是在解决一个战术性的局部问题，同时抬高了全局复杂度？

---

## 模块深度规则

### 优先选择深模块
深模块提供一个简单的接口，同时在其背后隐藏了大量复杂度。

规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）：
1. 设计模块时要让它隐藏实质性的内部复杂度。
2. 优先选择语义强的小接口，而不是带一堆次要辅助方法的大接口面。
3. 让每个模块都担得起自己的分量。
4. 一个只做工作转发的模块，通常太浅了。

### 避免浅模块
出现以下情况时，浅模块是有害的：
- 接口暴露的复杂度几乎和实现一样多
- 某些分层的存在主要只是为了转发调用
- 小包装层在不减轻读者负担的情况下增加了概念数量

反模式（MUST NOT）：
- 纯转发的服务类
- 对库的薄包装，且没有带来任何简化
- 仅仅为显而易见的操作换个名字的辅助模块

---

## 信息隐藏规则

1. 隐藏那些可能会变化的设计决策。
2. 隐藏内部数据表示。
3. 隐藏附带性的流程步骤和记账逻辑。
4. 不要让调用方依赖实现细节、性能技巧或存储形状。
5. 把杂乱的边界条件和归一化逻辑封装起来。

反模式（MUST NOT）：
- 通过模块接口暴露内部表示或状态
- 通过模块接口泄漏存储、协议、框架或文件格式细节
- 让调用方跨多个模块去协调对象内部结构

---

## 接口设计规则

1. 围绕客户端需要知道什么来设计接口，而不是围绕实现如何工作。
2. 让接口窄小但有实质意义。
3. 避免那些要求调用方按脆弱顺序分阶段调用的 API。
4. 消除那些只为暴露内部实现选择而存在的参数。
5. 使用能揭示抽象、而非揭示机制的名称和方法形态。

好接口的标志（SHOULD）：
- 方法数量少
- 语义保证强
- 所需的上下文有限
- 调用方无需理解内部结构

坏接口的标志（属警报；通常为 MUST NOT）：
- 大量配置标志
- 调用顺序陷阱
- 使用前需要调用多个初始化方法
- 用布尔值和模式参数切换内部行为

---

## 战略性编程优于战术性编程

### 战略性编程
1. 投入时间降低未来的复杂度，而不只是让当下这次改动通过。
2. 当反复出现摩擦时，重塑抽象。
3. 在接口和模块分解上投资，使未来的改动保持局部化。
4. 每一次实质性编辑之后，都留下更清晰的结构。

### 战术性编程
避免：
- 修补局部症状，同时抬高全局复杂度
- 为赶截止日期而复制粘贴
- 再多暴露一个内部细节，而不是设计一个更好的边界
- 增加标志和例外，以回避一个更好的抽象

---

## 通用模块与专用模块

1. 优先选择那些在恰当抽象层级上捕捉到可复用概念的模块。
2. 当一个略微更通用的概念显而易见时，不要把接口过度拟合到某个狭窄的调用方。
3. 也不要通用化到让抽象变得含义模糊的程度。
4. 最好的模块：足够具体因而强大，足够通用因而能在其领域内复用。

---

## 错误处理与消除例外情况

1. 设计那种让误用变难的 API。
2. 在可能的情况下，从定义层面消除非法状态和别扭的情形。
3. 通过改变接口或不变式来消除例外情况，而不只是靠增加更多检查。
4. 当异常情况把主抽象搞得杂乱时，使用"特例—通用"分解。
5. 让常规路径显而易见，让异常路径被隔离。

反模式（MUST NOT）：
- 要求每个调用方都重复一遍防御性仪式的 API
- 散落在众多调用点上的"特例"分支
- 暴露半合法的对象，然后要求调用方小心翼翼地绕着它走

---

## 把复杂度向下压

1. 把复杂度放在一个地方，而不是许多地方。
2. 把错综复杂的逻辑隐藏在一个更简单的公开契约之后。
3. 如果能让所有调用方都更简单，那么稍微复杂一点的实现是值得的。
4. 从各调用点移除重复的推理负担。

这与通过标志、初始化步骤和相互耦合的操作把复杂度向外推恰恰相反。

---

## 注释规则

注释必须降低复杂度，而不是叙述显而易见的代码。

在以下场合使用注释：
- 接口契约
- 非显而易见的不变式
- 被隐藏的设计决策
- 某个抽象为何存在的理由
- 调用方不需要知道的棘手实现事实

不要用注释去弥补：
- 糟糕的命名
- 拙劣的模块分解
- 令人困惑的控制流
- 缺失的抽象

---

## 函数与变量规则

1. 让函数有足够的深度，以隐藏实质分量的工作。
2. 只有当过长的函数确实造成认知负担时才避免它，而不是把行数当作一种数字仪式。
3. 避免那些不增加任何含义的纯传递变量。
4. 用变量来捕捉含义，而不是照抄语法。
5. 让局部细节留在局部。

反模式（MUST NOT）：
- 一串细碎的小函数，读者为理解一个想法必须不断跳转
- 只为满足风格要求、而非为了清晰而引入的变量
- 暴露那些本应留在内部的中间状态

---

## 时序分解规则

1. 如果真正的结构是概念性的，就不要主要围绕执行顺序来组织模块。
2. 优先围绕稳定的概念和职责来做分解。
3. 初始化步骤、处理阶段和清理阶段，不应迫使读者仅凭时间顺序去重建整个设计。
4. 在调用顺序确实重要的地方，让它保持简单且显式。

反模式（MUST NOT）：
- 处处是 `prepare/process/finalize`，却没有领域概念
- 要求调用方掌握不成文时序知识的 API
- 其含义取决于"哪个阶段已经跑过"的半成品对象

---

## 特例—通用分解

当少量例外情况把主逻辑搞得杂乱时，使用特例—通用分解。

规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）：
1. 让通用情形保持简单。
2. 把异常或罕见的行为隔离出去。
3. 不要用每一个边界情况去污染主抽象。

这比让条件判断在核心路径上无止境地堆积要好。

---

## 合并还是分离代码

1. 只有当分离能降低复杂度、隐藏一项真实的设计决策，或造就一个更强的抽象时，才分离代码。
2. 当拆开的碎片迫使读者在多个浅薄片段之间跳转才能理解一个想法时，把它们合起来。
3. 当分离会造成变更放大时，把相关的状态、行为和不变式放在一起。
4. 如果一条边界暴露的复杂度几乎和它隐藏的一样多，不要仅因为它已经存在就保留它。
5. 优先选择一个连贯的、更深的模块，而不是若干细碎模块加上让调用方去协调细节。

反模式（MUST NOT）：
- 当稳定的概念并非时序性的时候，却按执行阶段拆分代码
- 把常规情形与特殊情形分离得太远，以致它们共同的不变式被掩盖
- 添加辅助分层，把一项设计决策散布到许多文件中

---

## 设计备选方案与"注释先行"设计

1. 对非平凡的设计选择，在实现第一个能跑通的方案之前，至少比较两个可行的设计。
2. 从接口简洁性、信息隐藏、特例削减和未来认知负担这几个维度评估备选方案。
3. 当某个接口或抽象还不清晰时，先把公开契约和解释性注释勾画出来，再落实到实现。
4. 用"注释先行"设计来澄清抽象边界，而不是用它保住含义模糊或有误导性的代码。
5. 当为解释某个抽象所需的注释变得复杂时，修改这个抽象。

反模式（MUST NOT）：
- 仅因为局部方便就接受第一个设计
- 用注释为一个令人困惑的接口辩解，而不去修改这个接口
- 记录调用方本不该需要了解的实现机制

---

## 命名、一致性与显而易见

1. 名称必须揭示抽象，而不是内部机制。
2. 对相关的操作，使用一致的命名、参数顺序、错误行为和接口约定。
3. 优先写那种读者能从局部结构和名称推断出行为的显而易见的代码。
4. 移除非显而易见的行为，除非它被隐藏在一个清晰的契约之后。
5. 当代码让读者感到意外时，即便代码很短，也把它当作复杂度。

---

## 性能、潮流与测试

1. 在没有证据表明这个权衡确实重要之前，不要为性能牺牲模块深度或信息隐藏。
2. 当性能确实重要时，把优化细节隐藏在稳定接口之后，使调用方不必继承这份复杂度。
3. 优先采用测量数据和有针对性的改动，而不是大范围的推测性调优。
4. 除非某个潮流、范式、模式或框架能降低本代码库的复杂度，否则不要采纳它。
5. 用测试在改变结构时保住行为，但不要让测试的便利性逼出浅薄或泄漏的接口。

---

## 评审规则

评审代码时，主动寻找：
- 浅模块
- 纯转发的分层
- 暴露实现细节的接口
- 过多的标志或模式参数
- 散落各处的特例
- 因过多相互作用的模块而造成的认知负担
- 被隐藏的时序约束
- 被推给调用方的复杂度
- 那些解释了本应被编码进结构中的内容的注释
- 加大未来难度的战术性补丁

---

## 禁用模式

### 浅分解
- 把代码拆成许多细小单元，却并未降低理解成本
- 增加了名字却没带来简化的包装器和门面

### 接口泄漏
- 向普通调用方暴露存储、传输或缓存机制的 API
- 要求调用方了解内部流程的方法调用序列

### 战术性复杂度债务
- 再加一个标志、回调或条件判断，而不去改进抽象
- 修好了局部症状，却让整体设计更难

### 复杂度扩散
- 在许多地方重复同样的特殊处理
- 让所有调用方为某一个模块的别扭之处负责

---

## 代码生成规则

生成代码时，默认按以下方式进行：
1. 识别出那个值得拥有一条模块边界的概念
2. 围绕该概念设计最窄且强有力的接口
3. 把易变或复杂的细节隐藏在内部
4. 让所有调用方都更简单，即使实现因此略微膨胀
5. 隔离特例
6. 减少读者必须同时兼顾的事实数量

默认避免：
- 纯转发的分层
- 无必要的细碎抽象
- 暴露内部数据格式
- 带脆弱调用序列的时序型 API
- 在不降低复杂度的情况下增加概念数量

---

## 测试规则

1. 测试公开行为和接口契约。
2. 在可能的情况下，通过稳定的公开 API 来测试被隐藏的复杂度。
3. 围绕被隔离的特例添加聚焦的测试。
4. 如果抽象承诺了相反的事情，就避免那些迫使调用方了解实现细节的测试。

---

## 评审检查清单

在最终定稿任何改动之前，核实：
- 这次改动是降低了还是抬高了认知负担？
- 编辑之后，模块是变深了还是变浅了？
- 我们是否把更多复杂度隐藏到了稳定接口之后？
- 我们是否减少了调用点上的特例处理？
- 我们是否从公开接口面上移除了某个实现细节？
- 我们是否避免了引入纯转发的分层？
- 接口描述的是抽象，还是机制？
- 我们是否改善了未来的可变更性，而不只是当下的便利？

如果任何一项答案为否，在交付前先修订。

---

## 最终指令

当不确定时，优先选择这样的设计：
1. 造就一个更深的模块
2. 隐藏更多复杂度
3. 减少特例
4. 降低调用方的认知负担
5. 改进抽象本身，而不是在它周围打补丁

直接对抗复杂度。
