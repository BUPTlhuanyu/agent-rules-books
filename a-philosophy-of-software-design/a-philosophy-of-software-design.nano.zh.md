# 遵循《软件设计哲学》（John Ousterhout）

## 何时使用

当主要风险是偶然复杂度、浅薄的抽象、泄漏的接口或战术性补丁时使用。

## 需要纠正的首要偏见

能跑起来的代码、细碎的小片段、熟悉的包装层，并不自动等于简单。

## 决策规则

- 以降低认知负担和提升局部可理解性为优化目标，而不是更短的文件、更熟悉的模式、更少的行数或精巧的紧凑写法。
- 优先选择深模块；拒绝那些并未隐藏真实复杂度的包装器、分层、辅助函数、门面和拆分。
- 把易变的决策、表示形式、存储、协议细节、流程记账逻辑和杂乱的边界处理，隐藏进唯一的归属模块中。
- 让接口以调用方为中心、以语义为单位；当模块本可以直接提供合适的操作时，避免分阶段 API、标志参数、初始化序列和机制泄漏。
- 如果某个改动让人感觉别扭或波及范围很广，应改进归属划分与抽象，而不是叠加战术性的特例处理。
- 以总体复杂度为依据来合并或拆分：把共享的知识放在一起，只在各部分能被独立理解的边界处拆分。
- 把命名和注释当作设计信号：抽象名称要精确、契约要显式，不要用注释去弥补糟糕的模块分解。
- 只有在有证据或调用方确有需要时，才为性能、潮流、模式、框架、测试或异常处理增加复杂度。

## 触发规则

- 当要新增一个辅助函数、分层、选项、回调、模式或抽象时，先证明它为调用方消除了复杂度。
- 当一个 API 要求调用方了解调用顺序、表示形式、存储、传输、缓存、协议或文件格式时，重新设计这个边界。
- 当命名很困难、注释越写越长，或评审者感到意外时，把这当作设计问题的证据。
- 当一次改动波及范围很广时，去寻找重复的知识、隐藏的依赖、时序耦合或错误的归属方。
- 当做性能优化或增加异常路径时，保持常规路径简单，并要求有证据或更强的不变式作为支撑。

## 最终检查清单

- 需要同时记住的概念是否更少了？
- 是否有更多复杂度被隐藏到了正确的边界之下？
- 特例、开关、泄漏和调用顺序陷阱是否更少了？
- 命名、契约、归属是否更好，新增的复杂度是否都有证据支撑？
