# 遵循《发布！软件的设计与部署》（Michael T. Nygard）

## 何时使用

用于那些必须在生产环境的故障、过载、延迟、脏数据、恶意流量和运维失误中存活下来的服务、API、后台任务、队列、部署路径、控制工具和关键流程。

## 需要纠正的首要偏见

主流程跑通并不等于生产就绪。在生产环境替你定义之前，先设计好故障语义、需求上限、隔离机制、恢复路径和诊断面。

## 决策规则

- 假定每一个依赖、队列、缓存、超时、调用方重试和降级状态，都可能以缓慢、局部或持续很久的方式失败；代码必须主动假定生产环境的混乱，而不是碰巧容忍了它。
- 相比那些追求最大耦合或理想路径优雅的设计，优先选择那些失败可见、爆炸半径受限、能卸载负载、保住核心服务、并让诊断成为可能的设计。
- 把部署、运维、安全、可观测性、回滚、构建与运行时状态、依赖状态和配置校验，都视为系统的一部分，而不是发布之后的杂活。
- 为出站调用和等待设置显式的、有意为之的时间上限。在响应必须有限的地方，不要依赖库的默认值，也不要允许无限等待。
- 只有当操作对调用方和提供方都安全时才重试；限制重试次数与总时长，使用退避或抖动，不要对校验错误和永久性失败重试。
- 用熔断器、快速失败、隔板、独立的资源池和慢任务隔离，来隔离依赖故障和工作负载故障，使一次故障不会耗尽所有线程、连接或工作进程。
- 显式设计过载行为：背压、有限队列、需求上限、为关键流量预留容量，并在核心功能崩塌之前先卸载低价值的工作。
- 按故障模式选用稳定性模式：稳态用于常规清理和限制增长；当继续执行会掩盖不可恢复的问题或占住稀缺资源时快速失败；"任其崩溃"仅在有监督进程和隔离机制时采用；握手用于就绪判断；解耦中间件需配合监控；调速器用于昂贵行为。
- 让运行时状态、外部响应、自动化进度、迁移过程、运维假设和边界数据，在被信任之前先做到可见且经过校验；为局部完成的运维变更保留回滚或前滚路径。
- 显式为稀缺资源做预算，确定性地释放它们，避免跨越慢速远程调用持有锁或昂贵连接，并对大载荷采用流式或分页，而不是默认整批载入内存。
- 把外部输入和外部响应都当作不可信：校验语法、结构、业务合理性、状态、内容类型和语义；防止格式错误的数据污染缓存、队列或下游系统。
- 在边界和故障点内建可观测性：结构化上下文、关联标识、延迟、吞吐、错误、饱和度、队列、重试、熔断器、依赖、版本、配置、健康状况和运行时信号，同时避免泄漏密钥和产生重试风暴式的日志刷屏。
- 让启动流程、健康检查、迁移、一次性任务、管理控制手段、流程代码和交付工具做到：安全地失败、可审计、有授权、可观测、可停止、可恢复。
- 让互连、路由、API 契约、缓存、定时任务和后台工作都具备生产意识：避免需求集中、隐藏的单点故障、失控的扇出、脆弱的频繁往返、缓存击穿风暴、陈旧数据带来的意外，以及同步化的任务重试。
- 把安全和恶意流量纳入生产就绪的范畴；只有在爆炸半径受限、有可观测性、有停止条件并能把结论反馈到设计中的前提下，才进行生产测试、上线检查、容量测试、演练日、混沌工程或灾难模拟。

## 触发规则

- 当新增出站调用、依赖操作、资源借出、队列消费或线程等待时，明确定义超时、是否可重试、重试上界、回退或降级模式、校验，以及调用方的存活行为。
- 当新增队列、缓冲区、资源池、缓存、日志流、后台任务、定时任务或返回集合的 API 时，明确定义容量、满载行为、清理、缓存未命中/击穿/陈旧的行为、限速、分页或流式处理，以及饱和度监控。
- 当一次改动触及部署、配置、启动、迁移、一次性任务、脚本或运维自动化时，在可行处让它具备幂等性或可重启性，并为它提供持久化状态、可审计性、验证手段，以及回滚或前滚能力。
- 当新增健康检查、负载均衡、服务发现、路由或服务间握手时，确保流量只到达已就绪的组件，且健康信号真实反映其服务能力。
- 当设计 API 或集成契约时，把实质性的故障模式显式化，区分可重试与不可重试的结果，优先采用粗粒度且有韧性的交互方式，并记录超时、重试、版本和兼容性方面的预期。
- 当复盘一次事故、性能故障或容量问题时，识别出故障链、缺失的防御、检测盲区、需求量、饱和度、延迟分布、队列积压时长、依赖行为、流量集中情况，以及需要的设计改动。
- 当新增管理控制手段、控制面、交付工具、恶意流量处理，或混沌/灾难演练工作时，必须要求授权、可审计性、安全的默认值、清晰的停止机制、受限的爆炸半径和恢复路径。

## 最终检查清单

- 是否有显式的超时、没有无限等待？
- 重试是否安全、有上界、带退避或抖动，且没有在多层之间重复叠加？
- 队列、缓冲区、资源池、缓存、日志、载荷、任务和结果集是否都有上界？
- 故障是否已通过熔断器、隔板、快速失败、降级或负载卸载被隔离？
- 外部输入和依赖响应，是否在影响状态、缓存、队列或下游系统之前就经过了校验？
- 诊断信息是否覆盖日志、指标、健康状况、关联标识、运行时、版本、配置、依赖、饱和度、队列深度、重试和熔断器状态？
- 启动、部署、迁移、自动化和运维控制手段，是否在可行处做到了可重启、可观测、有授权、可审计、可恢复？
- 互连、API、缓存、定时任务、安全和混沌测试，是否都有显式定义的生产故障行为？
