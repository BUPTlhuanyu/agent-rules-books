# 遵循《发布！软件的设计与部署》（Michael T. Nygard）

## 何时使用

当运维层面的生存能力很重要而上下文预算紧张时使用。

## 需要纠正的首要偏见

生产环境的故障语义、过载行为、隔离、恢复和诊断必须被设计出来，而不是发布之后才被发现。

## 决策规则

- 假定依赖、队列、缓存、调用方、超时、脏数据和降级状态会以缓慢、局部的方式失败，且持续时间超出预期。
- 相比主流程的优雅，优先保证故障可见、爆炸半径可控、能主动卸载负载、核心服务得以保留，以及可诊断性。
- 在响应必须有限的地方，为出站调用、等待、重试、队列、连接池、缓存、日志、结果集、载荷和稀缺资源设置上界。
- 只在安全、有次数上界且带退避或抖动的前提下重试；绝不对永久性失败重试，也不要让重试层层叠加形成风暴。
- 用熔断器、隔板（bulkhead）、快速失败、独立连接池、降级模式和确定性的清理逻辑来隔离故障。
- 把部署、启动、自动化、健康检查、可观测性、配置、回滚、安全和运行时状态都当作生产设计的一部分。
- 在信任外部输入和响应之前先做校验；防止脏数据污染缓存、队列、状态或下游系统。
- 让 API、互连、缓存、后台任务和运维控制手段，在失败、容量、恢复、授权和停止行为方面都有明确定义。

## 触发规则

- 当新增远程调用、等待、队列、连接池、缓存、后台任务、重试或大结果集路径时，明确定义上界、失败行为、校验和饱和信号。
- 当修改启动、部署、迁移、配置、脚本或控制工具时，让恢复能力、可审计性、可观测性和可重启性显式化。
- 当流量可能因路由、调度、重试、扇出或恶意使用而集中时，在进入昂贵操作之前加上背压、卸载、限速或隔离。
- 当进行生产环境测试、演练日、混沌工程或灾难演练时，必须先有假设、爆炸半径限制、可观测性、停止条件和恢复路径。

## 最终检查清单

- 是否有上界？
- 重试是否有纪律？
- 故障是否被隔离？
- 负载是否受控？
- 数据是否经过校验？
- 是否可观测？
- 是否可恢复？
- 是否可停止？
