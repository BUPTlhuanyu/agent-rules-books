# 遵循《数据密集型应用系统设计》（Martin Kleppmann）

## 何时使用

用于那些正确性取决于数据归属、一致性、持久性、复制、分区、Schema 演进、事件流、重放或派生数据维护的系统。

## 需要纠正的首要偏见

不要把分布式数据行为设计得像是每一次写入、读取、入队、缓存、副本、时钟和下游副作用都是本地的、有序的、最新的且恰好一次的。

## 决策规则

- 把核心权衡显式化：事实来源、一致性预期、重试行为、重复与乱序的工作、部分失败、数据演进，以及状态是持久的、缓存的、派生的还是临时的。
- 把崩溃、部分写入、重复工作、超时、陈旧读取和下游结果未知都当作正常输入。区分"已接收"、"已持久化"、"已应用"和"已持久且不可丢失"这几种成功语义。
- 在改动架构之前，先用具体的请求速率、数据量、访问模式、延迟、吞吐、分位数、瓶颈、争用和长尾行为来描述负载与性能。
- 依据实体关系、访问模式、一致性需求、更新的局部性、演进压力，以及数据是主数据还是派生数据，来选择数据模型、查询模型和归属边界。
- 让存储引擎、索引和分析型存储布局匹配写入模式、读取模式、范围扫描、恢复需求、写放大、OLTP 与分析负载的分离，以及关于内存与持久性的假设。
- 把索引、缓存、搜索副本、读模型、物化视图和反规范化副本都当作派生数据，为其明确定义传播机制、延迟、可观测性、修复和重建路径。
- 定义写入语义：一次写入何时算持久化、何时变得可见、是否允许陈旧读取、可能发生哪些冲突，以及冲突如何被检测或解决。
- 让命令、后台任务、事件、批处理作业和流处理器在重试与重放下保持安全，依靠去重键、天然幂等的状态转换，或一份显式的事务性恢复契约。
- 只保留业务逻辑真正需要的那部分顺序保证。把它的作用域限定在单个键、流、分区、记录、实体历史或某个更强的契约上，并让对顺序敏感的逻辑贴近该作用域。
- 把命令、事件、持久日志、流和物化视图分开。事件描述已发生的事实；消费者必须能容忍延迟、重复、重启、重放，并处理稳定标识符、关联元数据和带版本的载荷。
- 把 Schema、编码、API、消息、事件和数据库变更设计为不断演进的契约，需要跨越旧读取方、旧写入方、旧数据、在途消息、滚动升级和跨服务格式而依然可用。
- 依据写入拓扑、延迟、故障容忍度、复制延迟、故障切换、重配置、冲突处理，以及读己之写、单调读、一致前缀、法定人数和收敛性需求，来选择复制拓扑。
- 按与工作负载相关的局部性和一致性键来分区，并把热点键、数据倾斜、路由、二级索引、再均衡和跨分区操作的成本都明确出来。
- 让事务和隔离级别与不变式相匹配。明确原子性作用域、提交行为、恢复、对账，以及丢失更新、写倾斜、幻读和副作用修复的语义。
- 把网络延迟、丢包、网络分区、重复消息、进程暂停、过期的主节点、超时、挂钟时间的不确定性、租约、锁、多数派和主节点身份，都当作需要一份故障模型来支撑的假设。
- 只在协调问题确实需要达成一致、且可用性或延迟代价可接受的地方，才使用线性一致性、全序广播、原子提交或共识算法。
- 让批处理和流处理可重算、可恢复：明确定义输入、输出、中间状态、检查点、外部副作用、事件时间、处理时间、摄入时间、窗口、迟到数据、连接操作，以及从数据源到数据汇的保证级别。
- 让服务边界与数据归属和更新语义对齐。不要随意把一个强一致的业务概念拆散到多个服务中，也不要把频繁的跨服务连接操作放在热路径上。

## 触发规则

- 当修改一条写入路径时，明确说明事实来源、一致性边界、持久化时点、可见性时点、下游影响、回滚或修复路径，以及超时或结果未知之后的行为。
- 当新增或修改缓存、索引、投影、搜索副本、读模型、数仓或反规范化字段时，明确定义归属、传播、陈旧度、写入成本、延迟可观测性、重建和修复。
- 当修改 Schema、API、消息、事件、枚举、状态或载荷含义时，为旧读取方、旧写入方、已存储的旧数据、旧消息、新写入方，以及灰度发布和迁移过程规划好兼容性。
- 当引入重试、后台任务、消费者、队列、CDC、事件溯源、流处理器或可重放的批处理工作时，证明其在重复、重放、顺序、保留期、副作用和恢复方面都是安全的。
- 当把读请求路由到副本或使用异步复制时，先明确读己之写、单调读、一致前缀、陈旧度、追赶、故障切换和冲突方面的预期，再放开这类读取。
- 当对数据或工作负载分区时，针对常规查询路径检验局部性、数据倾斜、热点键、路由元数据、再均衡成本、二级索引行为和跨分区协调。
- 当选择事务隔离级别或放松一致性时，把每一种异常现象映射到它可能破坏的那条不变式上，并在必要处加上可串行化隔离、锁、比较并设置、版本号、对账或其他补偿性设计。
- 当使用时间戳、租约、锁、主节点身份、多数派决策、协调服务或类共识机制时，明确定义时钟假设、法定人数/会话语义、权威过期后的行为，以及屏障（fencing）机制。
- 当评审或测试数据密集型代码时，专门查找这些问题：事实来源归属不清、缺失幂等性、无意中假定了恰好一次、顺序保证的作用域未界定、Schema 漂移、无法重建的投影、含义不明的多处写入，以及不可观测的延迟或故障。

## 最终检查清单

- 事实来源与各派生表示是否显式。
- 一致性预期、持久化时点、可见性时点、陈旧度和冲突规则是否具体。
- 重试、重复投递、重放、乱序、超时、崩溃和结果未知是否都已处理。
- Schema、编码、API、消息、事件、枚举和状态是否能在多版本混跑的情况下安全演进。
- 存储、索引、复制、分区、路由和分析型布局是否匹配真实工作负载。
- 事务隔离级别与协调机制的选择，是否保护了那些被明确指出的不变式。
- 事件、日志、流、批处理作业和投影是否可重放，或有显式的修复路径。
- 服务边界是否遵循数据归属与更新语义。
- 延迟、重试、故障、重建和修复路径是否可观测。
- 设计是否避免了"恰好一次"的一厢情愿，以及隐式的分布式系统契约。
