# 遵循《数据密集型应用系统设计》（Martin Kleppmann）

## 何时使用

当数据正确性、持久性或分布式写入语义比局部代码风格更重要时使用。

## 需要纠正的首要偏见

隐式的数据契约同样是契约。

## 决策规则

- 对每一处重要的数据变更，都明确说明事实来源、一致性预期、持久化时点、可见性时点、重试语义和演进路径。
- 依据工作负载、访问模式、一致性、可靠性、可维护性和运维成本，来选择数据模型、存储、索引、复制、分区、事务、队列、流和 API。
- 把缓存、索引、投影、搜索副本、反规范化数据和物化视图都当作派生数据，为其准备好陈旧度、延迟可观测性、修复和重建路径。
- 让重试的、重放的、入队的、批处理的、流式的和事件驱动的工作具备幂等性或事务性；拒绝草率的"恰好一次"（exactly-once）声明。
- 把 Schema、编码、服务 API、消息、日志和事件都当作带版本的契约，它们必须能在旧代码、旧数据、滚动升级和在途消息中存活。
- 假定分布式环境下的种种不确定性：崩溃、部分写入、超时、重复消息、乱序事件、陈旧副本、复制延迟、时钟误差、进程暂停、过期的主节点，以及结果未知的操作。
- 让复制、分区、隔离级别、事务和协调机制与要保护的不变式相匹配；不要在缺乏论证的情况下依赖从库的数据新鲜度、法定人数公式、弱隔离级别、挂钟时间顺序或临时的主节点选举。

## 触发规则

- 当引入重试、后台任务、消费者、队列、CDC、事件溯源或流处理时，证明其在重复、重放、顺序、副作用和恢复方面都是安全的。
- 当修改 Schema、API、消息、事件、枚举值或状态含义时，规划好前向与后向兼容性，以及迁移、初始化或重建路径。
- 当从副本读取数据或对数据分区时，明确定义陈旧度、路由、热点键、顺序、再均衡和跨分区的行为。
- 当使用锁、租约、时间戳、主节点选举、多数派或协调服务时，明确定义故障模型、法定人数/会话语义、权威过期后的行为，以及屏障（fencing）机制。

## 最终检查清单

- 归属方与事实来源是否清晰？
- 一致性、持久性、可见性和陈旧度语义是否显式？
- 在重试、重放、重复投递、乱序和结果未知的情况下是否安全？
- 是否兼容旧数据、旧代码、新代码和在途消息？
- 隔离级别、复制、分区、事务和协调机制是否都对照实际的不变式做过检查？
