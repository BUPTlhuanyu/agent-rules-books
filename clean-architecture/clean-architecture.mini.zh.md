# 遵循《架构整洁之道》（Robert C. Martin）

## 何时使用

当新增、修改、评审或重构那些业务规则需要在框架、数据库、交付机制、外部服务、设备、厂商、部署形态或工期压力发生变化时依然存活的代码时使用。

## 需要纠正的首要偏见

不要让细节变成架构。业务策略保持独立，依赖指向内层，易变的机制保持可替换。

## 决策规则

- 即便当下这个功能不考虑它们会写得更短，也要保住业务规则的独立性、指向内层的依赖、可测试性和可替换的细节。
- 源码依赖必须向内指向更高层的策略。领域层与用例层不得引入框架、数据库、Web 处理器、消息队列、外部服务客户端、UI 类型或其他细节。
- 把企业级规则和不变式放在实体或等价的领域对象中；把特定于应用的编排逻辑放在职责聚焦的用例中。
- 在用例边界上传递朴素的请求与响应模型。不要把 Web 请求、框架上下文、ORM 行对象、绑定数据库的结构或框架响应对象传入或传出核心策略。
- 把框架、数据库、Web 交付、消息通信、文件系统、时钟、服务客户端、网络、设备和厂商都当作外层细节，置于端口、网关、展示器、映射器或适配器之后。
- 内层拥有它所需要的接口，外层来实现这些接口。对象构造和具体装配属于组合根（composition root）或其他外层的 main 组件。
- 让适配器保持"谦卑"。控制器、端点、展示器、网关适配器、服务监听器和硬件适配器只负责把外部格式翻译成用例调用再翻译回去；它们不拥有业务决策。
- 优先按用例、特性或业务能力组织代码，而不是按泛化的技术分类。代码结构应当揭示领域意图和应用行为。
- 依据易变性、策略重要性、可替换价值、可测试性和成本来选择边界。当完整的部署或运行时分离代价过高时，使用最轻量但可强制执行的边界，包括部分边界。
- 当共享会把不同参与者、不同变更原因、不同团队归属、不同部署需求或不同发布压力耦合在一起时，不要合并不相关的用例，也不要为消除重复而消除重复。
- 使用结构化代码、依赖倒置、按角色划分大小的接口、可替换的实现、受控的状态修改、无环的组件依赖以及沿稳定性方向的依赖，来保护策略不受易变细节侵蚀。
- 用包结构、依赖规则、构建约束、测试、可见性或窄接口来强制边界。仅有一张架构图、一次服务拆分、一个包名或一个共享的 `common` 目录是不够的。
- 优先测试实体、用例和边界契约，不使用真实的框架、数据库、网络、外部服务或目标硬件。适配器在接缝处单独测试。
- 在改进依赖方向的同时保持行为不变。优先采用渐进式的边界提取而非重写，并在当下无法安全修复时明确指出架构债务。

## 触发规则

- 当紧急交付要跳过架构工作时，先说明由此带来的未来变更、测试、替换或运维成本，再接受这个捷径。
- 当框架注解、请求/响应对象、序列化器、ORM 行对象、Schema、厂商 SDK、配置、环境变量读取、设备寄存器或传输格式渗入核心策略时，把转换逻辑外移。
- 当控制器、定时任务、处理器、视图、展示器、网关、仓储、SQL、服务监听器、脚本或硬件适配器中包含业务分支或校验时，把这些规则内移。
- 当一个用例自行实例化基础设施、直接调用易变依赖，或依赖某个具体实现时，引入一个由策略层拥有的端口，并在边缘处装配具体细节。
- 当某个 `*Service`、工具目录、共享模块、基础包或泛化的 `core` 包变成逃生通道时，按用例、角色或归属拆分它，并恢复依赖方向。
- 当适配器绕过用例、展示器直接读取持久化层，或基础设施既被内层代码引入又引入内层代码时，恢复原本设定的边界。
- 当出现服务边界、进程边界、远程调用、部署边界或嵌入式硬件时，仍要核查源码依赖方向、数据归属、I/O 成本和策略的独立性。
- 当测试必须依赖框架、数据库、网络、服务或硬件才能验证业务规则时，把测试下移到用例/实体层并使用测试替身，或添加一个稳定的边界契约。
- 当妥协不可避免时，把它保持在尽可能靠外的层次，记录这处违规，避免让它变成常态，并保留未来分离出去的路径。

## 最终检查清单

- 业务规则是否独立于框架、数据库、UI、服务、设备和厂商？
- 依赖是否指向内层，端口是否由内层策略拥有，具体细节是否都在外层？
- 实体是否守护不变式，职责聚焦的用例是否各自编排一个应用行为？
- 边界是否显式，并在代码、测试、包或构建规则中被强制执行？
- 控制器、展示器、网关、服务监听器和适配器是否足够"谦卑"？
- 代码结构是否揭示了用例和业务能力，而不是泛化的技术分类？
- 核心测试是否能在不依赖真实交付层、持久化、网络、外部服务或硬件的情况下快速运行？
- 细节是否依然可以在不重写业务规则的前提下被替换？
