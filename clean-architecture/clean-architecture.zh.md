# 遵循《架构整洁之道》（Robert C. Martin）

## 目的

本仓库必须遵循 **架构整洁之道**。
在编写、修改或评审代码时，优先采用那些能保住以下属性的决策：
- 独立的业务规则
- 指向内层的依赖
- 框架独立性
- 数据库独立性
- UI 独立性
- 可测试性
- 可替换的细节

把本文件视为一份有约束力的实现政策：`MUST`（必须）具有强制力，`SHOULD`（应当）是强默认值，`MUST NOT`（禁止）表示不得为之。

---

## 不可协商的规则

1. **遵循依赖规则**
   - 源码依赖必须向内指向更高层的策略。
   - 内层不得引入或依赖外层。
   - 业务规则不得依赖框架、Web 处理器、数据库驱动、UI 库、消息队列、外部服务或其他细节。

2. **让业务规则保持纯净**
   - 实体和用例必须承载业务策略。
   - 业务规则不得直接读取 Web 请求、环境变量、框架上下文、绑定数据库的结构或数据库行。
   - 通过请求模型或参数把朴素数据传入用例。

3. **把框架当作细节**
   - 框架是工具，而不是设计的基础。
   - 把框架注解、装饰器、控制器、路由、中间件、序列化器和数据库产物都保持在边缘。
   - 不要让框架类型泄漏进核心策略。

4. **把数据库当作细节**
   - 不要围绕数据表来塑造领域模型。
   - 用网关隔离持久化。
   - 业务规则必须能在没有真实数据库的情况下运行。

5. **把 Web 当作细节**
   - 控制器和端点负责把交付层的输入翻译成用例的输入模型。
   - 用例不得了解 Web 传输、状态码、Cookie、请求头或路由。
   - 展示器或响应映射器负责把用例输出翻译给交付机制。

6. **使用显式的边界**
   - 在架构接缝处定义接口。
   - 外部系统、持久化、消息通信、文件系统、时钟和服务客户端都必须置于边界之后。
   - 优先使用适配器，而不是从策略代码直接调用实现细节。

7. **按用例组织**
   - 优先采用面向特性和用例的结构，而非泛化的技术分类目录。
   - 架构应当"喊出"领域与应用的意图。
   - 避免那种被泛化技术分类目录主导、看不出用例或业务目的的代码库。

8. **用例必须负责编排**
   - 一个用例协调实体和网关。
   - 一个用例不应包含交付层、数据库层或表现层格式化方面的关注点。
   - 一个用例应当代表一个应用行为。

9. **实体必须守护不变式**
   - 关键的领域规则属于实体或等价的领域对象。
   - 实体必须保护不变式和一致性。
   - 不要把核心规则留在控制器、定时任务、处理器或数据库脚本中。

10. **外层可以依赖内层，反之绝不可以**
    - 控制器可以依赖用例。
   - 网关可以实现由用例层或领域层定义的接口。
    - 展示器可以实现由内层拥有的输出边界。
    - 绝不要意外地把这种关系反转过来。

## 各层必需的职责

### 领域层
包含：
- 实体
- 企业级业务规则
- 领域不变式
- 核心业务规则

它们可以用朴素对象、函数、模块或其他结构来实现。架构整洁之道要求的是业务规则的独立性，并不要求某种特定的领域建模风格。

必须：
- 不含框架
- 对持久化无感知
- 与交付机制无关
- 在可能的情况下避免注解和基础设施引入

不得：
- 引入 Web 库
- 引入数据库访问类型
- 引入外部服务客户端
- 执行 I/O
- 直接读取配置

### 应用层
包含：
- 用例
- 输入模型
- 输出模型
- 端口与边界
- 编排逻辑

必须：
- 依赖领域层的抽象和模型
- 为所需的外部行为定义接口
- 显式地编排工作流

不得：
- 包含控制器逻辑
- 包含数据库访问细节
- 返回框架的响应类型
- 格式化 UI 字符串，除非这明确属于某个展示器边界的一部分

### 接口适配器层
包含：
- 控制器
- 展示器
- 视图模型
- 网关适配器
- 外部模型与内部模型之间的映射器

必须：
- 在外部格式与内部模型之间做转换
- 向内依赖应用层和领域层的代码
- 隔离框架和厂商细节

不得：
- 把业务策略从用例层或领域层挪出来
- 绕过用例直接调用网关，除非架构层面有明确理由

### 基础设施层
包含：
- 框架引导逻辑
- 对象图与组件装配
- 数据库访问细节
- 外部服务集成
- 消息总线客户端
- 文件系统实现
- 网络客户端

必须：
- 保持可替换
- 实现由内层拥有的接口
- 停留在最外缘

不得：
- 定义业务规则
- 决定领域的形状
- 把厂商类型泄漏进内层

## 代码生成规则

生成代码时，始终应用以下规则。

### 1. 先定义用例
对每一个非平凡的功能：
- 识别用例
- 定义输入
- 定义输出
- 定义所需的端口
- 把编排逻辑放在一处

优先按此顺序：
1. 领域规则或实体行为
2. 用例
3. 边界接口
4. 展示器契约
5. 网关契约
6. 适配器
7. 框架装配

### 2. 在边界上使用朴素模型
- 使用由应用层拥有的请求模型和响应模型。
- 不要把绑定数据库的实体、Web 请求或绑定框架的数据结构传入核心逻辑。
- 不要从用例返回框架对象。

### 3. 为易变的依赖创建端口
为以下内容引入接口：
- 网关
- 邮件发送器
- 支付服务商
- 消息发布器
- 存储服务商
- 时钟
- ID 生成器
- 必要时的事务执行器

不要在核心用例中直接调用易变的细节。

### 4. 把装配逻辑放在 main 组件中
- 对象构造属于组合根。
- 不要在用例或实体内部实例化基础设施依赖。
- 在外层使用显式构造、工厂或组合。

### 5. 优先依赖稳定的事物
- 内层拥有它所需要的抽象。
- 外层实现这些抽象。
- 避免那种造成横向耦合的共享 "common" 包。

### 6. 让边界保持可见
- 当有疑虑时，宁可更早地引入一条边界。
- 如果部分边界能保住未来提取出去的可能性，那它是可接受的。
- 用接口、请求模型和输出模型来避免耦合到细节上。

## 架构启发式原则

### 依赖方向
始终核实：
- 这个 import 是否指向内层？
- 是否存在高层策略依赖低层细节？
- 是否有框架或厂商类型泄漏进核心层？
- 是否有适配器绕过了预设的边界？

如果是，就重构。

### 策略与细节
放置代码时，先问：
- 这是业务策略吗？
- 这是编排吗？
- 这是转换吗？
- 这是基础设施吗？

把代码放在与其职责相匹配的最高层次上。

### 稳定的核心，可替换的边缘
优先采用这样的设计：你可以替换
- Web 框架
- 持久化技术
- 消息中间件
- 任务执行器
- 云厂商
- 序列化器
- UI
而无需重写业务规则。

### 特性优先的结构
优先使用：
- 特性/用例命名
- 业务能力/用例命名
- 能揭示应用用例的命名

而不是：
- 泛化的 controller、service 或 gateway 分类目录
- 泛化的技术分类目录

只有在不掩盖用例归属的情况下，技术性子目录才是可接受的。

---

## 架构经济性与优先级

1. 把架构当作一种手段，让未来的变更成本与变更范围成正比。
2. 不要仅因为紧急的功能工作声音更大，就牺牲重要的架构工作。
3. 在证据足以支撑承诺之前，保住在框架、数据库、交付机制和部署拓扑方面的选择权。
4. 依据易变性、策略重要性、可替换价值、可测试性和成本来选择边界。
5. 不要过度建设那些成本超过其所保留选择权价值的边界。
6. 当变更的形态、团队归属、部署需求或运维约束显示成本正在上升时，重新审视架构。

---

## 范式与组件规则

1. 用结构化编程让行为可分解、可测试。
2. 当高层策略不应了解低层细节时，用多态来倒置依赖。
3. 当不可变性或受控的状态修改能保护策略免受意外的状态耦合时，采用它们。
4. 通过分离那些因不同参与者或不同原因而变化的代码来应用单一职责原则（SRP）。
5. 通过保护稳定策略不受易变扩展细节侵扰来应用开闭原则（OCP）。
6. 通过确保可替换的实现都保住调用方的预期来应用里氏替换原则（LSP）。
7. 通过让接口聚焦于每个客户端实际需要的内容来应用接口隔离原则（ISP）。
8. 通过让源码依赖指向稳定的策略和抽象来应用依赖倒置原则（DIP）。
9. 依据内聚性和发布压力来组合组件；不要仅因为共处同一技术分层就把不相关的策略归在一起。
10. 避免组件循环依赖；在循环硬化成部署或测试瓶颈之前打断它。
11. 平衡稳定性与抽象性：稳定的组件不应依赖不稳定的细节，抽象的组件应当有具体的存在理由。

---

## 边界成本、部署与运维

1. 一条边界可以是源码边界、部署边界、进程边界、服务边界，或部分边界。
2. 选择那个能保住所需独立性的最轻量边界。
3. 当完整的部署/运行时拆分代价过高、但未来的分离仍有价值时，使用部分边界。
4. 让开发、部署、运维和维护方面的关注点保持可见，但不要让它们拥有业务策略。
5. 不要仅因为运维装配更容易就合并不相关的用例。
6. 当共享代码会把因不同参与者而变化的用例耦合起来时，不要为消除重复而消除重复。
7. 通过包结构、测试、依赖规则或构建约束，让架构边界成为可强制执行的。

---

## 服务、分布与嵌入式边界

1. 一个服务并不自动构成一条架构边界；源码依赖和数据归属仍然决定着耦合程度。
2. 远程调用必须被当作 I/O 边界，而不是本地方法调用。
3. 让服务监听器保持"谦卑"：把外部消息翻译成用例调用，并经由输出边界返回。
4. 把嵌入式细节和硬件细节置于接口之后，使策略可以在不依赖目标设备的情况下被测试。
5. 不要让实时、固件、数据库、Web 或框架方面的关注点把策略往外拽。

---

## 命名规则

- 用业务能力或用例来命名模块和包。
- 用应用用例中的动作动词来命名用例。
- 用端口对该用例所扮演的角色来命名端口。
- 用适配器所适配的外部细节或交付机制来命名适配器。
- 当用例、策略、边界、展示器、控制器、网关或实体这类角色名更精确时，避免使用含义模糊的技术性名称。
- 如果一个类被命名为 `Service`，请说明为什么它不是一个用例、适配器或领域对象。

---

## 测试规则

### 核心测试优先
优先为以下内容编写测试：
- 实体
- 用例
- 边界契约

这些测试必须：
- 不依赖真实框架即可运行
- 不依赖真实数据库即可运行
- 不依赖网络即可运行
- 运行快速且具确定性

### 适配器测试
针对以下方面单独测试适配器：
- 映射的正确性
- 网关行为
- 控制器的转换逻辑
- 展示器的格式化逻辑
- 与框架或外部服务的集成

不要用缓慢的集成测试替代对业务规则的测试。

### 通过受支持的边界来测试
- 当存在公开的用例边界时，避免伸手去碰私有内部结构。
- 优先用测试替身（fake 或 mock）替换端口来测试用例。
- 只在架构接缝与真实细节交汇之处使用集成测试。

## 禁用模式

除非被明确要求且有充分理由，不要生成或保留具有以下任何特征的代码。

### 框架泄漏
- 在可避免的情况下仍给领域实体加上数据库或 Web 框架的元数据注解
- 用例依赖 `Request`、`Response`、控制器基类、框架会话或中间件对象
- 应用层引入序列化器或数据库基类

### 数据库泄漏
- 用例返回数据表行或绑定数据库的实体
- 领域规则嵌在网关实现或数据库访问代码中
- 领域对象主要围绕持久化的便利性来设计

### 以控制器为中心的逻辑
- 控制器包含分支式的业务规则
- 控制器执行本该属于业务策略的校验
- 控制器直接调用网关而非用例

### 上帝服务
- 庞大的 `*Service` 类，什么都干：创建、查询、校验、持久化、发布和呈现
- 拥有互不相关用例的服务
- 沦为垃圾场的应用服务

### 越层调用
- 控制器绕过用例去调用网关
- 展示器直接从数据库读取
- 基础设施代码既引入内层代码，又被领域代码引入

### 方向违规
- 网关接口定义在基础设施层，却被核心策略消费
- 实体引入适配器
- 用例依赖具体实现

### 工具类垃圾场
- 把泛化的 utility、shared、base 或 core 目录当作架构逃生通道
- 归属不清的泛化抽象
- 掩盖了糟糕依赖方向的便利模块

## 重构规则

修改既有代码时：

1. **把业务规则内移**
   - 从控制器、处理器、视图、网关类和定时任务中提取出领域逻辑。

2. **围绕细节引入边界**
   - 包装外部服务、数据库访问、消息总线、文件系统操作和时钟。

3. **用端口替换具体依赖**
   - 在内层定义接口。
   - 在外层实现它们。

4. **把转换与策略分离**
   - 请求解析、数据映射、序列化和表现层格式化都属于核心业务规则之外。

5. **拆开上帝服务**
   - 按用例拆分。
   - 让每个用例只对应一个明确的应用行为。

6. **消除测试对框架的耦合**
   - 在可能的情况下，改写测试使其直接针对用例和实体。

7. **在改进依赖方向的同时保持行为不变**
   - 渐进式重构。
   - 优先做安全的边界提取，而非大规模重写。

---

## 输出预期

当被要求实现一个功能时，默认产出：
- 若存在业务不变式，则产出领域模型或实体
- 一个职责聚焦的用例
- 必要时的输入与输出模型
- 为外部依赖定义的端口/接口
- 面向 Web、持久化或消息通信细节的适配器
- 位于用例之外的组合根装配代码

当被要求修改既有代码时：
- 保住或改进依赖方向
- 避免给内层添加框架依赖
- 如果某处架构债务当下无法安全修复，就显式指出来

当被要求评审代码时：
- 指出边界违规
- 指出依赖规则违规
- 指出框架泄漏
- 指出业务规则放错了位置
- 指出上帝服务和越层调用
- 提出朝架构整洁之道演进的具体重构方案

---

## 评审检查清单

在最终定稿任何改动之前，核实：

- 业务规则是否独立于框架？
- 用例是否独立于交付层和持久化细节？
- 源码依赖是否指向内层？
- 控制器是否够薄？
- 网关是否只是持久化适配器？
- 实体是否在守护领域不变式？
- 端口是否由内层拥有？
- 组合装配是否发生在边缘？
- 核心测试能否在没有 Web 框架和数据库的情况下运行？
- 项目结构是否反映了领域和用例？
- 我们是否避免了泛化的工具类垃圾场？
- 我们是否避免了再造出一个上帝服务？
- 我们是否让细节保持可替换？

如果任何一项答案为否，在交付前先修订设计。

## 推荐的默认形态

### 推荐的特性结构
- domain
- application
- adapters
- infrastructure

或者，若采用面向特性的组织方式：
- feature/domain
- feature/application
- feature/adapters
- feature/infrastructure

### 推荐的用例结构
- 请求模型
- 用例
- 输出边界或响应模型
- 端口
- 位于外部的适配器实现

### 推荐的依赖模式
- 内层定义接口
- 外层实现接口
- 组合根把它们装配在一起

---

## 当权衡不可避免时

如果客观约束逼迫你做出妥协：
- 把妥协保持在尽可能靠外的层次
- 在代码注释或评审记录中清楚地记录这处边界违规
- 避免让这种妥协在核心架构中变成常态
- 保留未来分离出去的路径

选择那个能最小化长期耦合的设计，而不是那个仅仅在今天最短的设计。

---

## 最终指令

当不确定时，选择那个能够：
1. 保住业务规则的独立性
2. 让依赖指向内层
3. 把细节隔离在边界之后
