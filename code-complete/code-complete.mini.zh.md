# 遵循《代码大全》（Steve McConnell）

## 何时使用

在实现、修改、评审、调试、重构或调优生产代码时使用，此时构建纪律必须减少缺陷并让代码易于审查。

## 需要纠正的首要偏见

构建质量不会自己发生。不要把敲完代码、让它跑通一次，或用上某个精巧的惯用法当作构建完成；要选择那个能降低缺陷风险、让代码更易推理的方案。

## 决策规则

- 在开始大规模构建工作之前，确认需求、架构、主要风险、编码规范、语言约束、错误处理策略、数据表示、复用方案、集成方式和测试方法是否已足够清晰。
- 当上游仍存在不确定性时，构建一个小而经过验证的切片，而不是写推测性的代码；对那些难以撤销的决策要审慎作出。
- 首先为人类读者做优化：清晰、局部性、显式、可见的控制流、一致的约定和实际的正确性，优先于精巧、更少的键入量或时髦做法。
- 对复杂的例程，先用精确的伪代码或意图注释在统一的抽象层级上勾画出来，再转换成代码，最后只保留那些仍在说明意图、约束、契约或理由的注释。
- 让例程保持内聚、命名精确、接口窄小且难以误用。当初始化、校验、计算和副作用在概念上不同时，把它们分开。
- 通过揭示用途的命名、小作用域、有意的初始化、具名常量、更强的类型，以及可见的单位或哨兵值含义，让变量和数据的含义显式化。
- 选择那些让非法或含义模糊的值更难被表示出来的数据类型；仅在含义确为二元时使用布尔类型，对封闭集合使用枚举，仅当记录/映射/表的形状本身能传达含义时才使用它们。
- 让控制流保持在可验证的简单程度内：浅嵌套、为复杂条件命名谓词、清晰的常规路径、清晰的循环初始化/终止/递进，不使用依赖副作用的表达式或精巧的单行写法。
- 仅当表格更清晰、含义显而易见、与规则保持同步且经过校验时，才对稳定明确的映射关系使用表驱动或数据驱动逻辑；不要把复杂行为藏进难以理解的编码中。
- 在信任边界上校验输入。用断言、不变式检查和简单契约表达程序员的假设；用校验或领域错误处理预期中的外部或业务失败。
- 在合适的抽象层级处理错误，保留诊断上下文，对类似的失败做标准化处理，让常规路径保持可读，并且绝不从已损坏或不可能的状态中静默地继续执行。
- 让类和模块保持聚焦、内聚，并由清晰的契约界定；隐藏内部表示和记账逻辑，避免混杂持久化、格式化、业务和集成方面的关注点。
- 把不断上升的复杂度视为缺陷风险：拆开纠缠的例程或模块，消除那些让维护成本倍增的重复，减少维护者必须放在工作记忆中的内容。
- 以小而可验证的增量推进构建；集成得足够频繁，以便暴露冲突、避免半成品腐化，并在构建过程中评审和改进代码。
- 让评审、正式检查、结对工作、测试、静态检查和回归测试的投入与缺陷风险相匹配。调试要通过复现、隔离、解释、修复和验证根因来完成，而不是靠猜测。
- 当结构掩盖了意图、重复了知识，或抬高了缺陷概率时进行重构；当分离能提升可评审性时，让重构与行为变更保持分离。
- 仅在需求和证据都能支撑时才做性能调优；在改动前后都做测量，除非有明确的、经过测量的权衡值得付出代价，否则保持清晰性。
- 使用工具、脚本、调试器、剖析器、编辑器和构建自动化来减少易错的手工劳动，而不是用它们替代理解。

## 触发规则

- 当写代码是从一个既定的解决方案开始时，先重新陈述需求、与架构的契合度、风险、规范和成功的约束条件，再开始实现。
- 当一个例程难以命名、混杂多个阶段、带有标志参数、参数列表过长或存在隐藏副作用时，重新设计其接口或拆分该例程。
- 当读者必须去解码单位、取值范围、精度、编码方式、归属、状态、魔数或原始类型的标志时，把这些含义挪进命名、常量、类型或结构中。
- 当输入跨越用户、文件、网络、外部系统或其他信任边界时，明确决定什么被校验、什么被拒绝、如何恢复、断言什么，以及如何保持可诊断。
- 当分支、循环、递归、退出点或异常路径变得难以验证时，先简化再添加逻辑。
- 当重复的分支判断映射的是稳定的类别、区间、转换、校验、分派或类配置的规则时，考虑使用经过校验的表格。
- 当一个类或模块暴露了内部表示、膨胀成上帝对象，或混杂了不相关的职责时，恢复其抽象边界。
- 当测试只覆盖了主流程时，补上常规、边界、非法输入、防御性检查、例程契约和数据驱动的边缘用例。
- 当调试是从一个猜测开始时，先让故障可复现、收集证据、隔离执行路径，并解释清楚成因。
- 当重构理解不足或有风险的代码时，先补上测试或分析，并让行为变更保持分离。
- 当开始性能工作时，设定目标、测量当前行为、一次只改一个地方、重新测量，并记录任何在清晰性上的权衡。
- 当注释只是重述显而易见的机械细节或已经过时时，重写代码或删掉注释；当代码无法表达意图、约束或用法时，在紧邻处添加一条准确的注释。
- 当局部风格开始偏离时，遵循共享的格式、命名、文件结构和惯用法约定，不要创造出模块专属的方言。

## 最终检查清单

- 需求、与架构的契合度、风险、规范和构建方法是否已足够清晰。
- 命名、例程、数据、类、排版、注释和规范是否降低了读者的工作量。
- 输入、错误、断言、契约、不变式、不可能状态和信任边界的处理是否都是有意为之。
- 控制流、循环、表格、递归、退出点和异常路径是否简单到足以审查。
- 测试、评审、调试、重构、集成、工具使用和调优是否都基于证据。
- 这次改动是否小到足以验证，并且能经得起仔细的评审。
