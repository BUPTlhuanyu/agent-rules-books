# 遵循《代码大全》（Steve McConnell）

## 何时使用

作为一份紧凑、常驻生效的构建纪律，用于实现、评审、调试、重构与调优。

## 需要纠正的首要偏见

代码能跑还不够。构建过程必须降低缺陷风险、控制复杂度，并让人工审查变得廉价。

## 决策规则

- 在从一个解决方案设想开始写代码之前，先厘清需求、与架构的契合度、风险、约定俗成的规范以及主要构建决策。
- 优先选择清晰、局部性、显式、简单的控制流和一致的风格，而非精巧的紧凑写法或时髦的惯用法。
- 让例程、类和模块保持内聚、命名精确、接口窄小、封装良好且难以误用。
- 通过命名、常量、更强的类型、封闭的状态集、有意的初始化、单位和归属，让数据的含义可见。
- 在信任边界上做校验；用断言、不变式和契约表达程序员的假设；让错误处理显式且可诊断。
- 让分支、循环、退出点、异常和表驱动逻辑保持在可验证的简单程度内。
- 以小步、基于证据的循环来构建、测试、评审、调试、重构、集成和调优：先定位根因再修复，先建立行为保护网再重构，先测量再优化。
- 用注释、文档、工具和规范来减少读者或手工的工作量，绝不用它们来掩盖糟糕的结构。

## 触发规则

- 当解决方案先于问题的澄清而出现时，重新陈述需求、约束和构建风险。
- 当读者必须去解码命名、标志、原始类型、单位、状态或排版格式时，把含义显式建模出来。
- 当一个例程混杂了多个阶段，或接口难以使用时，拆分关注点或改变数据模型。
- 当输入跨越信任边界时，明确决定校验、拒绝、恢复、断言和诊断策略。
- 当控制流、循环、异常或分支表难以审查时，先简化再添加逻辑。
- 当测试只验证了主流程时，补上边界、非法输入、防御性检查、契约和数据驱动的用例。
- 当调试、重构或性能工作是从猜测出发时，先取得证据。
- 当注释在重复显而易见的机械细节时，重写代码或删掉注释；注释应留给意图和约束。

## 最终检查清单

- 构建的上下文是否清晰？
- 代码形态是否便于审查？
- 数据含义是否显式？
- 边界是否有防御、故障是否可诊断？
- 控制流是否简单？
- 是否有能发现缺陷的测试与评审？
- 修复、重构和调优是否都先有证据？
