# 遵循《企业应用架构模式》（Martin Fowler）

## 目的

本仓库遵循 **《企业应用架构模式》** 那种务实风格：
围绕领域逻辑、持久化、事务边界、集成和表现层各自的清晰职责，来组织企业软件的结构。

所有代码生成、编辑和评审都必须以下列目标为优化方向：
- 显式的关注点分离
- 业务逻辑归属可预期
- 采用恰当的企业模式，而非偶然形成的耦合
- 可管理的持久化与事务边界
- 内存对象与外部系统之间清晰的映射
- 在真实企业约束下依然可维护的代码

本文件是一份有约束力的工程政策：`MUST`（必须）具有强制力，`SHOULD`（应当）是强默认值，`MUST NOT`（禁止）表示不得为之。

---

## 首要指令

企业软件不会因为给每个功能都从零发明一套架构而变好。
优先采用少量被充分理解的结构性模式，并有意识地运用它们。

当不确定时，选择那个能让下列职责都显式化的设计：
- 表现与传输
- 应用流程
- 领域逻辑
- 数据源交互
- 事务管理
- 并发控制
- 集成边界

不要让某一个类或某一层拥有其中全部职责。

---

## 架构基线

### 分层
把分层作为默认的组织原则：
1. 表现与交付
2. 应用编排
3. 领域逻辑
4. 数据源与集成访问

规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）：
- 上层可以依赖下层
- 下层不得触及表现层的关注点
- 每一层都必须通过降低耦合或澄清职责来赚回其存在的合理性

反模式（MUST NOT）：
- 控制器直接伸手去碰 SQL 和事务细节
- 领域逻辑嵌在视图或处理器里
- 仓储返回 HTTP 形状的 DTO
- 只做调用转发的假分层

---

## 选择业务逻辑模式

### 事务脚本（Transaction Script）
在以下情况使用：
- 逻辑简单
- 每个请求或用例基本彼此独立
- 不需要丰富的领域建模

规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）：
- 脚本必须保持短小并以用例为焦点
- 不要让事务脚本变成所有业务逻辑的垃圾场
- 如果重复、生命周期或不变式复杂度增长，就升级到更强的模式

### 表模块（Table Module）
在以下情况使用：
- 逻辑天然围绕表格化数据集组织
- 计算是面向集合的
- 对象标识不是主要的组织力量

规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）：
- 让行为以表抽象为中心
- 如果真实模型从根本上就是表格化的，不要伪造实体
- 把表格化逻辑与表现层、传输层隔离开

### 领域模型（Domain Model）
在以下情况使用：
- 领域复杂度较高
- 业务规则、不变式和生命周期都很重要
- 标识、协作关系和行为都应属于模型

规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）：
- 丰富的领域逻辑属于模型对象
- 让应用编排与领域决策保持分离
- 在行为丰富的领域中避免贫血模型

---

## 应用流程规则

### 服务层（Service Layer）
用服务层来定义应用操作。

规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）：
1. 应用服务负责编排用例。
2. 它们定义事务边界和编排逻辑。
3. 它们默认不得吸纳全部领域逻辑。
4. 它们应当暴露面向应用的 API，而不是 UI 机制。

### 远程门面（Remote Facade）
在以下情况使用：
- 边界是远程的
- 粗粒度 API 能减少频繁往返的调用
- 传输层形状与内部设计不同

规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）：
- 暴露粗粒度的远程操作
- 在远程契约与内部模型之间做转换
- 把远程传输相关的关注点留在边界处

### 数据传输对象（DTO）
在以下情况使用：
- 数据跨越进程或分层边界
- 把多个值打包能降低远程调用或序列化成本
- 转换能保护内部模型

规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）：
- DTO 是传输结构，不是领域模型
- 让映射保持显式
- 不要把业务行为搬进 DTO

---

## 持久化模式规则

### 仓储（Repository）
用仓储在领域对象访问之上提供一个类集合的接口。

规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）：
1. 仓储必须说领域语言。
2. 仓储接口应当反映领域的访问需求，而不是表的形状。
3. 仓储实现隐藏查询、映射和存储细节。
4. 仓储不得沦为通用的"什么都干"的网关。

### 数据映射器（Data Mapper）
在以下情况使用：
- 领域模型应当与数据库结构解耦
- 对象-关系不匹配是真实存在的问题
- 持久化逻辑值得被隔离出来

规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）：
- 映射代码属于领域对象之外
- 不要迫使领域对象了解 SQL、记录格式或映射机制
- 让映射保持显式且可测试

### 行数据网关（Row Data Gateway）
当行为简单且以记录为中心时使用。

### 表数据网关（Table Data Gateway）
当操作天然以表为中心、且一个表接口能清晰地集中访问逻辑时使用。

### 活动记录（Active Record）
仅当领域逻辑简单、且与持久化耦合可被接受时使用。
不要在复杂领域中默认选用活动记录。

---

## 标识、缓存与工作单元规则

### 标识映射（Identity Map）
- 在需要之处，让每个作用域内每个标识只对应一份内存表示
- 避免同一个逻辑工作单元内部出现重复对象实例相互冲突

### 工作单元（Unit of Work）
- 让事务性的写入协调显式化
- 把工作作为一个逻辑单元提交
- 让工作单元的作用域保持可理解

### 延迟加载（Lazy Load）
- 有意识地使用，而不是处处使用
- 弄清延迟加载可能在何处触发远程/数据库往返
- 避免在循环和序列化路径上出现延迟加载带来的意外

反模式（MUST NOT）：
- 到处都是看不见的 N+1 行为
- 隐藏的自动持久化，写入时机令人意外
- 从各个随机调用方随意地保存每个对象

---

## 对象-关系映射模式索引

- 当内存对象需要稳定的数据库标识时，使用「标识字段」（Identity Field）；让标识映射保持显式。
- 当对象引用映射到关系型键时，使用「外键映射」（Foreign Key Mapping）；避免把昂贵的连接藏在看似无害的对象遍历背后。
- 当多对多关系需要一张独立的关系表时，使用「关联表映射」（Association Table Mapping）。
- 当子对象在其所有者之外没有独立的数据库标识时，使用「依赖映射」（Dependent Mapping）。
- 当一个小的值对象可以存放在所属行内、且没有独立生命周期时，使用「嵌入值」（Embedded Value）。
- 仅当不需要在该值内部做查询、且序列化的版本管理可控时，才使用「序列化 LOB」（Serialized LOB）。
- 当"一张带可空列的表"比多次连接更简单时，使用「单表继承」（Single Table Inheritance）。
- 当规范化的子类型数据值得付出连接的复杂度时，使用「类表继承」（Class Table Inheritance）。
- 当每个具体类型都能拥有自己的表、且不会造成过多冗余时，使用「具体表继承」（Concrete Table Inheritance）。
- 使用「继承映射器」（Inheritance Mappers）把继承相关的持久化决策与领域逻辑隔离开。
- 当映射规则规整到足以被安全集中时，使用「元数据映射」（Metadata Mapping）；当元数据会掩盖例外行为时避免它。
- 当查询构造需要一个可组合的对象模型、而非散落的 SQL 字符串时，使用「查询对象」（Query Object）。

## 并发与事务规则

### 乐观离线锁（Optimistic Offline Lock）
当冲突可能发生但并不常见时使用。

规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）：
- 检测出相互冲突的并发更新
- 安全且显式地失败
- 有意识地呈现冲突解决或合并语义

### 悲观锁（Pessimistic Locking）
仅当预期存在争用、且这份代价有充分理由时使用。

### 事务边界
1. 事务边界必须在应用流程中显式呈现。
2. 在可能的情况下，避免跨越远程调用的事务。
3. 让事务保持短小。
4. 不要把事务归属埋进辅助类的深处。

### 其他离线并发模式
- 当相关对象必须被一并加锁以保住一次用户级编辑时，使用「粗粒度锁」（Coarse-Grained Lock）。
- 仅当加锁能被可靠地隐藏、且不会让并发对维护者完全不可见时，才使用「隐式锁」（Implicit Lock）。
- 不要让隐式加锁使事务归属或争用状况变得无法诊断。

## 表现层规则

1. 表现层代码处理输入、渲染和传输相关的关注点。
2. 业务规则不得存在于控制器或视图中。
3. 表现模型可以与领域模型不同。
4. 格式化、分页和 UI 交互状态属于领域逻辑之外。

务实地在页面控制器与前端控制器之间做选择，但要把路由关注点挡在业务逻辑之外。

### 表现层模式索引
- 使用「模型-视图-控制器」（MVC）分离领域模型、视图和控制器的职责。
- 当每个页面/动作都可以被独立处理时，使用「页面控制器」（Page Controller）。
- 当集中式的请求处理、认证、路由或分发有价值时，使用「前端控制器」（Front Controller）。
- 当服务端模板能清晰表达响应时，使用「模板视图」（Template View）。
- 当"把数据转换为输出"比"把逻辑嵌进模板"更清晰时，使用「转换视图」（Transform View）。
- 当共享的表现结构应当与页面特定内容分离时，使用「两步视图」（Two Step View）。
- 当流程与导航决策需要一个专门的协调者时，使用「应用控制器」（Application Controller）。

---

## 离线与集成规则

1. 外部系统必须通过清晰的边界来访问。
2. 把合作方的格式翻译成内部概念。
3. 集成事件/消息不是领域对象。
4. 不要让集成上的便利性主导内部设计。

反模式（MUST NOT）：
- 内部代码的形状围绕合作方 API 载荷来定
- 厂商 DTO 在整个应用中被直接使用
- 业务逻辑嵌在序列化代码里

---

## 会话状态与基础模式索引

- 仅当客户端存储可被接受、且完整性/安全性影响已被处理时，才使用「客户端会话状态」（Client Session State）。
- 当需要服务端托管的会话数据、且扩展性/清理成本已被明确时，使用「服务端会话状态」（Server Session State）。
- 当会话的持久性或跨服务器集群共享的价值超过数据库负载的代价时，使用「数据库会话状态」（Database Session State）。
- 使用「网关」（Gateway）隔离对某个外部资源或子系统的访问。
- 使用「映射器」（Mapper）在对象或分层之间搬移数据，同时保持两侧相互独立。
- 仅当共享的层级行为真实且稳定时，才使用「层超类型」（Layer Supertype）。
- 当客户端应当依赖一个位于实现细节之外的包中的接口时，使用「分离接口」（Separated Interface）。
- 谨慎地为知名对象使用「注册表」（Registry）；避免把它变成隐藏的全局依赖。
- 对那些"按值判等"和不可变性能简化代码的小值，使用「值对象」（Value Object）。
- 对货币金额使用「Money」，使舍入、币种和算术规则保持显式。
- 使用「特例」（Special Case）把反复出现的 null 或例外处理替换为一个具名对象。
- 当实现必须在不修改核心代码的前提下被选择或扩展时，使用「插件」（Plugin）。
- 使用「服务桩」（Service Stub）在没有真实远程服务的情况下测试或运行。
- 当表格化数据是天然的交换形态、且不需要对象行为时，使用「记录集」（Record Set）。

---

## 分布规则

1. 不要默认把对象或服务做远程分布化。
2. 远程边界必须是粗粒度的。
3. 把本地对象设计与远程契约设计分开。
4. 显式为延迟、序列化、版本管理和部分失败做预算。

反模式（MUST NOT）：
- 频繁往返的远程对象接口
- 假定网络之上具有本地方法调用的语义
- 通过远程端点泄漏领域内部结构

---

## 代码生成规则

生成代码时，按以下顺序进行：
1. 找出真正契合当前复杂度的业务逻辑模式
2. 把用例编排放在应用层/服务层
3. 当领域较为丰富时，把领域决策放在领域模型中
4. 把持久化置于仓储、映射器或网关之后
5. 显式定义事务边界
6. 只在边界处定义 DTO 或远程门面
7. 把表现与传输关注点保持在最外缘

默认选择：
- 简单 CRUD -> 事务脚本或简单的服务层
- 丰富的不变式 -> 领域模型 + 仓储 + 映射器
- 面向表的计算 -> 表模块或表数据网关
- 远程边界 -> 远程门面 + DTO

默认避免：
- 不论复杂度如何都到处使用领域模型
- 用一个通用仓储包打天下
- 把持久化模型直接暴露给调用方
- 把事务、校验、渲染和 SQL 放在同一个类里

---

## 评审规则

评审代码时，主动寻找：
- 控制器或视图中的领域逻辑
- 返回传输层形状的仓储
- 下层了解表现层细节
- 琐碎的 CRUD 被包上过度的建模
- 复杂规则被困在事务脚本中
- SQL 散布在业务代码里
- 缺失的事务边界
- 隐藏的工作单元行为
- 意外的 N+1 加载
- 频繁往返的远程 API
- 内部模型与远程模型之间没有任何转换

---

## 禁用模式

### 分层表演
- 五个只做方法调用转发的分层

### 到处都是通用仓储
- 用一套 CRUD 抽象覆盖所有领域和数据访问
- 仓储 API 的形状由表决定，而不是由用例决定

### ORM 主导一切
- 所有设计决策都由 ORM 的便利性决定
- 聚合、服务和 DTO 塌缩成同一个持久化模型

### 以控制器为中心的企业应用
- 请求处理器同时协调事务、SQL、领域规则和外部调用

### 分布式对象幻想
- 假装网络调用就是普通的方法调用

### 事务归属不清
- 各层散落着随意的 save 调用
- 没有明确的事务归属方
- 把长时间运行的流程当作一个即时事务来处理

---

## 测试规则

1. 在可能的情况下，把领域逻辑与表现层、持久化层分开测试。
2. 把仓储、映射器和网关作为数据访问基础设施单独测试。
3. 针对事务与编排行为测试服务层/应用层的工作流。
4. 在乐观锁或悲观锁重要之处测试并发行为。
5. 在边界处测试 DTO 与远程门面的映射逻辑。

---

## 评审检查清单

在最终定稿任何改动之前，核实：
- 我们是否为实际的复杂度选择了正确的业务逻辑模式？
- 表现、流程、领域逻辑和持久化的职责是否彼此分明？
- 事务归属是否显式？
- 仓储或网关的形状是由用例或聚合决定，而不是由原始表决定吗？
- 映射逻辑是否与领域逻辑隔离？
- 远程边界是否粗粒度且有显式转换？
- 我们是否避免了通用仓储的过度扩张？
- 我们是否避免了以控制器为中心的设计？
- 我们是否避免了分层表演？
- 我们是否让并发和加载方面的假设保持可见？

如果任何一项答案为否，在交付前先修订。

---

## 最终指令

当不确定时，选择那个最小的企业模式集合，它能让：
1. 业务逻辑的归属显而易见
2. 持久化与映射显式化
3. 事务边界清晰
4. 远程边界粗粒度且安全
5. 应用在真实企业约束下更易演进

同样地拒绝时髦的复杂度和偶然形成的耦合。
