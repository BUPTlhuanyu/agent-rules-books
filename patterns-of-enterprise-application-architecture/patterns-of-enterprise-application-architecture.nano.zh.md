# 遵循《企业应用架构模式》（Martin Fowler）

## 何时使用

作为一份紧凑、常驻生效的指南针，用于企业应用的模式选型。

## 需要纠正的首要偏见

复用模式不等于选择模式。在给出模式名称之前，先把职责、持久化、事务和远程边界弄清楚。

## 决策规则

- 让表现层/传输、应用流程、领域逻辑、数据源交互、事务管理、并发控制和集成边界在逻辑上彼此分离。
- 按复杂度选择业务逻辑模式：简单独立流程用事务脚本（Transaction Script），以表为中心的集合逻辑用表模块（Table Module），行为丰富、有不变式、标识或生命周期的场景用领域模型（Domain Model）。
- 用服务层（Service Layer）做用例协调和事务编排，但不要把它变成所有领域行为的默认归宿。
- 让持久化方案匹配耦合压力：需要与领域分离时用仓储/数据映射器（Repository/Data Mapper），访问记录或表时用网关（Gateway），仅在领域简单且可与持久化耦合时用活动记录（Active Record）。
- 在信任 ORM 的行为之前，先让工作单元（Unit of Work）、标识映射（Identity Map）、延迟加载、事务边界和锁语义清晰可见。
- 让表现层、DTO、集成消息、厂商载荷和序列化代码中不含业务行为。
- 把远程边界视为昂贵且易失败的：使用粗粒度的远程门面（Remote Facade）操作、DTO 转换、显式版本管理和部分失败处理。
- 只在有具体压力时才使用会话状态模式和基础模式；避免假分层、通用仓储、被 ORM 主导的设计、以控制器为中心的流程，以及分布式对象的幻觉。

## 触发规则

- 如果某个类或某一层同时拥有 UI、流程、领域规则、SQL、事务和外部调用，先拆分职责，再考虑引入更多模式。
- 如果一个简单的事务脚本长出了重复代码、不变式或生命周期决策，就把领域模型和持久化模式一并重新审视。
- 如果仓储只是表形状的 CRUD，或行为丰富的区域里模型只是表的镜像，或服务只做转发调用，检查一下设计是否已被数据库或 ORM 绑架。
- 如果出现延迟加载问题、重复标识、隐藏写入、N+1 行为、随意的保存调用或含义不明的锁，就显式定义标识作用域、工作单元、加载策略和并发语义。
- 如果远程 API 交互过于琐碎、呈对象形状，或泄漏了领域内部结构，就把它重新设计为带 DTO 转换的粗粒度用例边界。

## 最终检查清单

- 业务逻辑模式和持久化模式是否匹配实际复杂度？
- 分层、事务、标识、加载、锁、会话和集成的归属是否显式？
- 业务规则是否被挡在 UI、DTO、集成和序列化代码之外？
- 远程边界是否做到了粗粒度、有转换、有版本意识、有失败意识？
