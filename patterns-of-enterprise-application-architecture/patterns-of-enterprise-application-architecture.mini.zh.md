# 遵循《企业应用架构模式》（Martin Fowler）

## 何时使用

当设计或评审那些跨越表现层、应用流程、领域逻辑、持久化、事务、并发、集成、会话状态或远程边界的企业应用代码时使用。

## 需要纠正的首要偏见

企业应用不会因为给每个功能都发明一套架构，或让框架、ORM、数据库 Schema、传输层形状来决定设计而变好。应当用一小组被充分理解的模式，把职责和边界显式化。

## 决策规则

- 在给出模式名称之前，先明确职责归属：表现与传输、应用流程、领域逻辑、数据源交互、事务管理、并发控制和集成边界，绝不能塌缩进同一个类或同一层。
- 把分层作为默认的组织原则，但每一层都必须通过降低耦合或澄清职责来赚回其成本；禁止下层反过来触及表现层的关注点，并拒绝纯转发的分层表演。
- 依据实际受力选择业务逻辑模式：短小、独立、简单的流程用事务脚本，以表为中心的集合逻辑用表模块，规则、不变式、标识、生命周期或协作关系较重的场景用领域模型。
- 让事务脚本保持以用例为焦点，让表模块保持诚实的表格化形态，让领域模型拥有丰富的行为；当重复、生命周期或不变式复杂度增长时，向上升级模式。
- 用服务层定义应用操作、协调用例、拥有事务边界与编排逻辑、暴露面向应用的 API，并避免默认把所有领域逻辑都吸纳进来。
- 在远程或跨层边界处，用远程门面和 DTO 把粗粒度操作、批处理、转换和传输层形状显式化；DTO 是传输结构，不是领域模型。
- 有意识地选择持久化模式：仓储说领域语言并隐藏查询/映射/存储细节，数据映射器把 SQL 和记录格式挡在领域对象之外，网关集中管理记录/表访问，活动记录仅用于持久化耦合可被接受的简单领域。
- 让标识、写入协调和加载行为保持可见：用标识映射保证每个作用域内每个标识只对应一个对象，用工作单元完成一次逻辑上的事务提交，仅在隐藏的数据库或远程往返不会给循环和序列化器带来意外时才使用延迟加载。
- 依据标识、生命周期、查询需求、Schema 形状和演进成本来选择对象-关系映射方式；让标识字段、外键、关联表、依赖对象、嵌入值、序列化值、继承映射、元数据映射和查询对象都是显式选择的结果，而非偶然形成。
- 在应用流程中设计并发与事务：乐观锁检测冲突并把合并语义暴露出来，悲观锁需要有充分理由的争用作为依据，事务保持短小，远程调用通常置于事务之外，辅助函数不得隐藏事务归属。
- 只有当粗粒度锁和隐式离线锁能保住一次用户级编辑，同时又不会让归属、争用和过期锁的清理变得无法诊断时，才使用它们。
- 让表现层代码专注于输入、渲染、路由、格式化、分页、UI 状态和传输；业务规则不进入控制器、视图、模板和表现模型。
- 通过边界访问外部系统，把合作方的格式翻译成内部概念，把集成事件和消息当作边界数据，不要让厂商载荷或序列化代码塑造内部领域设计。
- 有意识地选择会话状态方案：客户端、服务端或数据库侧的会话存储，都必须考虑完整性、安全性、扩展性、清理、持久性、服务器集群间共享和数据库负载。
- 只在有具体压力时才使用基础模式：网关用于外部资源，映射器用于两侧相互独立的场景，层超类型用于真实的共享行为，分离接口用于打断依赖，注册表用于受控的知名对象，值对象和 Money 用于值语义，特例类用于反复出现的 null/默认行为，插件用于运行时扩展，服务桩用于远程服务测试，记录集用于表格化交换天然合适的场合。
- 不要默认把对象或服务分布化；当确实需要分布时，把本地对象设计与远程契约分开，并为延迟、序列化、版本管理和部分失败留出预算。
- 按此顺序生成代码：选定业务逻辑模式，把用例协调放进应用服务，把丰富的领域决策放进领域模型，用仓储/映射器/网关隐藏持久化，显式定义事务，只在边界处放置 DTO 或门面，把表现/传输保持在最外缘。
- 在每项职责真正归属的层次上测试它：领域逻辑脱离 UI 和持久化来测，仓储/映射器/网关作为数据基础设施来测，服务针对流程与事务来测，加锁在并发重要处来测，DTO/门面映射在边界处来测。

## 触发规则

- 如果领域行为出现在控制器、视图、处理器、SQL 脚本、触发器、DTO、框架胶水代码、序列化代码或厂商载荷适配器中，把它挪到归属层，或显式给出破例的理由。
- 如果某个类或某一层同时协调渲染、校验、SQL、事务、领域规则和外部调用，先按职责拆分，再考虑引入另一个模式。
- 如果一个事务脚本堆积起重复的决策、不变式或生命周期规则，重新审视领域模型及其配套的持久化模式。
- 如果在行为丰富的领域里模型却呈表形状、仓储只是通用 CRUD，或服务只向持久化层转发调用，检查一下 ORM 或数据库 Schema 是否已经接管了设计。
- 如果 SQL、映射、事务归属、加锁、保存操作或外部资源访问散落在各个调用方，引入那个能集中该规则的最小仓储、映射器、网关、工作单元、服务边界或策略。
- 如果在一个逻辑工作范围内可能出现延迟加载、内存中重复的标识、隐藏的自动持久化、N+1 行为或随意的保存调用，先定义标识作用域、工作单元和加载行为，再继续。
- 如果并发冲突、过期锁、用户级编辑或长时间运行的流程很重要，就明确选择乐观、悲观、粗粒度或隐式的加锁语义，而不是依赖开发者的非正式自律。
- 如果一个远程 API 看起来像本地对象协作、泄漏了领域内部结构，或一次用户操作需要多次调用，把它重新设计为带 DTO 转换的粗粒度用例契约。
- 如果会话状态的归属、生命周期、存储位置、安全性、扩展性、故障切换、持久性或清理行为不清晰，先选定会话状态模式，再添加功能。
- 如果某一层的存在只是为了转发调用、一个通用仓储包打天下、一个 ORM 模型同时兼作聚合/服务/DTO，或一个控制器拥有企业级流程，就把它当作评审中的"禁用模式"阻断项处理。

## 最终检查清单

- 表现、流程、领域、持久化、事务、并发、集成、会话和分布方面的职责，是否都是有意分离的？
- 业务逻辑模式是否匹配实际复杂度，而不是出于习惯或框架形状？
- 仓储、映射器、网关、活动记录、工作单元、标识映射和延迟加载，是否只用在它们的受力条件确实吻合之处？
- 事务归属是否显式、短小，并被挡在隐藏的辅助函数和远程调用区间之外？
- 并发冲突、离线锁、标识作用域和加载行为是否可见？
- 远程和集成边界是否做到了粗粒度、有转换、有版本意识、有失败意识？
- 会话状态是否归属明确、受保护、可扩展、持久性足够，并会被清理？
- 测试是否与每项行为真正的职责归属对齐？
