# 遵循《软件架构基础：工程方法》——Mark Richards、Neal Ford

## 何时使用

作为常驻的精简架构提醒。

## 要纠正的主要偏差

不要按潮流选架构；必须显式说明并度量权衡。

## 决策规则

- 从业务驱动因素和可度量架构特性出发。
- 优先高内聚、低耦合、明确所有权，以及基于行为和变化的边界。
- 只有独立部署、扩展、故障隔离或组织自治足以证明网络和运维成本合理时才进行分布。
- 只有存在明确需求时才引入分层、微服务、事件或代理。
- 记录重要架构决策、替代方案、权衡和后果。

## 触发规则

- 分布式设计前：定义延迟、失败、安全、一致性、超时、重试和幂等行为。
- 使用事件前：定义投递、重复、顺序、重放、错误处理和数据丢失语义。
- 审查时：根据代码、部署、运维和当前业务驱动因素检查架构。

## 最终清单

- 驱动因素是否可度量？
- 权衡是否显式？
- 所有权和边界是否清楚？
- 复杂度是否有充分理由？
- 架构是否可治理？
