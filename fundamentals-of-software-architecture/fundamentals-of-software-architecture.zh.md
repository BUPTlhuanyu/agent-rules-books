# 遵循《软件架构基础：工程方法》——Mark Richards、Neal Ford

## 来源与状态

本规则集根据 Mark Richards 和 Neal Ford 的《Fundamentals of Software Architecture: An Engineering Approach》（O'Reilly，2020）及用户提供的 PDF 蒸馏而成。目前为待人工审阅草稿。

## 目的

在设计、审查或演进软件架构时使用本规则。将架构理解为一组重要的结构决策、架构特性和设计原则，它们共同决定系统及其变更能力。

## 架构思维

- 架构师必须先理解业务驱动因素，再选择架构风格或技术。
- 架构师必须区分架构决策（约束和允许的结构）与设计原则（指导局部设计选择的准则）。
- 架构师应保持技术广度，理解技术方案的权衡，而不是成为某个工具或风格的拥护者。
- 架构师必须显式说明权衡。不存在普适的最佳架构，应根据优先级选择当前最不差的方案。
- 架构师应保持足够的动手实现，以便用现实约束校验架构决策。
- 架构师必须持续分析架构，确认它仍然满足当前业务和运行需求。
- 当技术、业务条件或运行约束发生变化时，架构师必须重新质疑继承下来的公理和假设。

## 架构特性

- 团队必须识别真正影响系统的架构特性，例如性能、可扩展性、可用性、可靠性、安全性、可观测性、可部署性、可测试性和可维护性。
- 团队必须区分需求中明确提出的特性，以及从领域、运行、法律或组织因素中发现的隐含特性。
- 团队必须用可度量或可测试的形式定义特性，不能只写“快”“安全”或“可扩展”。
- 团队应控制关键特性的数量，使权衡保持可见；每增加一种特性，都会增加约束和成本。
- 团队必须把横切特性作为架构问题处理，不能把它们留给局部实现偶然决定。
- 团队应使用 fitness functions、自动化检查或其他可重复度量来治理重要特性。
- 当范围、规模、组织或部署环境变化时，团队必须重新检查架构特性。

## 模块化与边界

- 团队必须追求高内聚、低耦合，同时识别不同强度和形式的耦合。
- 团队应把一起变化的行为和数据放在一起，把因不同原因变化的内容分开。
- 团队必须分析 connascence，即组件之间必须共同了解或共同修改的程度；优先选择静态、局部、弱形式。
- 团队必须根据工作流、职责、领域行为和架构特性划分组件，而不能只根据数据库实体或技术层划分。
- 当业务能力和独立变化比技术相似性更重要时，团队应采用领域分区。
- 在分配职责和特性之后，团队必须重新评估组件粒度；初始分区只是待验证假设。
- 团队应使依赖和所有权显式化，避免造成过多协调和连锁修改的边界。

## 架构量子与部署

- 团队必须判断系统需要一个架构量子，还是多个可独立部署的架构量子。
- 团队必须考虑分布式架构的成本：网络延迟、可靠性、安全、序列化、运维复杂度和数据一致性。
- 当功能共享强一致性要求且频繁跨边界调用时，团队应将它们保持在一起。
- 只有独立部署、独立扩展、故障隔离、组织自治或其他明确特性足以证明成本合理时，团队才应进行拆分。

## 架构风格选择

- 团队必须根据需求和架构特性选择风格，而不能根据潮流、熟悉程度或对某技术的偏好选择。
- 分层架构适合强调清晰隔离和简单性的场景，但必须警惕不恰当分层、共享数据库耦合以及跨越所有层的变更。
- 管道架构适合由独立、连续的转换步骤组成，且每一步都有清晰输入输出契约的场景。
- 微内核架构适合拥有稳定核心和可替换插件的产品。
- 服务化架构适合粗粒度服务和集中式或分区数据符合领域的场景；必须检查服务间耦合和事务问题。
- 事件驱动架构适合确实需要异步通信、时间解耦、响应性或独立反应的场景。
- 团队不得仅为了显得现代，或为了解决未经度量的问题而引入微服务、事件代理或分布式工作流。
- 团队必须记录选择某种风格的优势、劣势及架构特性评分。

## 分布式系统

- 团队必须假设网络并不可靠、延迟不为零、带宽不是无限的，且传输存在成本。
- 团队必须把网络视为不安全、会变化、异构且由多个主体管理的环境。
- 分布式设计必须定义超时、重试、失败、幂等、认证、授权、可观测性和恢复行为。
- 团队必须有意识地决定数据存放位置，以及通信采用同步还是异步。
- 当需要即时响应和简单一致性时，默认使用同步通信；只有在时间解耦、韧性、吞吐量或独立处理的收益值得额外复杂度时，才使用异步通信。
- 事件驱动系统必须定义投递、顺序、重复、重放、错误处理和防止数据丢失的语义。

## 架构决策与风险

- 架构师必须记录重要决策、上下文、考虑过的替代方案、权衡和后果。
- 架构师应在架构约束层面记录决策，而不是记录每个局部实现细节。
- 团队必须在做出选择前分析架构风险，尤其关注耦合、分布、数据所有权和运维复杂度。
- 团队应使用轻量级决策记录，并在假设或业务驱动因素变化时重新审视。
- 架构图必须说明目标读者、范围、边界、职责以及运行时或部署关系。
- 架构图不能被当成架构本身；必须用代码、部署和运行事实进行验证。

## 演进与治理

- 团队必须针对真正可能变化的特性设计可变性，但不得在没有可信变化场景时增加灵活性。
- 团队应使用 fitness functions 和自动化治理持续检测架构腐化。
- 架构治理应通过护栏和反馈赋能团队，而不是集中所有设计决策。
- 架构师必须考虑组织结构、团队所有权、流程、运维、成本、法律约束和组织政治。
- 架构师应在谈判前收集信息、用证据沟通；当其他论据不足时，明确说明成本和时间。

## 审查清单

- 业务驱动因素和可度量架构特性是否明确？
- 权衡和被拒绝的替代方案是否记录？
- 边界是否基于行为、所有权、工作流和变化模式？
- 分布式设计是否有明确理由，并定义了失败语义？
- 是否有架构治理和演进机制？
- 架构是否仍然可理解、可演进，并与团队所有权一致？
