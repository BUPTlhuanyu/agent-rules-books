# 遵循《软件架构基础：工程方法》——Mark Richards、Neal Ford

## 何时使用

用于架构设计、审查、演进，以及技术或架构风格选择。

## 要纠正的主要偏差

架构是一组显式权衡和可度量约束，不是时髦的图或框架选择。

## 决策规则

- 从业务驱动因素和可度量架构特性出发，选择当前最不差的方案。
- 区分架构决策和设计原则，记录重要决策、替代方案和后果。
- 保持高内聚、低耦合以及局部且较弱的 connascence，把行为和数据放在共同变化的概念内。
- 根据工作流、职责、所有权和变化模式识别组件，而不是只按数据库实体识别。
- 根据一致性、扩展、自治和运维成本选择部署边界。
- 把分布式系统的失败、安全、延迟、序列化和一致性作为显式问题处理。
- 默认使用同步通信；只有收益足以证明额外复杂度时才使用异步通信。
- 只有架构特性明确要求时才引入微服务、代理、分层或其他机制。
- 用 fitness functions 或可重复检查度量并治理重要架构特性。
- 为可信的变化场景设计演进能力，拒绝推测性灵活性和不必要的间接层。

## 触发规则

- 选择架构风格时，将其特性、优缺点和运维负担与实际驱动因素对比。
- 拆分组件或服务时，检查事务边界、数据所有权、工作流耦合和连锁影响。
- 分布式设计必须定义超时、重试、幂等、投递、顺序、重放、恢复和可观测性语义。
- 使用事件前，先定义重复、错误处理和防止数据丢失的语义。
- 审查架构时，用代码、部署、运行事实和当前业务驱动因素验证架构图与决策。
- 当继承的假设不再适合当前条件时，显式质疑并替换它。

## 最终清单

- 业务驱动因素和可度量特性是否明确？
- 权衡和决策记录是否完整？
- 边界是否基于行为和所有权？
- 复杂度是否有充分理由？
- 架构是否可治理？
