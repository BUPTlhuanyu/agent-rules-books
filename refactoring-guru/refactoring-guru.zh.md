## 目的

重构是在不增加新功能的前提下、受控地改进代码结构的过程。

使用这些规则来：

- 在改动之前和过程中识别代码坏味道
- 判断当下是否有理由进行重构
- 选择那个能应对该坏味道的最小手法
- 让每一次变换都保持行为不变
- 留下更简单、更清晰、更易修改的代码

本规则集中的"整洁代码"指这样的代码：

- 对其他程序员而言显而易见
- 避免重复的知识和重复的控制流
- 活动部件数量最少
- 能通过相关测试
- 比它所取代的代码更易维护、维护成本更低

## 首要指令

修改既有代码时，先诊断出那个让本次改动变困难的坏味道。

然后选择那个能在保持行为不变的前提下、消除或隔离该坏味道的最小重构手法。

绝不要把重构当成一次含义模糊的清理。每一次重构都 MUST 具备：

- 它所应对的某个具体的坏味道、摩擦或维护成本
- 一个有边界的变换
- 一条验证路径
- 不夹带任何隐藏的功能变更

## 重构流程

### 让重构保持独立

- MUST NOT 把直接的功能开发与重构混在一次难以区分的编辑中。
- SHOULD 至少通过提交、补丁分节或清晰标注的步骤，把重构与行为变更分开。
- MUST 在重构期间保持既有行为不变。
- MUST 把任何行为变更明确称为功能开发或缺陷修复，而不是重构。
- 当脏代码阻碍理解、或让功能实现变别扭时，SHOULD 先重构再做功能开发。
- 当功能开发留下了新的重复、别扭的命名或不必要的结构时，SHOULD 在功能开发之后重构。

### 以小步推进

- MUST 把重构作为一系列小改动来施加。
- 在可行处，MUST 让程序在每个有意义的步骤之后都保持可正常工作。
- SHOULD 在每次有风险的结构性变更之后运行相关测试。
- 当一次重构大到无法局部推理时，MUST 停下并收缩范围。
- SHOULD 优先采用若干具名的变换，而不是一次大范围重写。
- MUST NOT 把重构当作失控的重新设计的掩护。

### 持续验证

- 在有风险的重构之前，MUST 确定相关的测试或检查手段。
- 重构之后，MUST 运行所有相关的既有测试。
- 如果测试失败，MUST 判断是重构改变了行为，还是测试与实现细节耦合过深。
- MUST 先修好重构中的失误，再继续。
- 当脆弱的低层测试阻碍保持行为不变的结构改动时，SHOULD 替换它们或把它们提升到更高层次。
- MUST NOT 为了让某次重构看起来成功而删除失败的测试。

### 让结果更整洁

- 只有当被触碰区域的代码变得更整洁时，重构才算成功。
- MUST NOT 执行那种让代码依然同样含糊、重复或臃肿的重构。
- 当一连串小编辑并未改善清晰度时，SHOULD 暂停并重新诊断。
- 只有当代码极其潦草、测试已存在或已先行补上、且明确分配了足够时间时，SHOULD 才考虑一次有计划的重写。

## 何时重构

### 三次法则

- MAY 直接实现第一次出现的情形。
- 当抽象尚不确定时，SHOULD 容忍第二次相似的出现。
- 在第三次相似的出现时，MUST 考虑进行重构。
- 在重复的职责尚未清晰之前，MUST NOT 对偶然的相似性做抽象。

### 在添加功能时

- 当既有代码脏到无法安全理解本次改动时，SHOULD 先重构。
- SHOULD 重塑局部结构，使该功能实现起来变得顺畅。
- MUST 让准备性重构与功能行为保持分离。
- SHOULD 把这次功能需求当作偿还那笔阻碍它的具体债务的机会。

### 在修复缺陷时

- SHOULD 检查缺陷周边区域是否存在隐藏的复杂度、重复和归属不清。
- 当清理量小且局部时，SHOULD 清理那个让缺陷得以藏身的结构。
- MUST 把已观测到的缺陷修复，作为一次与配套重构分离的行为变更来保留。

### 在代码评审时

- SHOULD 把评审当作代码公开之前捕获坏味道的最后机会。
- 当评审的上下文和归属允许时，SHOULD 立即修掉简单的坏味道。
- 对较大的坏味道，SHOULD 做出评估并将其隔离出来，而不是把它偷偷塞进被评审的改动里。
- 当某个坏味道需要对意图作出判断时，SHOULD 与作者协作。

## 技术债规则

- 把技术债视为一种会因拖慢未来开发而复利累积的成本。
- 如果补丁、权宜之计、缺失的测试或含糊的结构会让后续改动更慢或更有风险，MUST NOT 把它们辩解为无害。
- 当债务来源是业务压力、缺失测试、薄弱的模块化、被延后的重构、糟糕的文档、长期隔离的分支或不一致的规范时，SHOULD 把这一来源揭示出来。
- MUST 优先处理那些影响当前变更速度、正确性或团队理解的债务。
- SHOULD 在日常的功能与缺陷工作中渐进式地削减债务。
- MUST NOT 把所有重构都推迟到未来某个清理项目，除非当前改动确实无法安全地吸收它。

## 坏味道检测流程

触碰既有代码时，按以下顺序扫描：

1. 臃肿者（Bloaters）：代码增长到难以理解或难以修改。
2. 面向对象滥用者（Object-orientation abusers）：继承、类型码或条件判断在误用对象模型。
3. 变更阻碍者（Change preventers）：一处改动迫使你修改太多地方，或一个类因不相关的原因而变化。
4. 可去除者（Dispensables）：代码的存在并未赚回其维护成本。
5. 耦合者（Couplers）：类之间彼此了解过多，或委托过多以致职责消失。
6. 库能力缺口（Library gaps）：外部类逼得你重复地写各种绕行代码。

对每一个坏味道：

- 识别症状
- 识别它为何让改动变得更难
- 选择相匹配的处理手法
- 检查所建议的处理手法是否会造成更糟的耦合或不必要的抽象
- 施加那个最小的有用重构

### 诊断、处理、验证、停止

对每一次非平凡的重构使用以下工作流：

1. 诊断坏味道：
   - 命名可见的症状
   - 命名它带来的维护成本
   - 判断该坏味道是局部的、重复出现的，还是架构层面的
   - 检查这个坏味道是真实存在的，还是只是一种风格偏好
2. 选择处理手法：
   - 挑选目录中那个直接应对该坏味道的手法
   - 在动用更大的结构性动作之前，优先选择较小的手法
   - 在动手编辑之前，先设想出期望达到的更整洁的终态
   - 如果某个处理手法自身的权衡代价比这个坏味道更糟，就拒绝它
3. 验证行为：
   - 在搬移代码之前，先确定既有测试、特征检查、类型检查或手工检查的方式
   - 在每个有风险的步骤之后运行相关检查
   - 如果行为发生变化，就停止把这次改动当作重构，并把行为变更隔离出去
4. 决定停止条件：
   - 当被命名的坏味道已消失或明显减轻时停止
   - 当下一步改进需要另一种坏味道诊断时停止
   - 当重构会在未获明确批准的情况下跨越归属、公开 API 或功能范围时停止
   - 当代码对所要求的改动而言已足够整洁、进一步清理已属推测性时停止

MUST NOT 仅因为发现了另一个坏味道就继续重构。把下一个坏味道单独记录下来，除非它阻碍当前改动。

### 坏味道的例外规则

- MUST NOT 机械地处理每一个坏味道；先确认该处理手法确实改善了本代码库的清晰度。
- 当用多态替换某个简单条件判断反而会掩盖一条直白的规则时，MAY 就让这个条件判断保持原样。
- 当共享抽象会比这份重复更不直观时，MAY 让重复的片段保持分离。
- MAY 保留那些解释"为什么"、说明外部约束，或描述已经抵抗住更简单结构的算法的注释。
- 当一个小类传达了一个真实的扩展点或边界时，MAY 保留它。
- 当设计有意支持可互换的行为时，MAY 让行为与数据保持分离。
- 当移除参数会造成更强的、不受欢迎的依赖时，MAY 暂时保留过长的参数列表。
- 当在被触碰的代码中留下了一个可见的坏味道时，MUST 记录或上报这次有意的不处理。

## 臃肿者

### 过长函数（Long Method）

- 触发条件：一个方法长到需要滚屏、需要注释或需要在脑中记账才能理解。
- 一旦某个方法明显偏长，MUST 提出质疑；十行是一个警戒阈值，而不是一条机械的硬限制。
- 当某个代码片段需要一条注释来解释它做了什么时，SHOULD 提炼函数。
- SHOULD 把循环、条件分支和连贯的阶段提取为具名方法。
- 当局部变量阻碍提取时，SHOULD 使用「以查询取代临时变量」、「引入参数对象」或「保持对象完整」。
- 当提取因大量局部变量或紧耦合的算法而受阻时，SHOULD 使用「以函数对象取代函数」。
- MUST NOT 仅因为一次方法调用可能带来微不足道的性能开销就回避提取。

### 过大的类（Large Class）

- 触发条件：一个类的字段、方法、职责或行数太多，无法作为一个概念来理解。
- SHOULD 拆分那种同时戴着多顶功能帽子的类。
- 当一部分字段和方法构成了一项独立职责时，SHOULD 使用「提炼类」。
- 当罕见或变体行为让主类膨胀时，SHOULD 使用「提炼子类」。
- 当客户端只需要一个稳定的行为子集时，SHOULD 使用「提炼接口」。
- 当界面对象承载了业务状态时，SHOULD 把 GUI 持有的领域数据移入领域类。
- 如果提取出来的部分并没有稳定的职责，MUST NOT 仅因为一个类庞大就拆分它。

### 基本类型偏执（Primitive Obsession）

- 触发条件：原始类型、字符串、数字、常量或数组在充当有意义的概念。
- SHOULD 用承载含义与校验的小对象，替换反复出现的原始值。
- 对某个带有领域行为或约束的单一原始类型，SHOULD 使用「以对象取代数据值」。
- 当类型码控制行为时，SHOULD 使用「以类取代类型码」、子类，或状态/策略模式。
- 当数组位置具有具名含义时，SHOULD 使用「以对象取代数组」。
- 当某个字面值承载领域含义时，SHOULD 使用「以符号常量取代魔数」。
- 如果包装器并未带来名称、校验、行为或错误预防，MUST NOT 把原始类型包进新类型。

### 过长参数列表（Long Parameter List）

- 触发条件：一个方法需要超过三四个参数，或调用方必须背下参数顺序。
- SHOULD 用「以函数调用取代参数」替换那些可推导出来的参数。
- 当被调方需要某个对象的多个值时，SHOULD 用「保持对象完整」传入这个既有对象。
- 当若干参数构成了一个反复出现的概念时，SHOULD 引入参数对象。
- 如果移除参数会在类之间造成不受欢迎的依赖，MUST NOT 移除它们。

### 数据泥团（Data Clumps）

- 触发条件：同一组值出现在多个字段、多个签名或多处调用中。
- SHOULD 检验：如果去掉其中一个成员，这些值是否还有意义；若没有，就把这一组建模出来。
- 对反复出现的字段组，SHOULD 使用「提炼类」。
- 对反复出现的参数组，SHOULD 使用「引入参数对象」。
- 当多个方法反复接收同一个概念的碎片时，SHOULD 传入整个对象。
- 在恰当之处，SHOULD 把使用该泥团的行为搬移到新对象上。
- 如果传入整个对象会造成对一个大得多的协作者的不良依赖，MUST NOT 这样做。

## 面向对象滥用者

### switch 语句（Switch Statements）

- 触发条件：复杂的 `switch` 或反复出现的 `if` 链，按类型、模式或类别做分支。
- 当新增一个分支情形需要修改多处 switch 时，SHOULD 怀疑这里缺失了多态。
- SHOULD 把 switch 逻辑提取出来，搬移到拥有该决策的那个类。
- 当行为随类型而变时，SHOULD 用子类或状态/策略模式替换基于类型码的分支。
- 一旦结构变得显式，SHOULD 用多态替换条件式分派。
- 当只有少数几个简单的参数变化时，SHOULD 使用明确的方法而非多态。
- 当某个分支只为处理 null 而存在时，SHOULD 使用空对象。
- MUST NOT 用不必要的多态替换一个简单诚实的条件判断或工厂选择逻辑。

### 临时字段（Temporary Field）

- 触发条件：某些字段只在特殊情形下有意义，其余时候为空或无效。
- SHOULD 把该算法及其临时状态提取到一个独立的类中。
- 当一个方法之所以需要临时字段只是为了承载许多中间值时，SHOULD 使用方法对象。
- 当围绕"状态缺失"的条件检查在代码中占据主导时，SHOULD 使用空对象。
- MUST NOT 把半初始化的对象当作正常设计而使之常态化。

### 被拒绝的遗赠（Refused Bequest）

- 触发条件：一个子类继承了它并不使用、或无法履行的行为或数据。
- SHOULD 把未被使用的方法或字段下推到确实需要它们的那些子类。
- 当这种子类关系具有误导性时，SHOULD 用委托取代继承。
- 只有当未被使用的继承行为无害、且不会让客户端困惑时，SHOULD 才保留继承。

### 异曲同工的类（Alternative Classes with Different Interfaces）

- 触发条件：两个类做同样的工作，却暴露了不同的方法名或签名。
- SHOULD 用「函数改名」对齐名称。
- SHOULD 用「搬移函数」、「添加参数」或「参数化函数」对齐签名。
- 当重复的行为只是部分重叠但真实存在时，SHOULD 提炼超类。
- 在共同的接口和行为使其中一个变得多余之后，SHOULD 删掉这个备选类。
- 当这些备选类分别位于不同的外部库中、统一起来不切实际时，MAY 让它们保持分离。

## 变更阻碍者

### 发散式变化（Divergent Change）

- 触发条件：一个类必须因许多互不相关的原因而变化。
- SHOULD 用「提炼类」拆分互不相关的职责。
- 当产品行为、展示行为、持久化行为和集成行为各自独立演进时，SHOULD 把它们分开。
- 只有当共享行为确实真实存在时，SHOULD 才使用提炼超类或提炼子类。

### 霰弹式修改（Shotgun Surgery）

- 触发条件：一次概念性的改动迫使你在许多类中做许多小编辑。
- SHOULD 把这份散落的职责集中起来。
- SHOULD 把方法和字段搬移到那个正在变化的概念的归属方。
- SHOULD 通过内联或提炼类，把相关的改动放到同一处。
- 一旦这种模式已经显现，MUST NOT 让知识继续散落各处。

### 平行继承体系（Parallel Inheritance Hierarchies）

- 触发条件：在一个继承体系中新增子类，就要求在另一个体系中新增一个对应的子类。
- SHOULD 通过搬移方法和字段，让一个继承体系拥有这份变化，从而消解重复的体系压力。
- 当平行结构只是为了彼此镜像而存在时，SHOULD 折叠或替换它们。
- 在做扩展工作时，MUST 避免造出新的平行继承体系。

## 可去除者

### 注释（Comments）

- 触发条件：注释在解释含义不清的代码做了什么，而不是解释它为何存在。
- SHOULD 用更好的命名、提取出的变量、提取出的方法或断言，来替换解释性的注释。
- SHOULD 保留那些说明理由、非显而易见的约束、外部契约，以及已经抵抗住简化的算法的注释。
- MUST NOT 把注释当作掩盖混乱结构的除臭剂。

### 重复代码（Duplicate Code）

- 触发条件：两个片段完全相同，或以略有差异的措辞做着同样的工作。
- 对同一个类中的重复，SHOULD 使用「提炼函数」。
- 对兄弟类之间的重复，SHOULD 使用上移或提炼超类的手法。
- 当重复的行为属于一个独立概念时，SHOULD 使用「提炼类」。
- 即使两个片段在文本上并不完全相同，SHOULD 也要消除偶然形成的重复。
- 当合并会让代码更不直观、或造出错误的抽象时，MAY 保留这份重复。
- MUST NOT 合并那些只是偶然相似、且很可能因不同原因而分化的重复代码。

### 冗赘的类（Lazy Class）

- 触发条件：一个类做的事已不足以证明其维护成本的合理性。
- SHOULD 内联掉一个几乎无用的类。
- 当子类或超类已不再承载各自独特的行为时，SHOULD 折叠这个继承体系。
- 当一个小类清楚地传达了一个有意设定的扩展点、并因此赚回了这份清晰度时，MAY 保留它。

### 纯数据类（Data Class）

- 触发条件：一个类只存储数据、只暴露粗糙的 getter 或 setter，而行为由客户端来执行。
- SHOULD 封装公开字段。
- SHOULD 封装集合，而不是暴露可变的集合内部结构。
- 当客户端的行为正是在操作这些数据时，SHOULD 把该行为搬移到这个数据类上。
- 在有意义的行为已经存在之后，SHOULD 移除那些宽泛的 setter 或访问器。

### 死代码（Dead Code）

- 触发条件：未被使用的变量、参数、字段、方法、类、文件，或不可达的分支。
- SHOULD 借助 IDE 和编译器的反馈来发现死代码。
- 当不再有任何兼容性理由时，MUST 删除未被使用的代码和文件。
- 在删除之前，必要时 SHOULD 先内联或折叠空的类或继承体系。
- SHOULD 从方法中移除未被使用的参数。
- MUST NOT 在未检查外部兼容性的情况下删除公开的、被序列化的、被反射调用的或面向插件的代码。

### 推测性通用化（Speculative Generality）

- 触发条件：某些抽象、参数、钩子、字段或类，只为想象中的未来需求而存在。
- SHOULD 内联掉未被使用的抽象。
- SHOULD 移除未被使用的参数、方法、字段和类。
- SHOULD 折叠未被使用的继承体系。
- 只有当真实用户确实需要时，MAY 保留框架的扩展点。
- 在删除某个仅为测试访问而存在的成员之前，MUST 先检查测试代码。

## 耦合者

### 依恋情结（Feature Envy）

- 触发条件：一个方法使用另一个对象的数据多于使用自己的数据。
- SHOULD 把该行为搬移到拥有其主要使用数据的那个类。
- 当只有方法的一部分在依恋另一个对象时，SHOULD 先把这个依恋片段提取出来，再搬移它。
- 当一个方法为了可分离的多个目的而使用了多个数据源时，SHOULD 把它按归属拆分开。
- 当这种分离是有意为之时（例如可互换的、类策略式的行为），MAY 让行为保持分离。

### 过度亲密（Inappropriate Intimacy）

- 触发条件：类之间依赖彼此的内部结构，或往来过于频繁。
- SHOULD 搬移方法和字段，以减少跨边界的私有知识传递。
- SHOULD 提取或隐藏受托者，以减少对协作者结构的不必要了解。
- 当这种亲密源于一段过度暴露的子类关系时，SHOULD 用委托取代继承。

### 过长的消息链（Message Chains）

- 触发条件：客户端代码要穿过一条对象链才能拿到数据或行为。
- SHOULD 把受托者隐藏在客户端已经认识的那个对象背后。
- SHOULD 把行为搬到更靠近数据的地方，而不是让客户端去遍历结构。
- MUST NOT 把对象图的拓扑结构当作一种常规的调用约定暴露出去。

### 中间人（Middle Man）

- 触发条件：一个类大部分工作只是转发调用，并未增加任何策略、协调或保护。
- 当直接协作更清晰时，SHOULD 移除这个中间人。
- SHOULD 内联掉那种只作为纯转发而存在的类。
- 当某个委托层保护着一条边界、隐藏了易变结构，或提供了有用的策略时，SHOULD 保留它。

### 不完美的库类（Incomplete Library Class）

- 触发条件：某个外部库类缺少你需要的方法，而你又无法直接修改它。
- 对一两个缺失的操作，SHOULD 使用外加函数（foreign method）。
- 当缺失的行为分量较重时，SHOULD 使用本地扩展（local extension）。
- MUST NOT 让针对该库的重复绕行代码散布在整个代码库中。
- 当一个窄小的外加函数就能填补缺口时，MUST NOT 大范围地 fork 或包装这个库。

## 手法选择规则

### 重新组织函数

- 当某个片段具有连贯用途或需要解释时，使用「提炼函数」。
- 当方法体比其名称更清晰、或这层间接毫无价值时，使用「内联函数」。
- 当某个表达式需要一个名字来揭示意图时，使用「提炼变量」。
- 当某个临时变量掩盖了一个简单表达式、或阻碍了另一次重构时，使用「内联临时变量」。
- 当某个临时值应当由一个具名查询重新计算得出时，使用「以查询取代临时变量」。
- 当一个变量在多次赋值中被赋予了不同含义时，使用「分解临时变量」。
- 当一个方法把参数当作局部草稿空间来复用时，使用「移除对参数的赋值」。
- 当一个方法与局部变量纠缠过深、无法干净地提取时，使用「以函数对象取代函数」。
- 当行为已受保护、且存在一个更清晰的等价算法时，使用「替换算法」。

### 在对象之间搬移特性

- 当一个方法使用另一个类多于使用当前类时，使用「搬移函数」。
- 当一个字段被另一个类或概念使用得更多时，使用「搬移字段」。
- 当一个类包含可分离的多项职责时，使用「提炼类」。
- 当一个类已不再赚回其存在的合理性时，使用「内联类」。
- 当客户端对某个对象的协作者了解过多时，使用「隐藏受托者」。
- 当委托已不再隐藏任何有用的复杂度时，使用「移除中间人」。
- 当某个库类缺少一个小的操作时，使用「引入外加函数」。
- 当某个库类需要分量较重的本地行为时，使用「引入本地扩展」。

### 重新组织数据

- 当直接访问字段妨碍了在访问过程中添加行为时，使用「自封装字段」。
- 当某个原始类型需要含义、校验或行为时，使用「以对象取代数据值」。
- 当许多相等的对象本应代表同一个可变的现实实体时，使用「将值对象改为引用对象」。
- 当生命周期管理不值得付出、而不可变的值语义正好契合时，使用「将引用对象改为值对象」。
- 当数组位置具有领域含义时，使用「以对象取代数组」。
- 当 GUI 持有的领域数据应当被拆分为领域数据并带同步逻辑时，使用「复制被监视的数据」。
- 只有当两侧确实都需要导航时，才使用「将单向关联改为双向关联」。
- 当一侧并不使用另一侧时，使用「将双向关联改为单向关联」。
- 当某个字面值承载含义时，使用「以符号常量取代魔数」。
- 当公开字段暴露了数据表示时，使用「封装字段」。
- 当调用方可以直接修改内部集合时，使用「封装集合」。
- 当某个类型码需要类型安全或行为、但不需要多态变体时，使用「以类取代类型码」。
- 当类型码驱动着稳定的变体行为时，使用「以子类取代类型码」。
- 当运行时状态或算法变化决定行为时，使用「以状态/策略取代类型码」。
- 当各子类之间只在常量数据上有差异时，使用「以字段取代子类」。

### 简化条件表达式

- 当条件或分支难以阅读时，使用「分解条件表达式」。
- 当多项检查都通向同一个动作时，使用「合并条件表达式」。
- 当所有分支都包含同样的代码时，使用「合并重复的条件片段」。
- 当某个变量只被用来跳出或引导控制流时，使用「移除控制标记」。
- 当特殊情形掩盖了常规路径时，使用「以卫语句取代嵌套条件表达式」。
- 当条件式行为随类型而变时，使用「以多态取代条件表达式」。
- 当 null 检查在行为中占据主导时，使用「引入空对象」。
- 当关于状态的隐含假设应当被显式化时，使用「引入断言」。

### 简化函数调用

- 当方法名未能揭示其行为时，使用「函数改名」。
- 只有当一个方法确实需要额外数据、且用字段来传会更糟时，才使用「添加参数」。
- 当某个参数未被使用、或已不再影响行为时，使用「移除参数」。
- 当一个方法既返回信息又改变状态时，使用「将查询函数与修改函数分离」。
- 当若干相似的方法只在取值上不同时，使用「令函数携带参数」。
- 当某个参数用于选择不同的行为时，使用「以明确函数取代参数」。
- 当调用方传入了同一个对象的多个值时，使用「保持对象完整」。
- 当某个参数可以由被调方自行获得时，使用「以函数调用取代参数」。
- 当若干参数总是一起出现时，使用「引入参数对象」。
- 当对象在创建之后或初始化之后不应再被修改时，使用「移除设值函数」。
- 当某些公开方法并不属于预期的对外接口时，使用「隐藏函数」。
- 当构造过程需要命名、选择、缓存或受控创建时，使用「以工厂函数取代构造函数」。
- 当调用方不应为了处理异常失败而手工检查状态码时，使用「以异常取代错误码」。
- 当调用方可以低成本地在调用某操作之前先检查条件时，使用「以测试取代异常」。

### 处理概括关系

- 当兄弟类之间重复了数据或行为时，使用「字段上移」或「函数上移」。
- 当子类的构造函数重复了初始化逻辑时，使用「构造函数本体上移」。
- 当超类的某个成员只被部分子类使用时，使用「字段下移」或「函数下移」。
- 当一部分实例具有独特行为时，使用「提炼子类」。
- 当若干类共享真实的行为或数据时，使用「提炼超类」。
- 当客户端只需要一个共享的行为子集时，使用「提炼接口」。
- 当子类与超类之间已不再有实质差异时，使用「折叠继承体系」。
- 当相似的算法共享结构但在若干步骤上不同时，使用「塑造模板函数」。
- 当继承造成了"被拒绝的遗赠"或过度耦合时，使用「以委托取代继承」。
- 只有当某个委托类确实是一个子类型、且委托毫无意义时，才使用「以继承取代委托」。

## 坏味道到处理手法的优先级映射

在诊断出坏味道之后使用这张映射表。先从首选手法开始，只有当首选手法走不通时才转向备选手法；把高风险选项视为需要更强测试和明确理由才能采用。

- `过长函数`：首选「提炼函数」；当局部变量阻碍提取时，备选「以查询取代临时变量」、「引入参数对象」或「保持对象完整」；高风险手法是「以函数对象取代函数」，因为它引入了一个新对象并改变了算法的形态。
- `过大的类`：首选「提炼类」；对罕见或变体行为备选「提炼子类」，对面向客户端的子集备选「提炼接口」；高风险手法是在职责尚未稳定之前就做大范围的继承体系提取。
- `基本类型偏执`：首选「以对象取代数据值」、「以符号常量取代魔数」或「以对象取代数组」；当行为随类型码而变时，备选类型码相关的重构；高风险手法是在变化点尚未稳定之前就把类型码替换为子类或状态/策略。
- `过长参数列表`：首选「以函数调用取代参数」或「保持对象完整」；备选「引入参数对象」；高风险手法是通过制造隐藏的对象依赖来移除参数。
- `数据泥团`：首选「提炼类」或「引入参数对象」；备选「保持对象完整」；高风险手法是仅为避免一个长参数列表就传入一个庞大的所有者对象。
- `switch 语句`：首选用「提炼函数」和「搬移函数」把决策逻辑隔离出来；备选类型码替换；高风险手法是在条件判断本身很简单、或并非基于稳定变化点时使用「以多态取代条件表达式」。
- `临时字段`：首选「提炼类」或「以函数对象取代函数」；对"缺失检查"备选「引入空对象」；高风险手法是让可选的半状态借更多条件判断继续扩散。
- `被拒绝的遗赠`：首选「函数下移」或「字段下移」；备选「以委托取代继承」；高风险手法是仅为了避免改动调用方而保留继承。
- `异曲同工的类`：首选「函数改名」并对齐签名；备选「提炼超类」；高风险手法是跨库或跨归属边界合并类。
- `发散式变化`：首选「提炼类」；对真实存在的共享行为备选「提炼超类」或「提炼子类」；高风险手法是用继承来回避清晰的职责拆分。
- `霰弹式修改`：首选用「搬移函数」和「搬移字段」把归属集中起来；备选「内联类」或「提炼类」；高风险手法是增加更多转发层，却并未减少编辑点。
- `平行继承体系`：首选通过搬移方法和字段来折叠镜像式的变化；备选折叠继承体系；高风险手法是不重新设计归属就继续新增下一对配套子类。
- `注释`：首选「提炼变量」、「提炼函数」或「函数改名」；对隐含的状态假设备选「引入断言」；高风险手法是在代码还没变成自解释之前就删掉注释。
- `重复代码`：首选「提炼函数」；对兄弟类之间的重复备选上移或「提炼超类」，对独立概念备选「提炼类」；高风险手法是合并偶然的相似性。
- `冗赘的类`：首选「内联类」；备选「折叠继承体系」；高风险手法是仅因为将来可能会用到就保留一个类。
- `纯数据类`：首选「封装字段」和「封装集合」；备选用「搬移函数」和「提炼函数」把行为带到数据身边；高风险手法是只做完琐碎的访问器就停手。
- `死代码`：首选在检查使用情况后删除；备选「内联类」、「折叠继承体系」或「移除参数」；高风险手法是删除外部可达的 API。
- `推测性通用化`：首选「内联函数」、「内联类」、「移除参数」和删除字段；备选「折叠继承体系」；高风险手法是不检查使用者就移除框架的扩展点。
- `依恋情结`：首选「搬移函数」；在搬移一个依恋片段之前备选先用「提炼函数」；高风险手法是搬移那些为可互换的策略式用途而有意分离的行为。
- `过度亲密`：首选「搬移函数」和「搬移字段」；备选「隐藏受托者」或「以委托取代继承」；高风险手法是通过放宽可见性来维持这种亲密。
- `过长的消息链`：首选「隐藏受托者」；备选把方法「搬移」到更靠近数据的地方；高风险手法是增加一个只做转发、并未减少知识传递的中间人。
- `中间人`：首选「移除中间人」；备选「内联类」；高风险手法是移除掉一条隐藏了易变结构或策略的边界。
- `不完美的库类`：对窄小的缺失操作首选「引入外加函数」；对反复出现且分量较重的缺失行为备选「引入本地扩展」；高风险手法是大范围包装或 fork 整个库。

## 手法操作手册

每一个具名手法都 MUST 配合症状、适用条件、回避条件、安全步骤和验证方式来使用。以下条目有意写得紧凑；它们是给智能体做决策用的，而不是教程式的散文。

### 重新组织函数操作手册

- `提炼函数`：症状：某个片段具有连贯用途、需要注释、与另一片段重复，或阻碍局部推理。适用于一个名字能比内联细节更好地解释这个片段时。当该片段隐藏着必需的副作用、或依赖过多变动中的局部状态时不要使用。安全步骤：识别输入、输出和被修改的变量，提取，按用途命名，用调用替换旧片段。验证方式：运行调用方周围的测试，并检查状态流的变化。
- `内联函数`：症状：一个方法名并未在其方法体之外增加任何清晰度。适用于这层间接让调用方更难理解时。当该方法是一个覆写点、公开契约，或是一个有用的概念名时不要使用。安全步骤：检查所有调用方，代入方法体，仅在没有任何调用方残留时移除。验证方式：检查分派/接口的使用情况，以及调用方周围的测试。
- `提炼变量`：症状：某个表达式在原地难以理解。适用于一个临时的名字能揭示意图时。当该变量只是机械地重复了这个表达式时不要使用。安全步骤：在使用处附近引入一个不可变的局部值，为该概念命名，保持求值顺序。验证方式：运行测试，并检查没有副作用被提前或推后求值。
- `内联临时变量`：症状：某个临时变量妨碍了另一次重构，或掩盖了一个简单表达式。适用于该表达式廉价且清晰时。当这个名字解释了一个非显而易见的概念、或能防止重复的副作用时不要使用。安全步骤：把引用替换为该表达式，然后删除这个临时变量。验证方式：核对求值次数和求值顺序。
- `以查询取代临时变量`：症状：某个临时值阻碍了提取，或重复了一个有意义的计算。适用于一个具名查询能在不修改状态的前提下算出同样的值时。当该计算昂贵、有状态，或依赖顺序且没有缓存策略时不要使用。安全步骤：创建查询，替换对该临时变量的读取，移除该临时变量。验证方式：核对结果等价性以及对性能敏感的路径。
- `分解临时变量`：症状：一个变量在多次赋值中承载了多种含义。适用于这些赋值代表着彼此独立的概念时。当该变量是一个有意为之的累加器时不要使用。安全步骤：为每种含义创建一个变量并更新使用处。验证方式：核对每处使用都指向预期的值。
- `移除对参数的赋值`：症状：某个参数被当作草稿状态复用。适用于这种修改掩盖了调用方意图时。当语言语义有意支持输出参数、且调用方确实依赖它时不要使用。安全步骤：引入一个局部变量，替换这些赋值，让参数保持只读。验证方式：核对调用方可见的行为。
- `以函数对象取代函数`：症状：某个方法与局部变量纠缠过深，无法提取出更小的方法。适用于一个专门的对象能持有算法状态、从而使更小的方法成为可能时。对于「提炼函数」就能应付的简单长方法不要使用。安全步骤：创建函数对象，把局部变量搬为字段，搬移算法，拆分内部步骤。验证方式：核对算法输出和副作用。
- `替换算法`：症状：某个算法令人困惑，且存在一个更清晰的等价算法。仅在行为已被良好保护之后使用。不要用它来悄悄改变语义、性能保证或边界情况行为。安全步骤：捕获当前行为，替换算法，在边界情况上比对结果。验证方式：用覆盖预期输入和边界输入的宽范围测试来验证。

### 搬移特性操作手册

- `搬移函数`：症状：某个方法使用另一个类多于使用自己所属的类。适用于该行为应当与它所修改的数据待在一起时。当这种分离是为可互换的行为而有意为之时不要使用。安全步骤：检查数据使用情况，必要时先提取出部分片段，把方法加到目标类，改道所有调用方，移除旧方法。验证方式：核对调用方和访问可见性。
- `搬移字段`：症状：某个字段被另一个类或概念使用得更多。适用于归属在别处更清晰时。当搬移会造成循环式的知识依赖、或破坏生命周期归属时不要使用。安全步骤：把字段加到目标类，迁移读写，保住初始化逻辑，删除旧字段。验证方式：核对构造、序列化、持久化和状态修改行为。
- `提炼类`：症状：一个类干了两份活。适用于一部分字段和方法构成了一项稳定的独立职责时。不要仅为缩减体积而使用。安全步骤：创建类，把数据和行为一并搬移，暂时保留委托，逐步更新客户端。验证方式：核对行为，并确认职责边界更清晰了。
- `内联类`：症状：某个类已不再赚回其维护成本。适用于其行为能自然地融入另一个类时。当它标记着一条真实的边界或扩展点时不要使用。安全步骤：把成员搬到目标类，替换引用，删除空掉的类。验证方式：核对构造过程和公开 API 的使用情况。
- `隐藏受托者`：症状：客户端在遍历协作者的结构。适用于当前对象能替客户端屏蔽这层结构时。如果这样做会造出一个不减少知识传递的纯转发层，就不要使用。安全步骤：添加带有实质策略的转发方法，更新客户端，让协作者保持私有。验证方式：确认客户端已不再知晓那条访问路径。
- `移除中间人`：症状：某个类大部分工作只是转发调用。适用于直接协作更清晰时。当中间层保护着易变性或策略时不要使用。安全步骤：把转发调用替换为直接调用，移除转发方法，然后重新评估这个类。验证方式：确认调用方仍持有恰当的依赖关系。
- `引入外加函数`：症状：某个库类缺少一个小操作。适用于那个你无法加进库里的、窄小的缺失方法。当缺失的操作很多时不要使用。安全步骤：在使用处附近创建本地辅助函数，为它取一个仿佛属于该库类型的名字，替换掉各处重复。验证方式：对照该库的边界情况核对行为。
- `引入本地扩展`：症状：某个库类反复缺少分量较重的行为。适用于一个本地的包装类/子类能减少重复的绕行代码时。仅为一个小辅助函数则不要使用。安全步骤：创建扩展类型，把重复的行为搬进去，有计划地迁移调用方。验证方式：核对与该库的构造方式及版本更新的兼容性。

### 重新组织数据操作手册

- `自封装字段`：症状：直接访问字段妨碍了受控的访问行为。适用于访问过程可能需要校验、延迟处理或被覆写时。当直接访问字段本就有意保持简单且局部时不要使用。安全步骤：添加访问方法，替换内部读写，随后让未来的访问都经由方法。验证方式：核对没有递归访问或初始化被破坏。
- `以对象取代数据值`：症状：某个原始类型承载着领域含义或校验规则。适用于行为或约束应当与该值待在一起时。对于不增加任何含义的包装则不要使用。安全步骤：创建值对象，迁移构造过程，搬移校验/行为，替换原始类型的使用处。验证方式：核对相等性判定、序列化和边界转换。
- `将值对象改为引用对象`：症状：许多相等的对象本应代表同一个可变实体。适用于共享标识和当前状态很重要时。对天然不可变的值则不要使用。安全步骤：引入工厂或仓储查找，返回规范实例，更新创建路径。验证方式：核对标识共享和"对象不存在"的处理。
- `将引用对象改为值对象`：症状：引用式的生命周期管理比该对象所应得的更沉重。适用于不可变的值语义正好契合时。当标识或共享的状态修改很重要时不要使用。安全步骤：让对象不可变，定义相等性，简化构造。验证方式：核对比较逻辑和更新流程。
- `以对象取代数组`：症状：数组下标背后藏着名称。适用于各个位置代表着不同字段时。对真正同质的序列则不要使用。安全步骤：创建带具名字段的对象，替换下标访问，必要时添加行为。验证方式：核对所有下标语义都被保住了。
- `复制被监视的数据`：症状：GUI 类持有领域数据。适用于领域状态应当存在于 UI 之外并带同步逻辑时。当只属于 UI 的状态并无领域含义时不要使用。安全步骤：创建领域对象，搬移领域数据，同步 UI/领域的更新。验证方式：核对双向更新行为。
- `将单向关联改为双向关联`：症状：两个类确实都需要导航。适用于反向查找复杂或频繁时。仅为方便则不要使用。安全步骤：选定主导的所有者，添加反向字段，把关联更新逻辑集中起来。验证方式：核对添加/移除时两侧的一致性。
- `将双向关联改为单向关联`：症状：其中一侧并不使用另一侧。用它来减少依赖和维护代码。当行为确实需要反向导航时不要使用。安全步骤：必要时把读取替换为参数传入或查找，移除更新代码，删除未被使用的字段。验证方式：核对导航相关的调用方。
- `以符号常量取代魔数`：症状：某个字面值藏着含义。适用于一个名字能解释该值时。对显而易见的局部字面值则不要使用。安全步骤：在其归属方附近引入具名常量，替换各处使用。验证方式：核对没有把无关的同值字面量一并卷入。
- `封装字段`：症状：公开字段暴露了数据表示。适用于访问过程需要受控时。如果行为本就该放进类内部，不要只做到琐碎的访问器就停手。安全步骤：添加访问器，迁移读写，把字段改为私有。验证方式：核对调用方和不变式。
- `封装集合`：症状：调用方可以直接修改内部集合。适用于所有者必须保住不变式时。不要用"暴露一个可赋值的可变集合"作为替代方案。安全步骤：返回只读视图或副本，添加 add/remove 方法，迁移调用方。验证方式：核对各条状态修改路径。
- `以类取代类型码`：症状：某个类型码需要类型安全或行为，但不需要多态变体。适用于有实质含义的类型码。对琐碎的常量则不要使用。安全步骤：为该类型码创建类，替换原始类型，把校验集中起来。验证方式：核对持久化和比较逻辑。
- `以子类取代类型码`：症状：类型码驱动着稳定的变体行为。适用于行为随类型而异、且类型在运行时不常改变时。对易变的状态则不要使用。安全步骤：创建子类，搬移变体行为，替换创建逻辑。验证方式：核对方法分派和构造过程。
- `以状态/策略取代类型码`：症状：类型或状态控制着行为，且可能在运行时改变。适用于运行时切换很重要时。当一个简单的类型码类就够用时不要使用。安全步骤：创建状态/策略对象，搬移行为，显式安排状态转换。验证方式：核对状态转换。
- `以字段取代子类`：症状：各子类之间只在常量数据上有差异。适用于该继承体系并未增加任何行为时。当子类拥有各自独立的逻辑时不要使用。安全步骤：把字段加到超类，替换子类的构造逻辑，移除空掉的子类。验证方式：核对类型检查和序列化。

### 条件表达式与函数调用操作手册

- `分解条件表达式`：症状：条件或各分支需要在脑中解析。适用于命名能澄清条件部分、then 部分和 else 部分时。如果提取会隐藏副作用就不要使用。安全步骤：把条件和各分支提取为具名方法。验证方式：核对各分支行为。
- `合并条件表达式`：症状：多项检查都通向同一个动作。适用于这些检查无副作用时。如果这些检查在时机或副作用上有差异就不要使用。安全步骤：合并表达式，提取为具名查询。验证方式：核对真值表。
- `合并重复的条件片段`：症状：所有分支都重复着同样的代码。适用于这段重复代码可以在不改变执行顺序的前提下前移或后移到条件之外时。如果分支特有的副作用会改变顺序就不要使用。安全步骤：搬移公共片段，若较长则提取出来。验证方式：核对各分支输出。
- `移除控制标记`：症状：某个标志变量只用来引导循环或分支的流程。适用于直接使用 break/return/continue 更清晰时。如果该标志代表着持久的领域状态就不要使用。安全步骤：把标志检查替换为直接的控制流。验证方式：核对循环的退出行为。
- `以卫语句取代嵌套条件表达式`：症状：特殊情形掩盖了常规路径。适用于提前返回能让常规流程显而易见时。当嵌套结构传达着必需的事务或清理范围时不要使用。安全步骤：识别特殊情形，把它们前移，把常规路径放在最后。验证方式：核对所有分支。
- `以多态取代条件表达式`：症状：行为随稳定的类型/状态而变，且条件判断反复出现。在变化点的归属已经清晰之后使用。对简单的一次性条件判断或工厂选择逻辑则不要使用。安全步骤：创建类型/状态结构，搬移变体行为，替换条件式分派。验证方式：核对每一个变体。
- `引入空对象`：症状：null 检查在行为中占据主导。适用于一个中性对象能遵循同一套接口时。当"缺失"本身是一种应当显式化的错误时不要使用。安全步骤：创建空对象，替换 null 分支，保住可观察的"缺失"行为。验证方式：核对"缺失"与"存在"两种情形。
- `引入断言`：症状：代码依赖着关于状态的隐含假设。用它把不变式显式化。对常规校验或可恢复的用户错误则不要使用。安全步骤：在该假设的边界处添加断言。验证方式：核对当不变式被违反时测试会清晰地失败。
- `函数改名`：症状：某个方法名掩盖了意图。适用于调用方应当无需阅读方法体就能理解其行为时。如果这次重命名的扰动与本次改动无关就不要使用。安全步骤：原子性地重命名定义和所有调用方。验证方式：核对引用和公开兼容性。
- `添加参数`：症状：某个方法缺少完成其工作所需的数据。适用于偶尔传入数据比把它存起来更好时。如果该方法本应自己拥有或推导出这份数据就不要使用。安全步骤：添加兼容的签名，迁移调用方，在安全时移除旧签名。验证方式：核对调用方。
- `移除参数`：症状：某个参数已不再影响行为。在确认它未被使用之后使用。如果该参数属于公开兼容性的一部分就不要使用。安全步骤：移除各处使用，迁移签名，必要时保留一条兼容路径。验证方式：核对调用方。
- `将查询函数与修改函数分离`：症状：某个方法既返回数据又修改状态。适用于调用方需要清晰的意图时。如果原子的"读-改"行为本身就是公开契约就不要使用。安全步骤：把查询与命令拆开，更新调用方。验证方式：核对状态变更和返回值。
- `令函数携带参数`：症状：若干相似方法只在取值上不同。适用于"一个带参数的方法"仍能保持意图清晰时。当该参数用于选择不同的行为时不要使用。安全步骤：创建带参数的方法，把旧方法改道过去，在安全时移除重复。验证方式：核对所有取值情形。
- `以明确函数取代参数`：症状：某个参数用于选择不同的行为。适用于分开命名比用标志或模式更清晰时。对普通数据则不要使用。安全步骤：创建明确的方法，把调用方改道，移除选择器参数。验证方式：核对每一种行为。
- `保持对象完整`：症状：调用方传入了同一个对象的多个值。适用于被调方天然依赖整个概念时。如果这样会造成一个过大的依赖就不要使用。安全步骤：把签名改为接收对象，更新字段读取，迁移调用方。验证方式：核对依赖方向。
- `以函数调用取代参数`：症状：调用方传入了被调方自己就能获得的数据。用它来减少调用方的冗余工作。如果这样会隐藏一个昂贵或令人意外的依赖就不要使用。安全步骤：把查找逻辑挪到被调方，移除参数，更新调用方。验证方式：核对查找行为。

### 概括关系操作手册

- `字段上移`、`函数上移`、`构造函数本体上移`：症状：兄弟类之间重复了成员或初始化逻辑。适用于超类能如实地拥有这份共享部分时。当重复是偶然的、或这些变体后续会分化时不要使用。安全步骤：把共享成员上移，更新各子类，移除重复。验证方式：核对所有子类。
- `字段下移`、`函数下移`：症状：超类的某个成员只被部分子类使用。适用于超类的契约过于宽泛时。如果调用方依赖该超类成员就不要使用。安全步骤：把成员下移，更新引用，收窄契约。验证方式：核对受影响的子类型调用方。
- `提炼子类`：症状：只有部分实例需要特殊行为。适用于这种变化稳定且有实质意义时。对临时性的标志或推测出来的类别则不要使用。安全步骤：创建子类，搬移变体行为，更新构造逻辑。验证方式：核对基类行为与变体行为。
- `提炼超类`：症状：若干类共享真实的行为或数据。适用于一个共同的归属方能简化重复时。对偶然相同的方法名则不要使用。安全步骤：创建超类，上移共享成员，更新继承关系。验证方式：核对所有子类。
- `提炼接口`：症状：客户端只使用一个共同的子集。适用于该子集是一份真实的客户端契约时。不要把它当成一种泛化抽象的习惯动作。安全步骤：定义接口，让客户端依赖该接口类型，让实现类保持诚实。验证方式：核对客户端的编译与行为。
- `折叠继承体系`：症状：子类与超类实际上完全相同。适用于该继承体系并未带来任何区分时。如果剩下的子类会破坏可替换性就不要使用。安全步骤：选定保留下来的类型，搬移成员，替换引用，删除空掉的类型。验证方式：核对类型方面的预期。
- `塑造模板函数`：症状：相似的算法共享结构但在若干步骤上不同。适用于骨架和步骤都稳定时。当这些算法只是表面相似时不要使用。安全步骤：对齐方法名，把骨架上移，把变体步骤下推。验证方式：核对所有算法。
- `以委托取代继承`：症状：继承造成了"被拒绝的遗赠"或过度耦合。适用于该对象是"使用"另一个对象、而非"就是"那个对象时。如果子类型替换是核心需求就不要使用。安全步骤：添加受托对象，转发所需行为，替换继承而来的访问。验证方式：核对公开行为。
- `以继承取代委托`：症状：某个类几乎把一切都委托给了一个它确实"就是"的对象。仅在子类型关系诚实成立的少数情况下使用。如果继承会带来用不上的行为就不要使用。安全步骤：改为继承，移除多余的委托，更新构造逻辑。验证方式：核对可替换性。

## 决策反模式

- MUST NOT 因为某个重构手法的名字听起来时髦就采用它；采用它是因为它能处理一个已被诊断出的坏味道。
- 除非变化稳定、反复出现，且由类型/状态拥有，MUST NOT 把一个简单条件判断改造成多态。
- MUST NOT 仅为缩短签名，就把互不相关的参数攒成一个参数对象。
- 在没有真实客户端或真实共享行为的情况下，MUST NOT 基于偶然相同的方法名引入超类或接口。
- MUST NOT 用一个名字比重复代码还糟的抽象来替换重复。
- 当真正的坏味道是"行为跑到了数据之外"时，MUST NOT 只做完 getter 和 setter 就停手。
- MUST NOT 把功能开发藏在一段重构序列里。
- MUST NOT 仅因为删掉某个转发类需要更新调用方就保留它。
- 当一侧可以通过参数或查找获得协作者时，MUST NOT 把双向关联当作方便的捷径来用。
- 在检查生成代码、反射、序列化、面向插件和公开的使用情况之前，MUST NOT 删除看起来像推测性代码或死代码的东西。
- MUST NOT 为常规用户输入、预期中的"缺失"或可恢复的错误添加断言。
- 当调用方可以低成本地先检查条件时，MUST NOT 把异常当作常规的判断手段。
- 即使方法体很短，MUST NOT 内联掉那些解释业务意图的名称。
- 如果把行为从其数据身边挪走会在相反方向造成依恋情结，MUST NOT 这样做。
- 在所诊断的坏味道被修好之后，除非下一个坏味道阻碍所要求的改动，MUST NOT 继续清理。

## 手法执行安全

### 提取的安全要点

- 在「提炼函数」之前，MUST 识别出该片段读取、写入或返回的每一个变量。
- 当某些变量仅在该片段内部声明和使用时，SHOULD 让它们保持为提取出的方法的局部变量。
- 只有当被提取的片段确实需要时，SHOULD 才把先前的值作为参数传入。
- 对该片段内部被修改的任何变量，MUST 再三核对；如果后续代码需要这个被改动的值，就显式地把它返回出来，或改选一个更安全的重构手法。
- 当临时变量阻碍形成一条干净的方法边界时，SHOULD 在提取之前先使用「以查询取代临时变量」。
- MUST 按提取出的方法的用途为其命名，而不是按它执行的机械步骤命名。
- MUST NOT 提取出一个"用听起来无害的名字掩盖了重要副作用"的片段。

### 内联的安全要点

- 在「内联函数」之前，MUST 确认该方法并未提供任何有用的名称、抽象、覆写点或公开契约。
- SHOULD 在检查过所有调用方之后再内联，尤其是可能涉及动态分派、继承或接口调用时。
- 如果调用方把某个方法当作公开 API 或面向测试的 API 的一部分来依赖，MUST NOT 内联它。
- 在「内联类」之前，MUST 把所有有用的行为和数据搬到目标类，并更新所有引用。
- 只有当引用、构造点、测试和文档都不再需要它时，MUST 才删除被清空的类。

### 搬移的安全要点

- 在「搬移函数」之前，MUST 查明该方法所使用的大部分数据由哪个类拥有。
- 当只有方法的一部分应当挪到别处时，SHOULD 先把这个片段提取出来。
- MUST 更新所有调用方，并有意识地保住可见性；不要仅为让搬移能编译通过就放宽访问权限。
- 在「搬移字段」之前，MUST 以小步序列的方式，通过访问器或直接替换来迁移读写。
- 如果这种分离是有意为之、且支持可互换的行为，MUST NOT 把行为从其数据身边挪走。

### 封装的安全要点

- 在「封装字段」之前，SHOULD 添加访问方法，迁移所有直接的读取方和写入方，然后把字段改为私有。
- 封装之后，SHOULD 复查访问器的调用方；相关行为可能本应放在所属类内部，而不是外部。
- 在「封装集合」之前，MUST 阻止调用方直接修改内部集合。
- SHOULD 暴露那些能保住不变式的 add/remove 操作，而不是暴露一个可赋值的集合。
- 如果琐碎的 getter 和 setter 只是把公开数据换了个名字继续暴露，MUST NOT 把它们当作最终设计。

### 条件表达式的安全要点

- 在「合并条件表达式」之前，MUST 核实这些条件无副作用。
- 当表达式复杂时，SHOULD 把合并后的条件提取为一个具名查询。
- 在「合并重复的条件片段」之前，只有当这样做能保住执行顺序时，SHOULD 才把重复代码移到条件之前或之后。
- 在「以卫语句取代嵌套条件表达式」之前，MUST 识别出常规路径并保住特殊情形的行为。
- 在「以多态取代条件表达式」之前，MUST 确认该条件判断确实随稳定的类型、状态或策略而变；否则优先使用明确的方法或更简单的条件判断。
- 对于一个在原地更易阅读的简单条件判断，MUST NOT 为它引入多态。

### 函数调用的安全要点

- 在「添加参数」之前，MUST 检查该方法是否应当改为把这份数据作为字段拥有，或通过既有协作者获取。
- 当调用方数量众多或属于公开范围时，SHOULD 先创建新方法或过渡路径以保住兼容性，再删除旧签名。
- 在「移除参数」之前，MUST 确认该参数未被使用、或已不再改变行为。
- 在「将查询函数与修改函数分离」之前，MUST 把状态修改与返回的信息拆开，并更新调用方，使每种意图都使用对应的方法。
- 在「以明确函数取代参数」之前，MUST 确认该参数是在选择不同的行为，而不是普通数据。
- 在「引入参数对象」之前，MUST 确认这组参数代表着一个概念，而不是一个随意的杂物袋。
- 如果某项简化会在类之间造成隐藏依赖，MUST NOT 做这项函数调用的简化。

### 数据重组的安全要点

- 在「以对象取代数据值」之前，MUST 定义该对象的含义、相等性、校验规则和允许的行为。
- 在改变值/引用语义之前，MUST 判断是否需要标识、可变性、共享和生命周期管理。
- 在把引用替换为值之前，SHOULD 先让值对象不可变。
- 在把值替换为引用时，SHOULD 使用工厂创建，使调用方拿到规范对象。
- 在改变关联方向之前，MUST 弄清哪一侧拥有更新权、以及一致性如何维护。
- 当一侧并不需要导航时，MUST 移除双向关联。
- 除非两侧确实都需要、且一致性逻辑是显式的，MUST NOT 添加双向关联。

### 概括关系的安全要点

- 在上移成员之前，MUST 确认兄弟类之间的重复是真实的，且超类的契约能如实地拥有该成员。
- 在下推成员之前，MUST 确认超类已不再承诺或需要该成员。
- 在提炼超类或接口之前，MUST 识别出真实的共享行为，或一个真实的面向客户端的子集。
- MUST NOT 仅因为两个类恰好共享方法名就提炼接口。
- 在折叠继承体系之前，MUST 检查剩下的子类在可替换性和公开类型预期方面是否成立。
- 在用委托取代继承之前，MUST 保住被委托的行为，并有意识地更新构造和转发路径。
- 除非委托类确实是一个子类型、且继承不会造成"被拒绝的遗赠"，MUST NOT 用继承取代委托。

## 安全与权衡规则

- MUST 依据坏味道来选择处理手法，而不是依据自己偏爱的模式。
- 当一次更简单的提取或重命名就能解决问题时，MUST NOT 引入多态、继承、双向关联或新类。
- 如果移除参数、关联或抽象会造成更糟的耦合、或掩盖必需的变化点，MUST NOT 这样做。
- SHOULD 优先做局部简化，再考虑改动继承体系。
- SHOULD 优先使用命名和提取出的方法，而非注释。
- SHOULD 优先删除未被使用的结构，而不是去扩展它。
- 在用对象替换原始类型或数组时，SHOULD 保住领域含义。
- 除非确实需要一个有意为之的可互换行为模型，SHOULD 让行为与它所修改的数据待在一起。
- SHOULD 把断言用于不变式，而不是用它替代常规校验或可恢复的错误处理。
- 在重构公开接口时，MUST 保住公开兼容性，或提供一条过渡路径。

## 面向智能体的重构工作流

编辑之前：

1. 明确所要求的行为变更或维护目标。
2. 用上文的目录扫描被触碰区域中的坏味道。
3. 命名主要的坏味道、它的成本，以及那个最小的有用重构手法。
4. 明确期望达到的更整洁的终态，以及停止条件。
5. 确定那些能证明行为得以保持的测试或检查手段。
6. 判断这次重构应当放在功能开发之前、之后，还是与之分离。

编辑过程中：

1. 一次只施加一个具名变换。
2. 让代码在每个有意义的步骤之后都保持可运行。
3. 先做重命名、提取、搬移、内联或封装，再引入更大的设计结构。
4. 在有风险的搬移、公开接口变更或状态流变化之后，重新运行相关测试。
5. 重新检查所选手法是否仍然是最小的处理方式。
6. 如果这次重构暴露出另一个更大的问题，就停下并上报新的范围。

编辑之后：

1. 确认行为得以保持。
2. 确认原来的坏味道已减轻或被移除。
3. 确认没有把更大范围的功能变更藏在这次重构里。
4. 确认没有引入新的坏味道，尤其是中间人、推测性通用化或过度亲密。
5. 确认任何有意未处理的坏味道都有其理由。
6. 报告所使用的重构手法、达到的停止条件，以及所做的验证。

## 评审检查清单

- 这次改动到底是重构、功能开发还是缺陷修复，这条界线是否清晰？
- 被触碰区域的代码是否变得更整洁了？
- 是否存在一个被命名的坏味道，来证明这次变换的合理性？
- 是否使用了最小的合适手法？
- 所有相关测试是否都通过了？
- 任何公开接口的变更是否都做了兼容性处理？
- 这次改动是否减少了重复、臃肿、耦合或含糊的控制流？
- 它是否避免了推测性抽象？
- 它是否避免了不必要的多态、继承或双向关联？
- 任何残留的坏味道是否被显式地推迟处理，而不是被藏起来？
