# 遵循 Refactoring.Guru

## 何时使用

作为一份紧凑、常驻生效的偏好设定，在修改既有代码时引导安全的、由坏味道驱动的重构。

## 需要纠正的首要偏见

重构不是为清理而清理：诊断出一个坏味道，用最小的保持行为不变的手法处理它，验证，然后停手。

## 决策规则

- 把结构性重构与功能、缺陷相关的行为变更分开；如果行为发生变化，明确指出并单独隔离。
- 在选择手法之前先诊断坏味道：症状、代价、最小的处理方式、验证手段和停止条件。
- 优先采用小的、有名字的变换，而不是大范围的重新设计。
- 保持程序始终可运行；在有风险的代码搬移、状态流变更、公开 API 变更或算法替换之后，运行相关检查。
- 当被诊断的坏味道已经减轻时就停手；除非新的坏味道阻碍当前改动，否则不要追着它们跑。
- 优先使用提取、命名、搬移、内联和封装，再考虑引入继承层次、多态、包装器或方法对象。
- 不要基于偶然的相似性、随意的参数包、简单的条件判断或推测性的未来需求来创建抽象。
- 让行为与它所修改的数据待在一起，除非分离是为了有意支持可互换的行为。
- 在修改签名、构造函数、可见性、继承层次或外部可达的代码时，保持公开兼容性。
- 只有在检查过公开调用、生成代码、反射、序列化、面向插件、框架和仅测试用途之后，才删除或内联可去除的代码。

## 触发规则

- 当一个方法需要注释或需要重建局部状态才能理解时，在检查清输入、输出和被修改的变量之后，提取出一个具名方法。
- 当一个类因互不相关的原因而变化时，把该职责提取出去；只在变体稳定或确实存在特定客户端子集时才使用子类/接口。
- 当条件判断按类型或状态重复出现时，先把决策逻辑隔离出来，再考虑使用多态；简单而诚实的条件判断就让它保持原样。
- 当重复代码第三次出现时进行重构，除非这些相似之处很可能后续分化。
- 当参数列表或成堆的原始类型承载着同一个概念时，把概念建模出来；不要为了掩盖依赖而传入一个巨大的对象。
- 当客户端在遍历调用链或内部结构时，隐藏受托者或搬移行为；移除那些不增加任何策略的纯转发中间人。
- 当考虑改动 null 处理、错误码、断言、值/引用语义或关联关系时，先确认语义，再改结构。

## 最终检查清单

- 坏味道是否已命名？
- 是否采用了最小的处理方式？
- 行为是否已被验证？
- 是否已达到停止条件？
- 是否没有夹带隐藏的功能变更？
- 是否没有推测性抽象？
