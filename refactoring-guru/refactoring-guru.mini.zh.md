# 遵循 Refactoring.Guru

## 何时使用

当修改既有代码，且代码坏味道、重构手法选择、行为保持和清理范围控制都很重要时使用。

## 需要纠正的首要偏见

重构不是泛泛的清理，也不是套用设计模式。它是一次小的、由坏味道驱动的、保持行为不变的针对性处理，并配有验证手段和停止条件。

## 决策规则

- 把重构与功能开发、缺陷修复分开。如果行为发生变化，就明确称之为行为变更，并把它与结构性编辑隔离开。
- 在选择手法之前先诊断坏味道：症状、维护成本、影响范围、期望达到的更整洁的终态、验证路径和停止条件。
- 优先采用能直接减轻所诊断坏味道的最小处理方式；只有当较小的手法走不通时，才升级到更大的动作。
- 通过小的、有名字的变换来保持代码可运行、可理解，而不是做大范围的重新设计。
- 在有风险的搬移、公开接口变更、状态流变更或算法替换之后，运行相关检查。
- 当被指明的坏味道已消除或明显减轻时就停手；把新发现的坏味道单独记录下来，除非它们阻碍当前改动。
- 使用"三次法则"：早期容忍尚不确定的重复，但当第三次出现类似代码时就进行重构，除非这种相似只是巧合。
- 把技术债视为会复利累积的成本；优先偿还那些正在拖慢当前变更速度、损害正确性或阻碍团队理解的债务。
- 按类别扫描坏味道：臃肿者、面向对象滥用者、变更阻碍者、可去除者、耦合者，以及第三方库能力不足带来的缺口。
- 对臃肿类坏味道，优先采用提取、参数/数据建模和职责拆分，再考虑创建方法对象、子类或接口。
- 对 switch/类型码类坏味道，先把决策逻辑隔离出来；只有当变化点稳定且反复出现时，才使用多态、子类或状态/策略模式。
- 对变更阻碍者，把行为和数据向那个正在变化的概念的归属方迁移，使一次概念性变更只对应一个主要的编辑点。
- 对可去除者，删除或内联未被使用的结构，但要先检查公开调用、生成代码、反射、序列化、面向插件和框架扩展等用途。
- 对耦合者，减少对象导航和对私有细节的了解；只有当委托层确实隐藏了易变结构、策略或一条真实边界时才保留它。
- 注释用于说明理由、约束、契约或难懂的算法；当注释是在解释含义不清的代码时，改用命名、变量、方法或断言。
- 让行为与它所修改的数据待在一起，除非分离是有意为了支持可互换的行为。
- 加上 getter 和 setter 并不意味着封装已完成；当调用方仍在直接操作暴露出来的数据时，把行为向内迁移。
- 避免推测性抽象：在没有真实概念或真实客户端的情况下，不要创建包装器、参数对象、接口、父类或继承体系的变体。
- 在修改签名、构造函数、可见性、类型层次或外部可达的 API 时，保持公开兼容性或提供一条过渡路径。
- 在做提取或搬移之前，先弄清输入、输出、被修改的变量、调用方、可见性、构造路径和不变式。
- 在合并条件判断或替换算法之前，先核实副作用、执行顺序、真值表、边界情况，以及对性能敏感的行为。
- 在重组数据之前，先决定标识、值/引用语义、可变性、相等性判定、生命周期归属、关联方向和同步策略。
- 在做通用化改动之前，先证明共享行为是真实存在的；保住可替换性，避免继承来用不上的行为。
- 有意识地留出例外：一个简单的条件判断、一条有用的注释、一处有意为之的策略分离、一个小的扩展点，或一处清晰的重复，都可能比机械地套用某个处理手法更好。

## 触发规则

- 当一个方法需要注释、需要滚屏，或需要重建局部状态才能理解时，尝试"提炼函数"；当局部变量阻碍提取时，使用"以查询取代临时变量"、"引入参数对象"或"保持对象完整"。
- 当一个类有多个变化原因时，使用"提炼类"；只有对稳定的变体或真实存在的、面向特定客户端的子集，才使用提取子类/接口。
- 当原始类型、数组、魔数或类型码承载了含义时，只有在建模能带来更好的命名、校验、行为或更安全的变化处理时才把概念建模出来。
- 当参数列表长到超出局部推理能力时，替换可推导的参数、保持对象完整，或仅在确实存在反复出现的概念时才引入参数对象。
- 当同一处变更需要跨多个文件编辑时，搬移方法/字段或提取出归属方，让这份知识集中起来。
- 当客户端代码在遍历对象链时，隐藏受托者或把行为移到更靠近数据的地方；不要添加纯转发代码。
- 当一个类大部分工作只是转发时，移除这个中间人，除非它保护着边界策略或易变结构。
- 当一个方法既查询又修改状态时，把查询与修改分离，除非原子的"读-改"行为本身就是公开契约。
- 当多个分支中出现重复行为时，先核实副作用和执行顺序，再做分解、合并或搬移重复片段。
- 当 null 检查占据主导时，只有当"缺失"能遵循同一套接口时才引入空对象；当"缺失"本身是一种错误时，让它保持显式。
- 当继承导致"被拒绝的遗赠"或过度亲密时，把成员下推，或用委托取代继承。
- 当删除死代码或推测性代码时，先核实外部可达性和仅测试用途的访问，再移除。
- 当某个库类能力不完整时，对单个窄小缺口使用外部方法（foreign method），仅对实质性且反复出现的缺口才使用本地扩展。
- 当清理工作不断扩大时，停在所诊断的那个坏味道上，把下一个坏味道单独上报。

## 最终检查清单

- 这次改动到底是重构、功能开发还是缺陷修复？
- 诊断出的是哪个坏味道，它带来了什么成本？
- 在动用更有风险的结构改动之前，是否已先用过最小的合适处理方式？
- 在相关检查下，行为是否保持不变？
- 那个被指明的坏味道是否有了实质性改善？
- 这次改动是否避免了推测性抽象和机械套用模式？
- 公开兼容性、状态流和归属关系是否都已检查？
- 那些有意未处理的坏味道，是否被记录下来而非藏起来？
