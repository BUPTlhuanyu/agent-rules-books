# 遵循《修改代码的艺术》（Michael Feathers）

## 目的

本仓库遵循 Michael Feathers 意义上的 **《修改代码的艺术》** 所主张的纪律：
通过建立理解、创建接缝和补上测试，让有风险的既有代码变得可修改。

所有代码生成、编辑和评审都必须以下列目标为优化方向：
- 在理解不足的代码中安全地做改动
- 重新设计之前先编写特征测试
- 打断那些阻碍测试的依赖
- 引入接缝
- 减少对修改的恐惧
- 渐进式改进，而非英雄式重写

本文件是一份有约束力的工程政策：`MUST`（必须）具有强制力，`SHOULD`（应当）是强默认值，`MUST NOT`（禁止）表示不得为之。

---

## 首要指令

遗留代码是指那些"安全地修改代价很高"的代码。
在实践中，默认假设是：

**如果某部分代码缺乏可信的测试，就把它当作遗留代码。**

修改遗留代码时：
1. 理解它现在做了什么
2. 在可能的情况下用测试保护这份行为
3. 找到或创建一处接缝
4. 打断那些妨碍观测或隔离的依赖
5. 做出所需的改动
6. 让这片区域比之前更可测

除非被明确要求，不要以重写作为起点。

---

## 不可协商的规则

1. **不要条件反射式地重写**
   - 优先采用有针对性的提取与改进。
   - 只有当被明确要求，或重写明显比继续修改更安全时，才重写。

2. **在重新设计之前先编写特征测试**
   - 当当前行为不确定时，把它捕获下来。
   - 用特征测试记录代码今天实际做了什么，即使这份行为很丑陋。

3. **找到或创建一处接缝**
   - 接缝是指这样一个位置：可以在不直接编辑周围代码的情况下改变其行为。
   - 用接缝来注入测试替身、隔离依赖和观测行为。

4. **有意识地打断依赖**
   - 在时间、随机数、文件、网络、进程环境、全局变量、框架和静态构造阻碍测试之处，移除对它们的直接依赖。

5. **让代码变得更可修改**
   - 理想情况下，每一次改动都应改善可测试性、可见性或模块化程度。

---

## 遗留代码改动的默认工作流

1. 确定受影响的确切区域。
2. 判断是否已有可信的测试在保护这份行为。
3. 如果没有，在可能的情况下围绕当前行为补上特征测试。
4. 找出那个让改动变困难的依赖。
5. 引入或利用一处接缝。
6. 打断阻塞的依赖。
7. 做出功能性改动。
8. 为清晰度做重构；如果那处接缝或新结构仍然值回其成本，就保留它。

简化说法：确定改动点，找到测试点，打断依赖，编写测试，做出改动，然后重构。

不要以清理整个模块作为起点。

---

## 测试策略规则

### 特征测试
1. 当你还不知道当前行为是否是有意为之时，使用特征测试。
2. 优先测试外部可见的行为。
3. 优先在你即将修改的那一小片周围建立窄粒度测试。
4. 如果真实的消费方依赖某些丑陋行为，就把它也捕获下来。
5. 一旦行为得到保护，就可以安全地改进结构。
6. 把可疑的当前行为标记出来待确认，而不是在编写特征测试的过程中悄悄"修好"它。
7. 只把感知变量或临时探针用于确认测试确实走到了目标路径；用完即移除。

### 新行为的测试
1. 为所要求的改动添加聚焦的测试。
2. 保留原有行为的测试，除非行为变更是有意为之。
3. 在有帮助时，把描述遗留行为的测试与描述新需求的测试分开。

### 可测试性改进
1. 让依赖显式化。
2. 移除硬编码的协作者。
3. 拆开那些迫使你做昂贵初始化的混杂职责。
4. 减少构造函数中的副作用和静态初始化的副作用。

## 接缝规则

### 什么算是有用的接缝
有用的接缝是指任何允许替换、观测或拦截的边界。

例如：
- 构造函数注入
- 参数注入
- 提取出的方法
- 对静态调用的包装
- 对框架对象的适配器
- 工厂带来的间接层
- 模块边界
- 在语言/构建系统支持的情况下的链接期接缝、导入接缝或预处理接缝
- 在语言约束逼迫下使用的子类接缝

### 必需行为
1. 使用那个能解锁本次改动的最小接缝。
2. 优先使用显式的接缝，而非带"魔法"的测试钩子。
3. 优先使用那些在当前任务之后依然有用的接缝。
4. 在硬依赖附近创建接缝，而不是在代码中随意创建。
5. 把"感知"与"隔离"区分开：明确这处接缝是用于观测行为、替换依赖，还是两者兼有。
6. 谨慎使用链接期接缝和预处理接缝；它们能解锁测试，但通常本身并不改善设计。

---

## 打断依赖的规则

当遗留代码难以测试时，首先寻找以下几类依赖：

### 隐藏的输入
- 当前时间
- 随机值
- 环境变量
- 线程局部状态
- 静态单例
- 全局配置
- 隐式的当前用户或当前请求

### 硬编码的输出
- 直接写文件
- 直接发起网络调用
- 进程退出
- 直接写数据库
- 直接发布消息
- 被当作控制流使用的日志

### 构造方面的问题
- 在构造函数里干真活
- 在方法内部深处 new 出复杂的协作者
- 藏在行为深处的工厂调用
- 在业务逻辑中间构建对象图

### 必需动作
- 包装静态访问和全局访问
- 注入时钟、随机数生成器、外部接口和硬编码的协作者
- 把构造与使用分开
- 把副作用提取到显式的协作者之后
- 把被测代码收窄到一个可管理的切片

## 测试点选择与理解代码的规则

1. 当一次改动的影响范围不清晰时，绘制影响草图（effect sketch）。
2. 从改动点出发，向外追踪受影响的值、调用、字段、输出和协作者。
3. 在能以有用精度观测到影响之处选择测试点。
4. 当若干计划中的改动可以被同一个更宽的测试保护时，使用拦截点。
5. 当许多影响都经由同一个窄小位置时，使用收缩点（pinch point）。
6. 把拦截点上的宽粒度测试当作走向更窄测试的第一步。
7. 可以用"草稿式重构"来理解代码，但除非后续有测试和评审支撑，否则丢弃它。
8. 在搬移行为之前，先在大段代码中勾画、标记或归拢职责。
9. 不要把仅用于学习的探索性重构提交进代码库。

## 推荐的遗留代码手法

### 萌芽方法（Sprout Method）
当新行为可以在不深入编辑脆弱代码的情况下添加时使用。

规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）：
- 把新行为提取到一个新方法中
- 让旧代码基本保持不动
- 从一个很小的插入点路由到新方法

### 萌芽类（Sprout Class）
当一项新职责不适合放进旧类中，或旧类风险太大、不宜先行重塑时使用。

规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）：
- 添加一个职责聚焦的新协作者
- 从遗留类向它委托
- 若后续证明有必要，再慢慢把行为迁移过去

### 包装方法（Wrap Method）
当你需要在某个有风险的方法前后加入行为，或需要一种更好的方式来观测其影响时使用。

### 包装类（Wrap Class）
当某个类太难直接测试，而其行为可以通过一个新抽象来中介时使用。

### 提取并覆写调用（Extract and Override Call）
仅在语言约束几乎没留下更好选择时使用。
一旦出现更干净的路径，改用组合。

## 打断依赖手法索引

- 当某个方法只需要一个难以构造的参数的窄小视图时，使用「适配参数」（Adapt Parameter）。
- 当一个大方法中的局部状态阻碍了提取和测试时，使用「分解出方法对象」（Break Out Method Object）。
- 在允许在测试代码中补全定义的语言中，当缺失的定义阻碍测试时，使用「补全定义」（Definition Completion）。
- 当全局变量或单例妨碍替换时，使用「封装全局引用」（Encapsulate Global References）。
- 当某段有用的逻辑并不需要实例状态、却被困在实例初始化之后时，使用「暴露静态方法」（Expose Static Method）。
- 当某个硬依赖的构造过程必须在测试下有所不同时，使用「提取并覆写工厂方法」（Extract and Override Factory Method）。
- 当具体依赖让编译或替换变得困难时，使用「提取实现类」或「提取接口」（Extract Implementer / Extract Interface）。
- 当静态行为需要一处实例接缝时，使用「引入实例委托」（Introduce Instance Delegator）。
- 当隐藏的协作者应当变成显式输入时，使用「参数化构造函数」或「参数化方法」（Parameterize Constructor / Parameterize Method）。
- 仅当真实类型引入测试脚手架的代价过高、且原始数据对新逻辑已足够时，才使用「原始化参数」（Primitivize Parameter）。
- 使用「上移特性」或「下推依赖」（Pull Up Feature / Push Down Dependency），把行为或依赖挪到继承层次中更可测的位置。
- 当直接的全局访问需要一处接缝时，使用「以取值函数取代全局引用」（Replace Global Reference with Getter）。
- 仅当没有更安全的组合式接缝可用时，才使用「子类化并覆写方法」（Subclass and Override Method）。
- 当测试需要替换某个保存在字段中的硬依赖时，使用「替换实例变量」（Supersede Instance Variable）。
- 仅当语言或构建方面的约束让普通对象接缝不可行时，才使用「模板重定义」、「文本重定义」、链接期接缝或预处理接缝。

## 遗留代码重构的启发式原则

1. 在改动点附近工作，不要横跨整个系统。
2. 优先做一次小的依赖打断，而不是一次大范围的重新设计。
3. 如果一个测试需要过多的初始化，那么设计正在告诉你一些有用的信息。
4. 如果代码的结果无法观测，就通过更小的单元把结果暴露出来。
5. 如果代码离开完整的运行时环境就无法被调用，就把策略与运行时隔离开。
6. 如果代码依赖大量细节，就把策略与机制分开。
7. 如果旧代码无法被安全地修改，就在它旁边插入新代码，然后逐步改道。

## 处理高风险区域

### 大方法
- 先剥离出纯计算部分
- 其次隔离副作用
- 围绕提取出来的部分补上测试
- 避免一次性修改多个分支

### 静态依赖与全局依赖
- 创建一个包装层或门面
- 把调用方迁移到这个包装层
- 在可能之处注入这个包装层
- 渐进式地减少直接调用

### 重度依赖数据库的代码
- 把查询和映射的关注点与策略分开
- 在可能的情况下，不依赖真实数据库来测试策略
- 为真实的持久化行为保留集成测试

### UI 或框架代码
- 把决策逻辑移出处理器和回调
- 独立测试被移出来的逻辑
- 让适配器保持薄

### 做得太多的构造函数
- 不要在构造函数里做 I/O、网络访问或配置查找
- 把初始化逻辑挪到工厂、构建器或组合根中
- 让构造出的对象在测试下易于实例化

## 评审规则

评审面向遗留代码的改动时，主动寻找：
- 被修改的逻辑周围没有测试
- 结构性改动与行为性改动混在一起
- 在理解不足的模块中做大范围编辑
- 隐藏的全局依赖被原封不动地留下
- 硬编码的协作者
- 直接的静态调用
- 带副作用的构造函数
- 被困在框架入口点里的业务逻辑
- 那些用萌芽方法或萌芽类就能降低风险的地方

---

## 禁用模式

### 以重写作为第一动作
- 在理解当前行为之前就替换某个子系统
- 选择重建，而不是先取得测试杠杆
- 因为代码看起来糟糕就假定旧行为无关紧要

### 无安全网的改动
- 在没有测试或观测策略的情况下修改遗留代码
- 没有特征测试就做大范围编辑
- 对有风险的行为仅依赖人工推理

### 扩大隐藏依赖
- 在已经难以测试的代码中，再增加全局变量、静态成员、隐式环境上下文或对框架的穿透访问
- 以与遗留代码相同的风格嵌入新的硬依赖

### 只做表面重构
- 只做重命名和格式调整，而把真正的依赖死结原封不动留下
- 那种并未让下一次改动更安全的"清理"

## 代码生成规则

当被要求修改遗留代码时，默认产出：
- 必要处的特征测试
- 小的接缝
- 对硬依赖的包装层
- 显式的协作者
- 提取出来的纯逻辑
- 能解锁安全改动的最小结构性编辑

推荐的首选动作：
- 提取方法
- 包装静态调用
- 注入协作者
- 把构造与行为分开
- 把逻辑移出框架入口点
- 为新行为引入一个职责聚焦的新类
- 添加一个窄粒度的特征测试

推荐避免：
- 大规模的打断依赖式重写
- 整体替换旧模块
- 在基本接缝还不存在时就引入庞大的新架构
- 围着不可测的结构堆 mock，而不去改善它

---

## 测试规则

1. 优先在你正在修改的行为周围建立快速测试。
2. 在更深入的编辑之前，用特征测试锁定当前行为。
3. 优先选择那个仍能安全隔离本次改动的最高层级来编写测试。
4. 为真实边界保留集成测试，但不要仅依赖它们。
5. 一旦接缝存在，就通过接缝来测试。

---

## 评审检查清单

在最终定稿任何改动之前，核实：
- 我们是否把未测试的代码当作有风险的遗留代码来对待？
- 在行为不明确之处，我们是否把当前行为捕获了下来？
- 我们是否创建或利用了一处接缝？
- 我们是否至少削减了一个硬依赖？
- 改动过的区域是否比之前更易测试？
- 我们是否避免了以重写作为第一动作？
- 我们是否把编辑局限在所要求的改动范围内？
- 在可行处，我们是否把结构性改动与行为性改动分开了？
- 我们留下的代码是否比发现它时更可修改？

如果任何一项答案为否，在交付前先修订。

---

## 最终指令

当不确定时，选择那个最小的改动，它能够：
1. 增进理解
2. 提升可测试性
3. 打断一个硬依赖
4. 保持当前行为不变
5. 让下一次改动更便宜

当一处接缝加一个测试就足够时，拒绝大规模重写和英雄式清理。
