# 遵循《修改代码的艺术》（Michael Feathers）

## 何时使用

在上下文预算紧张的情况下，修改测试薄弱或理解不足的代码时使用。

## 需要纠正的首要偏见

处理遗留代码的第一步是取得控制权，而不是清理、重写或追求优雅。

## 决策规则

- 把缺乏可信测试的代码视为遗留代码：明确说明哪些会变、哪些必须保持不变。
- 在修改行为不明的现有代码之前，先为其编写特征测试（characterization test），包括那些消费方可能依赖的丑陋行为。
- 使用遗留代码工作循环：找到改动点，找到观测点，创建或利用一处接缝（seam），打断阻塞的依赖，编写测试，进行修改，然后在局部重构。
- 优先使用快速、聚焦的测试；只有在找不到窄粒度测试点时，才把更宽的测试脚手架当作临时的首层覆盖。
- 为感知或隔离创建最窄的可用接缝，只打断那些阻碍获得反馈的依赖。
- 当直接修改不安全时，采用萌芽（sprout）、包装（wrap）、参数化、注入、提取或覆写等手法。
- 让行为变更、结构性重构和清理工作彼此分离且都保持小步。
- 不要在没有清理计划的情况下遗留仅供测试用的接缝、隐藏依赖、包装层、全局变量、子类技巧或链接期/预处理器技巧。

## 触发规则

- 当行为不明确时，先写特征测试。
- 当构造函数、全局变量、静态成员、框架、I/O、时钟、随机数、环境或深层对象图阻碍测试时，在最窄处打断一个依赖。
- 当一个巨型方法或类让局部推理失效时，先勾画出其影响范围并创建接缝，再做语义层面的修改。
- 当重写或大范围清理的诱惑升起时，选择下一个更小的、经过验证的动作。

## 最终检查清单

- 行为是否已被特征测试覆盖？
- 反馈是否足够快？
- 依赖是否已被隔离？
- 本次是否只做了一类改动？
- 现在是否更安全、更清晰了？
