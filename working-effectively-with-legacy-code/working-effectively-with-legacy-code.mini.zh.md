# 遵循《修改代码的艺术》（Michael Feathers）

## 何时使用

当要修改那些"安全地改动代价很高"的代码时使用——因为行为不明确、测试薄弱或缺失、依赖被隐藏，或运行时/框架的初始化阻碍了本地反馈。

## 需要纠正的首要偏见

先取得控制权，再改进设计。理解当前行为，保护必须保持不变的部分，创建最小的可用接缝，打断阻碍反馈的依赖，做出所需的改动，然后让这片区域比之前更可测。

## 决策规则

- 把任何缺乏可信测试的区域都视为遗留代码；除非明确要求或明显更安全，否则不要以重写或全模块清理作为起点。
- 在动手编辑之前，先陈述所需的行为变更，以及必须保持不变的当前行为；对不确定或可疑的行为编写特征测试，而不是悄悄把它"修好"。
- 遵循遗留代码工作循环：确定改动点，检查现有的保护，在可能处补上特征测试，找到或创建接缝，打断阻塞的依赖，改变行为，然后在局部重构。
- 优先在被改动的那一小片周围建立快速、聚焦的测试；只有当更宽的拦截式或集成测试确实是最安全的首个观测点时才使用它们。
- 通过从改动点向外追踪影响来选择测试点，沿着值、调用、字段、输出、协作者、拦截点和收缩点（pinch point）逐层追踪。
- 使用那个能实现替换、观测或拦截的最小接缝；明确说明这个接缝是用于感知、用于隔离，还是两者兼有。
- 有意识地打断依赖：只在隐藏的输入、硬编码的输出、硬编码的构造、全局变量、静态成员、隐式环境上下文和框架回调确实阻碍了测试或安全改动的地方，才把它们暴露出来。
- 让行为变更、结构性重构和清理彼此分离；验证每一个小步，并避免把仅用于理解代码的探索性重构提交进去。
- 当直接编辑有风险时，用萌芽方法、萌芽类、包装方法、包装类，或"提取并覆写"这类手法来添加行为，待测试足以支撑时，再把这些临时结构收拢成更好的设计。
- 对难以测试的方法：把构造与使用分开，把副作用提取到协作者之后，先剥离出纯计算部分，并把策略与运行时、持久化、UI 或框架机制隔离开。
- 按实际存在的障碍选择打断依赖的手法：适配窄参数、提取接口或提取实现类、参数化构造函数或方法、封装全局引用、引入实例委托、覆写工厂方法或覆写调用；只有当普通的对象接缝不可行时，才使用链接期或预处理接缝。
- 在大段代码中，先勾画影响范围并归拢职责，再搬移行为；把过多的初始化、无法观测的结果和反复出现的改动，当作应当提取出更小职责的信号。
- 评审时，把以下情形都视为遗留代码改动风险：被修改的逻辑周围没有测试、结构性与行为性编辑混杂、在理解不足的模块中做大范围编辑、硬编码的协作者、对全局/静态状态的穿透访问、构造函数中的副作用，以及被困在框架入口点里的业务逻辑。
- 拒绝这类改动：扩大了隐藏依赖；围着不可测的结构堆 mock 却不改善它；只做重命名或格式调整而把真正的依赖死结原封不动留下；在基本的接缝还不存在时就引入大型架构。
- 让改动过的区域更易理解、更易测试或更易修改；不要把仅供测试的接缝、包装层、子类技巧或构建技巧本身误当作设计改进。

## 触发规则

- 当行为不确定、消费方可能依赖某些丑陋行为，或某个分支/路径难以验证时，先补上特征测试或另一条显式的观测路径，再改变语义。
- 当测试需要过多初始化，或某个类无法低成本地实例化时，打断第一个真实的障碍：构造函数中的工作、隐藏的对象分配、工厂调用、全局状态、静态构造、框架对象或硬编码的参数。
- 当时间、随机数、环境、线程局部状态、当前用户/请求、文件、网络、进程退出、数据库写入、消息或控制流日志阻碍了可重复的测试时，包装或注入那个边界。
- 当一个巨型方法或类让局部推理失效时，勾画影响范围，找到拦截点或收缩点，先提取出纯计算部分，并避免一次性修改多个分支。
- 当修改重度依赖数据库的代码、UI、框架或 API 边界代码时，把策略与查询/映射/持久化、处理器/回调、适配器和运行时初始化分开；在真正重要的地方保留针对真实边界的集成测试。
- 当某个接缝带有"魔法"、属临时性质、为测试而设为 public、只能靠子类生效、基于链接期/预处理器，或基于探针/感知变量时，为它记下一项清理义务，并在更安全的结构出现后移除它。
- 当反复出现的编辑聚集在若干处时，在测试保护下渐进式地消除重复，而不是启动一次大范围的重新设计。
- 当重写或英雄式清理的诱惑升起时，选择那个能让今天这次改动更安全的最小动作：萌芽、包装、接缝、特征测试或一步重构。

## 最终检查清单

- 是否把未测试或测试薄弱的区域视为遗留风险？
- 行为变更量与必须保持的行为是否都已陈述？
- 不确定的当前行为是否已被特征测试覆盖或显式观测？
- 测试是否足够贴近、足够快，以便诊断这次改动？
- 是否选择了最小的可用接缝，并明确了它是用于感知还是隔离？
- 阻塞性依赖是否在不扩大隐藏依赖的前提下被削减？
- 行为变更、重构和清理是否保持分离？
- 临时接缝或打断依赖的技巧是否有清理路径？
- 改动过的区域是否更易理解、更易测试或更易修改？
