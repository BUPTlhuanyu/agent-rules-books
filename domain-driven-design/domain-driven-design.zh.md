# 遵循《领域驱动设计》（Eric Evans）

## 目的

本仓库遵循 **领域驱动设计**。
所有代码生成、修改和评审都必须以下列目标为优化方向：
- 一个精确的领域模型
- 一套共享的通用语言
- 显式的限界上下文
- 在复杂度存在之处拥有丰富的领域行为
- 有纪律的聚合设计
- 对不变式的保护
- 领域模型与支撑性基础设施之间清晰的分离

本文件是一份有约束力的工程政策：`MUST`（必须）具有强制力，`SHOULD`（应当）是强默认值，`MUST NOT`（禁止）表示不得为之。

---

## 首要指令

当不确定时，优先选择那个能让 **领域模型更清晰** 的方案。

不要主要为以下目标做优化：
- 更少的文件
- 泛化的复用
- CRUD 的便利性
- 对象-关系映射的便利性
- 交付层的便利性
- 框架的约定
- 以牺牲模型清晰度为代价换取短期速度

模型必须首先服务于业务含义。

---

## 在本仓库中 DDD 意味着什么

这里的 DDD **不** 意味着：
- 为了仪式感而增加分层
- 把服务类改名以显得高级
- 用冗长的抽象包裹 CRUD
- 创建只有字段和 setter 的实体
- 把每个概念都变成聚合
- 到处引入每一个 DDD 模式
- 对简单的子域过度设计

这里的 DDD **确实** 意味着：
- 围绕业务概念构建代码
- 用领域语言表达规则
- 让上下文边界显式化
- 用模型保护不变式
- 有意识地为标识、值、生命周期和一致性建模
- 在跨上下文边界处做显式转换
- 在核心域之外积极地做简化

## 知识消化与深层模型

### 规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）
1. 把模型当作被发现出来的东西，而不是从技术结构中臆造出来的。
2. 在添加抽象之前，先弄清领域专家会如何称呼这个概念。
3. 当需求含糊时，去寻找缺失的领域区分，而不是硬套一个泛化的名字。
4. 让别扭的代码、自相矛盾的措辞和重复的条件判断成为深入建模的触发信号。
5. 当出现新的领域洞见时，更新名称与边界。

### 必需行为（MUST）
- 追问代码正在表达的是哪条业务规则、策略、生命周期或不变式。
- 优先选择能澄清行为的深层模型，而不是只会存数据的浅层模型。
- 把新发现的概念落实到名称、测试、API 和模块中。
- 把重构视为模型发现的一部分，而不只是代码清理。

### 反模式（MUST NOT）
- 从数据库表出发，然后把结果称为领域模型
- 在已经发现更精准的领域用语之后仍保留含糊的名称
- 把领域复杂度藏进 `type`、`status` 或 `metadata` 字段里
- 把第一版模型当成最终版

---

## 模型驱动设计

### 规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）
1. 落地实现的设计必须反映讨论中所使用的那个模型。
2. 如果模型无法指导代码，就打磨模型或代码，直到二者一致。
3. 领域对象必须表达行为与含义，而不只是持久化状态。
4. 让建模者贴近实现。不要把分析与编码割裂到让模型变得空洞理论化的程度。

### 必需行为（MUST）
- 让重要的模型概念在类、函数、模块、测试和接口中显式可见。
- 优先使用可执行的示例与测试，而非与代码脱节的文档。
- 让图与文档保持轻量、及时更新，并与代码绑定。
- 解释性模型只用于教学或推理；除非它们本就用于驱动代码，否则不要把它与实现模型混为一谈。

### 反模式（MUST NOT）
- 设计文档使用与代码不同的名称
- 分析人员产出开发人员无法或不会实现的模型
- 代码只遵循框架约定而忽视领域模型
- 在代码和领域认知都已变化之后，图仍被当作权威

---

## 突破与更深的洞见

### 规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）
1. 要预期有用的模型会在获得更深洞见后发生变化。
2. 把突破性的模型当作一次有意为之的重构候选，而不是无谓的折腾。
3. 当更好的模型出现时，把它的解释力与迁移成本作比较。
4. 在以安全的小步走向更深模型的过程中，保持既有行为不被破坏。

### 必需行为（MUST）
- 寻找那种能一次性简化众多特例的概念。
- 优先选择让未来的业务规则更易表达的改动。
- 把别扭感、矛盾和反复失败的尝试当作模型过浅的信号。
- 当模型变得过于繁复时，回到基本要素上来。

### 反模式（MUST NOT）
- 仅因为当前模型还能跑就拒绝更好的模型
- 在可以增量迁移时却做大爆炸式重写
- 无助于提升领域洞见的繁复抽象

---

## 让隐式概念显式化

### 规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）
1. 留意那些尚未在代码中得到表达的领域用语。
2. 审视别扭的 API、重复的分支和自相矛盾的名称。
3. 在条件允许时阅读领域参考资料、政策、法规和已有成果。
4. 对复杂概念，先尝试多种模型形态，再决定采用其中一种。

### 必需行为（MUST）
- 把隐藏的约束、策略和流程提升为显式的领域概念。
- 先给概念命名，再选择实现形式。
- 当行为具有业务含义时，优先用清晰的领域对象而非匿名辅助函数。

### 反模式（MUST NOT）
- 把业务规则埋在注释里
- 把矛盾当成边缘情况，而不是当成建模信号
- 在已发现真实概念之后仍保留含糊的技术标志位

---

## 通用语言

### 规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）
1. 在一个限界上下文内部，使用领域专家实际使用的确切业务术语。
2. 在一个限界上下文内部，一个概念必须只有一个名字。
3. 在一个限界上下文内部，一个名字不得表示不同的概念。
4. 方法名、测试名和模块名必须使用与领域相同的词汇。
5. 当领域认知提升时，重命名代码。

### 必需行为（MUST）
- 优先使用当前限界上下文中的名称；在一个航运模型中，`Cargo`（货物）、`Itinerary`（航程）、`Handling Event`（装卸事件）、`Route Specification`（路线规格）这类术语应当直接出现。
- 优先使用表达领域动作的操作名，例如变更货物目的地、添加装卸事件、检查舱位分配、应用超售策略。
- 当存在精确的领域术语时，避免使用技术性占位名称。
- 避免不加转换就从另一个限界上下文引入名称。

### 反模式（MUST NOT）
- 在业务已有精确名称的地方使用技术名称
- 在同一上下文中对同一概念使用同义词
- 因为方便就把同一术语复用于不同含义
- 因为数据库里已经这么叫就保留糟糕的名称

---

## 沟通产出物

### 规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）
1. 文档与图必须支撑通用语言。
2. 书面设计材料必须足够简短，以便能持续被维护。
3. 对于可验证的规则，优先采用可执行的测试。
4. 图应当强调边界、关系、不变式和生命周期，而不是罗列类清单。

### 必需行为（MUST）
- 把示例和场景测试作为活文档。
- 让类似术语表的说明贴近它所描述的限界上下文。
- 当术语或上下文边界变化时更新文档。

### 反模式（MUST NOT）
- 冗长的设计文档，逐渐与代码脱节
- 展示了每一个类却掩盖了模型含义的图
- 引入了代码和测试都不使用的词汇的文档

---

## 场景走查

### 规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）
1. 通过走查真实的应用场景来验证模型。
2. 用场景检验实体、值对象、聚合、仓储和工厂是否能自然地协作。
3. 当某个场景显得过程化或别扭时，去寻找缺失的模型概念或错误的边界。
4. 当场景走查暴露出压力点后，重新审视聚合与模块的边界。

### 必需行为（MUST）
- 优先选择能演练真实业务决策的示例，而不只是 CRUD 路径。
- 用场景验证对象创建、生命周期迁移和跨上下文转换。
- 让性能调优跟在模型清晰之后；不要为了优化而过早扭曲模型。

### 反模式（MUST NOT）
- 只孤立地设计模型元素
- 把场景代码当作基础设施完工后的补充事项
- 在模型还没正确表达业务之前就优化持久化路径

---

## 分层架构与智能 UI

### 规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）
1. 让领域层始终是模型和业务规则所在之处。
2. 当领域复杂到需要模型驱动设计时，把表现、应用协调、领域行为和基础设施分离开。
3. 让应用层代码只协调任务，而不拥有领域决策。
4. 把基础设施服务与框架关注点放在领域对象之外。
5. 只在那些不看重丰富领域抽象、复用、集成和深层业务规则的简单应用中使用智能 UI。

### 反模式（MUST NOT）
- 由 UI 界面、数据库表或框架注解来定义领域词汇
- UI、应用协调、定时任务或脚本承载领域规则，而领域对象保持被动
- 在业务行为需要复用或抽象时却选择智能 UI

---

## 限界上下文

### 规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）
1. 每一个实质性的领域区域都必须归属于一个被明确识别的限界上下文。
2. 一个模型只在它自己的限界上下文内部有效。
3. 来自其他上下文的概念不得像本地概念一样被直接引入。
4. 跨上下文的转换必须是显式的。
5. 禁止跨多个上下文共享模型，除非有意作为共享内核加以治理。

### 必需行为（MUST）
- 让包、模块或命名空间的归属显式化。
- 如果含义不同，就在不同上下文中分别对 `Customer` 建模。
- 优先使用上下文专属的契约、ID、公开语言或防腐层，而不是共享类。

### 反模式（MUST NOT）
- 一个覆盖全公司的巨型领域模型
- 一个抹平了边界的 `shared/domain` 包
- 不加转换就把外部术语抄进本地模型
- 在互不相关的上下文之间复用同一个聚合类型

---

## 战略设计

### 核心域
1. 把最多的心力投入到核心域上。
2. 保护核心域，使其免受外部模型、厂商 schema 和泛化抽象的侵扰。
3. 即便支撑性区域更简单，也要让核心域保持富有表达力。

### 支撑子域与通用子域
1. 不要对通用商品化的关注点过度建模。
2. 在业务复杂度低的地方使用更简单的模型。
3. 把最丰富的建模投入留给在战略上真正重要的部分。

### 上下文映射
1. 集成关系必须在代码中可见。
2. 转换的归属责任必须显式。
3. 上游与下游的影响必须体现在适配器和契约中。

### 反模式（MUST NOT）
- 在管道代码上花的设计精力多于核心域
- 把认证工具类建模得比定价引擎还丰富
- 允许遗留系统的词汇主导核心模型

---

## 模型完整性模式

### 上下文内的持续集成
1. 一个限界上下文必须维持一个内部一致的模型。
2. 在同一上下文中工作的成员必须持续集成术语与模型变更。
3. 一个上下文内部含义冲突的情况必须通过命名、测试和重构尽快解决。

### 上下文关系
有意识地使用上下文关系模式：
- `Shared Kernel`（共享内核）仅用于一小块共同治理的模型子集。
- `Customer/Supplier`（客户/供应商）用于上游团队承诺满足下游需求的情形。
- `Conformist`（追随者）仅在采纳上游模型比转换它更省成本时使用。
- `Anticorruption Layer`（防腐层）用于保护本地模型免受外部或遗留模型侵蚀。
- `Separate Ways`（各行其道）用于集成成本高于共享能力价值的情形。
- `Open Host Service`（开放主机服务）用于某上下文对外暴露稳定集成协议时。
- `Published Language`（公开语言）用于上下文之间需要一套有文档的交换语言时。

### 上下文关系的演化
1. 只有当重叠部分很小、很有价值且值得协调时，才从各行其道转向共享内核。
2. 只有当团队已准备好频繁共享同一个模型时，才从共享内核转向持续集成。
3. 通过保护新模型、并借助转换层增量地替换职责，来逐步淘汰遗留系统。
4. 当交换的稳定性需求超出单个服务范围时，把开放主机服务演进为公开语言。

### 必需行为（MUST）
- 让上下文映射在包结构、集成适配器、文档或测试中可见。
- 当有助于清晰表达时，用适配器所实现的关系来给它命名。
- 除非有意作为追随者接受，否则把外部模型术语挡在本地核心之外。

### 反模式（MUST NOT）
- 没有归属规则的、无意间形成的共享内核
- 把每个集成都叫做防腐层，却并不做任何转换
- 让上游 API 悄悄定义了下游的领域语言
- 把上下文映射仅当作架构文档，而不落到代码结构上

## 精炼

### 核心域
1. 识别出模型中创造战略优势的那一部分。
2. 把最强的建模投入和最干净的设计放进那个核心。
3. 不要让核心被通用机制、基础设施或大范围共享抽象所掩埋。

### 精炼模式
当这些模式有助于澄清优先级和投入时使用它们：
- `Domain Vision Statement`（领域愿景说明）用一段简短陈述说明核心模型的目的。
- `Highlighted Core`（突出核心）在较大的模型中标出最重要的元素。
- `Generic Subdomain`（通用子域）用于不值得丰富定制建模的商品化能力。
- `Cohesive Mechanism`（内聚机制）用于可从领域策略中分离出来的技术机制。
- `Segregated Core`（分离核心）用于核心与支撑性关注点纠缠在一起时。
- `Abstract Core`（抽象核心）用于相关的专门化模型需要一个稳定概念基础时。

### 必需行为（MUST）
- 让核心域在代码中容易被找到。
- 除非支撑子域和通用子域的复杂度是真实存在的，否则让它们保持更简单。
- 依据战略重要性来选择重构目标，而不只是看局部有多乱。

### 反模式（MUST NOT）
- 对每个子系统投入同等的建模精力
- 让技术机制主导核心模型
- 把核心藏在通用的共享包背后
- 在核心仍不清晰时却去重构外围代码

---

## 大型结构

### 规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）
1. 大型结构应当帮助人们理解系统，而不是把系统冻住。
2. 让结构随模型一同演进。
3. 只有当一种指导性结构能降低跨上下文的认知负担时才使用它。
4. 让结构的约束性保持在最低限度。

### 模式
有意识地使用这些模式：
- `Evolving Order`（演进式秩序）用于结构必须通过迭代建模逐步浮现时。
- `System Metaphor`（系统隐喻）仅在它确实澄清了模型时使用。
- `Responsibility Layers`（职责层）用于职责在系统中天然分层时。
- `Knowledge Level`（知识级别）用于规则或策略必须显式表示、并可通过配置或数据变更时。
- `Pluggable Component Framework`（可插拔组件框架）用于变化点已稳定且值得形式化时。

### 必需行为（MUST）
- 把限界上下文、精炼与大型结构整合成一套连贯的策略。
- 当结构不再契合模型时重新审视它。
- 在可能的情况下，优先依靠沟通与自律，而不是沉重的结构机制。

### 反模式（MUST NOT）
- 一份阻碍模型学习的总体规划
- 听起来很聪明但会误导设计决策的隐喻
- 与领域相冲突的、过度限制性的分层
- 冒充领域结构的框架架构

---

## 战略决策

### 规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）
1. 在给出一套战略结构之前，先评估当前的模型与上下文映射。
2. 明确决定谁拥有战略设计的决策权。
3. 让应用开发反哺战略；不要在脱离实现反馈的情况下强推战略。
4. 架构团队必须以客户和模型为中心，而不是以框架为中心。
5. 随着领域认知变化，战略决策必须保持可修订。

### 必需行为（MUST）
- 当系统复杂度确有需要时，把限界上下文与精炼、大型结构结合起来。
- 让战略足够可见，使团队无需一份僵化的总体规划也能协同。
- 让技术框架服从于领域战略。
- 把战略设计当作团队决策，而不只是画图产出。

### 反模式（MUST NOT）
- 一份忽视模型学习的自上而下总体规划
- 战略由脱离实现的人掌握
- 把技术架构决策包装成领域战略
- 上下文映射、核心域决策和大型结构从未被重新审视

## 实体

### 何时使用实体
- 标识随时间推移具有重要意义
- 生命周期具有重要意义
- 超出当前属性之外的连续性具有重要意义
- 业务规则取决于「是哪一个」而不仅仅是「值是什么」

### 规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）
1. 实体必须拥有显式的标识。
2. 实体必须保护自身合法的状态迁移。
3. 实体必须暴露意图明确的行为，而不是任意的状态修改。
4. 在行为丰富的领域中，实体不得被当作被动的记录。

### 必需行为（MUST）
- 优先使用那种告诉实体去执行某个领域动作的方法。
- 在航运模型中，把目的地变更和装卸事件的添加表达为模型操作，而不是过程式的数据编辑。
- 把直接的状态修改隐藏在承载领域含义的方法背后。
- 让标识保持稳定且显式。

### 反模式（MUST NOT）
- 为每个字段提供公开的 setter
- 应用服务手工编辑实体的全部状态
- 由 UI 或应用代码判定哪些迁移是合法的
- 实体仅被用作持久化外壳

---

## 值对象

### 何时使用值对象
- 一个概念由属性而非标识来定义
- 该概念带有校验规则
- 该概念带有行为
- 传递一个原始类型会掩盖含义

### 规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）
1. 值对象默认必须不可变。
2. 构造过程必须保证有效性。
3. 相等性必须按值判定，而不是按标识判定。
4. 该概念的校验应当放在值对象内部。
5. 在概念重要之处，积极消除基本类型偏执。

### 必需行为（MUST）
- 对那些属性合在一起承载领域含义的描述性概念使用值对象。
- 按领域概念给值对象命名，而不是按其原始表示形式命名。
- 把针对该值的校验和无副作用操作放在该值附近。
- 当一个有名字的数量、区间、编码、度量或描述性整体值对模型有意义时，就替换掉裸的原始类型。

### 反模式（MUST NOT）
- 在各个处理器中重复同一份值校验
- 用裸的原始类型传递有名字的领域数量、区间、编码或度量
- 用裸字符串传递有含义的标识符
- 在没有为「不完整」建立显式模型的情况下，允许无效值短暂存在

---

## 关联与模块

### 关联
1. 只有当关联支撑行为或含义时才对它建模。
2. 优先选择更简单、更易导航的关联，而不是全连接的对象图。
3. 除非领域确有要求，否则减少双向关联。
4. 除非直接对象遍历本身属于某个不变式边界，否则通过标识来引用其他聚合。

### 模块
1. 模块必须传达领域概念以及限界上下文的归属。
2. 围绕模型含义组织模块，而不只是按技术分层。
3. 让一同变化的相关概念放在一起。
4. 避免由基础设施驱动、掩盖领域的打包方式。

### 必需行为（MUST）
- 使用与通用语言相符的包名。
- 让模型概念能从目录结构中被发现。
- 当不同概念开始独立演化时拆分模块。

### 反模式（MUST NOT）
- 以 `models`、`services`、`utils`、`helpers` 作为主导结构
- 仅因为持久化机制支持就创建的关联
- 让聚合边界变得不可见的对象图
- 按技术制品分组模块，而领域概念却四散各处

---

## 聚合

### 目的
聚合是 **一致性边界**，而不只是对象图。

### 规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）
1. 围绕必须即时保持一致的不变式来设计聚合。
2. 让聚合尽可能小。
3. 所有影响聚合不变式的修改都必须经由聚合根。
4. 除非确实需要更强的一致性，否则通过标识来引用其他聚合。
5. 让事务边界与不变式对齐；不要仅为了方便就把事务扩展到多个聚合。

### 必需行为（MUST）
- 把保护不变式的方法放在聚合根上。
- 让内部成员保持封装。
- 当某个不变式不属于单个聚合内部时，有意识地处理跨聚合边界的一致性。
- 有意识地为事务边界建模。

### 反模式（MUST NOT）
- 为了对象-关系映射方便而构建的大型对象图聚合
- 聚合根暴露内部集合，供外部任意修改状态
- 因为对象引用很方便，事务就修改了许多聚合
- 把父子对象结构与聚合边界混为一谈

---

## 领域服务

### 仅在以下情况使用领域服务
- 该行为在领域上是重要的
- 该行为不天然属于某个实体或值对象
- 该操作仍然属于通用语言的一部分

### 规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）
1. 领域服务必须表达一个领域概念，而不是一种技术便利。
2. 如果行为明确属于某个实体或值对象，就把它留在那里。
3. 不要仅为了让实体保持「薄」就把行为搬进服务。

### 必需行为（MUST）
- 领域服务的名字听起来应当像业务用语。
- 领域服务应当协调领域概念，而不是基础设施细节。

### 反模式（MUST NOT）
- 一个 `*Service` 里装着某个模型区域的全部规则
- 一个服务里塞了几十条互不相关的策略
- 只是仓储或外部技术客户端包装层的「领域服务」
- 过早地从实体中抽离行为

---

## 显式概念与规格

### 规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）
1. 在模型中把隐式约束显式化。
2. 当某个流程具有业务含义时，把领域流程建模为领域对象。
3. 对那些回答「某物是否满足某一准则」的、有名字且可组合的业务规则，使用规格（Specification）。
4. 让规格使用领域语言，而不是查询语言。

### 必需行为（MUST）
- 把重复的条件判断抽取为有名字的领域概念。
- 优先使用像路线规格、超售策略、舱位分配规则这类有名字的概念，而不是匿名布尔表达式。
- 除非项目有意提供转换机制，否则把持久化查询的关注点与领域规格分开。
- 用规格来澄清策略、校验、筛选和兼容性规则。

### 反模式（MUST NOT）
- 复杂业务条件在多个服务中重复
- 掩盖了某条有名字领域规则的布尔标志位
- 只是持久化查询构造器的「规格」
- 业务上被视为概念的流程，却仅以脚本或事务处理器的形式呈现

---

## 仓储

### 目的
仓储作为模型的一部分，提供对聚合的访问。

### 规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）
1. 仓储是为聚合根而存在的，不是为每张表而存在的。
2. 仓储接口必须由使用它的领域模型或应用模型来定义。
3. 仓储必须返回领域对象或面向领域的结果。
4. 在有价值之处，仓储契约必须体现意图。
5. 仓储不得沦为万能查询工具。

### 必需行为（MUST）
- 用仓储来重建和持久化聚合。
- 把基础设施映射隐藏在仓储实现背后。
- 当领域意图重要时，优先使用聚焦的仓储方法，而不是庞大的泛化 CRUD 接口。
- 当有助于保护不变式时，把重建路径与普通创建路径分开。
- 让客户端代码不依赖仓储实现细节，同时仓储实现者要理解这些细节。
- 当查询条件本身是领域规则时，把它表达为规格或模型概念。
- 返回领域对象或集合，而不暴露数据库结构。

### 反模式（MUST NOT）
- 抹平领域含义的泛型仓储抽象
- 把持久化记录直接返回到领域中
- 把业务规则塞进仓储实现里
- 一张表一个仓储，与聚合设计毫无关系
- 让关系数据库设计来决定对象标识、关联或聚合边界

---

## 工厂

### 何时使用工厂
- 创建过程复杂
- 构造过程带有业务规则
- 合法的创建需要多个相互协作的值
- 创建这件事本身具有领域含义

### 规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）
1. 工厂必须创建出有效的对象。
2. 工厂必须编码领域的创建规则，而不是技术性的对象拼装。
3. 客户端与映射器不得包含业务构造逻辑。
4. 把工厂放在创建职责与模型相契合的位置上。
5. 当创建过程简单、意图明确且不暴露复杂不变式时，直接使用构造函数。
6. 把从存储中重建与新对象创建区分对待。

### 反模式（MUST NOT）
- 先构建出无效对象，之后再修补
- 让接口端点直接拼装聚合
- 只是为了隐藏一个平凡构造函数而使用工厂

## 应用层

### 目的
应用层协调应用任务。
它不替代领域模型。

### 规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）
1. 应用服务负责加载聚合、调用领域行为、持久化结果并协调副作用。
2. 应用服务不得持有本应属于领域的核心业务不变式。
3. 应用服务必须使用通用语言。
4. 应用服务可以协调事务与集成消息发布，但不应变成过程式的上帝类。

### 必需行为（MUST）
- 让每个应用操作聚焦于一个应用动作。
- 让领域对象来做领域决策。
- 让编排与业务规则保持分离。

### 反模式（MUST NOT）
- 应用服务包含了全部分支业务逻辑
- 应用服务直接操作实体内部
- 仓储、UI 处理器和应用服务都在实现相互重叠的规则

---

## 基础设施

### 规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）
1. 基础设施从属于模型。
2. 对象-关系映射、序列化器、外部技术客户端、交付机制、消息细节、缓存和框架类型必须置于领域模型之外。
3. 基础设施必须适配模型，而不是反过来。
4. 持久化的形态不得定义领域的形态。

### 反模式（MUST NOT）
- 按数据库表来命名领域概念
- 围绕懒加载来设计聚合
- 仅因为持久化机制需要就给实体加方法
- 让传输层的表示形式变成领域对象

---

## 边界处的转换

### 规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）
1. 在上下文边界处，转换是强制性的。
2. 在领域对象与传输或持久化表示之间，转换通常也是强制性的。
3. 防腐层必须守护本地模型，而不是照搬外部模型。
4. 外部术语不得悄然侵入本地的通用语言。

### 必需行为（MUST）
- 显式地转换外部 ID、状态和词汇。
- 把传输层表示映射为本地命令或领域输入。
- 把持久化模型和集成模型放在核心域之外。

### 反模式（MUST NOT）
- 把外部 API 模型一路传进领域深处
- 同一个表示形式既做交付入参、又做持久化记录、又做领域对象、又做集成消息
- 把厂商的状态码当作本地的领域术语

---

## 柔性设计

### 规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）
1. 设计用领域语言揭示意图的接口。
2. 对计算和查询优先使用无副作用函数。
3. 在模型中把断言和不变式显式化。
4. 依照概念轮廓来塑造对象，而不是依照任意的技术便利。
5. 当一个概念可以在没有不必要依赖的情况下被理解时，使用独立类。
6. 当有助于清晰时，优先采用在有意义的领域类型上闭合的操作。
7. 当声明式设计能让规则更易读、易组合、易验证时，就使用它。
8. 只在每个组成部分的含义仍然可读的前提下，用 AND、OR、NOT 组合规格。
9. 当一个规格或范畴包含另一个、且这种关系确实重要时，使用包容（subsumption）。

### 必需行为（MUST）
- 按业务想要达成的目标来命名方法。
- 在副作用会让阅读者意外的地方，把命令与查询分开。
- 把不变式校验放在无效状态进入模型的位置。
- 在冗长方法、条件判断或参数组中寻找隐藏的内聚概念。
- 只有当领域特定语言能简化真实的领域表达时才考虑使用它。

### 反模式（MUST NOT）
- 用技术化命名的 API 掩盖意图
- 既回答一个问题又修改领域状态的方法
- 不变式只体现在注释或 UI/应用层校验中
- 让业务规则更晦涩而非更清晰的声明式框架

---

## 分析模式与模型模式

### 分析模式
1. 当已有的领域建模知识契合当前领域时，就加以利用。
2. 当本地语言与某个分析模式相冲突时，不要硬套。
3. 把模式适配到限界上下文中，而不是整体照搬。
4. 当团队缺少构建好模型所需的概念时，去查阅领域文献、已有成果和成熟的形式化体系。
5. 只有当探索小组的成果会在代码中被检验并回流到主团队时，才用探索小组攻克困难的建模问题。

### 模型中的设计模式
只有当设计模式能表达领域模型时才使用它：
- `Strategy` 或 `Policy` 用于可互换的领域策略。
- `Composite` 用于领域专家能够识别的部分-整体结构。
- 避免那些优化了实现却掩盖了模型含义的模式。

### 必需行为（MUST）
- 当领域已有成熟概念时，去借用既有的形式化体系。
- 让模式名称从属于领域名称。
- 在公开 API 中优先使用领域专有名称，而不是泛化的模式名。

### 反模式（MUST NOT）
- 因为熟悉而套用设计模式，而不是因为模型需要
- 用模式而不是业务概念来命名领域对象
- 引入某个参考模型却不用本地领域语言加以验证

---

## 代码生成规则

生成代码时，始终按以下顺序执行。

### 1. 先识别领域概念
在写代码之前，先弄清：
- 限界上下文
- 领域术语
- 该概念属于实体、值对象、聚合、领域服务、仓储、工厂还是规格
- 哪些不变式是重要的

不要从以下起点开始：
- 交付层代码
- 持久化模型
- 数据库 schema
- REST 结构

除非任务本身纯属基础设施性质。

### 2. 优先建模，而不是通用管道代码
如果领域中存在真实的规则：
- 把行为放进模型
- 引入值对象
- 定义聚合边界
- 在 API 中使用领域语言

不要默认写出操作被动记录的过程式服务。

### 3. 仅在原始类型确实不承载任何领域含义时才使用它
当含义、校验、单位语义或不变式重要时，就把原始类型包装起来。

### 4. 在模型边界处保护不变式
不要把 UI 校验、应用层校验或仓储校验当作业务规则的主要防线。

### 5. 让模型对持久化无感
不要主要为了对象-关系映射的便利去塑造类型或边界。

### 6. 让限界上下文在结构中可见
优先在模块与包中体现特性或上下文的归属。
避免那种把业务边界藏在通用目录背后的架构。

### 7. 显式转换外部模型
只要涉及另一个上下文、系统、传输层或持久化格式，就建立转换，而不是任其泄漏。

### 8. 寻找隐式概念
当条件判断、标志位、校验代码块或重复计算表达了业务含义时，把它们抽取为有名字的概念，如值对象、策略、规格或领域服务。

### 9. 保持战略优先级
给核心域比支撑子域或通用子域更多的建模心力。当上下文关系与精炼选择会影响代码时，让它们保持可见。

---

## 评审规则

在评审或修改代码时，主动查找以下问题：

### 语言问题
- 用含糊的技术名称取代了业务术语
- 同一概念存在多个同义名称
- 同一术语被赋予多种含义

### 模型问题
- 被动的实体
- 缺失的值对象
- 无效的构造过程
- 缺失的不变式
- 领域逻辑散落在交付层处理器、应用协调层或仓储中

### 边界问题
- 限界上下文相互渗透
- 外部模型向内泄漏
- 共享的「公共领域」抽象破坏了语言的清晰度
- 缺少上下文关系策略
- 无治理的隐式共享内核

### 聚合问题
- 过大的聚合
- 聚合根暴露内部状态修改
- 本应使用标识之处却跨聚合直接持有对象引用
- 事务默认跨越多个聚合

### 服务问题
- 实质上只是技术辅助类的领域服务
- 上帝服务
- 应用服务取代了整个领域模型

### 基础设施问题
- 持久化优先的建模方式
- 传输层结构定义了领域
- 持久化规则嵌入业务逻辑

### 战略问题
- 核心域被藏在通用基础设施背后
- 支撑子域被过度建模，而核心逻辑仍然薄弱
- 系统复杂度已需要精炼或大型结构，却看不到任何体现
- 上下文映射的决策未在代码或测试中留下记录

---

## 测试规则

### 领域测试优先
优先为以下内容编写测试：
- 实体不变式
- 值对象的有效性
- 聚合行为
- 领域服务
- 规格与显式约束
- 应用层编排
- 上下文转换与防腐层

### 规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）
1. 测试读起来必须使用通用语言。
2. 测试必须验证被允许与被禁止的状态迁移。
3. 测试必须验证无法通过受支持的路径创建出无效对象。
4. 在存在防腐层之处，测试必须验证其转换行为。
5. 基础设施测试必须与领域测试分开。
6. 核心域的测试应当读起来像模型的可执行示例。
7. 测试上下文边界，确保转换保持了预期含义。
8. 测试一个上下文不会悄然破坏另一个上下文的假设。

### 反模式（MUST NOT）
- 用传输或交付层词汇而非领域词汇命名测试
- 验证持久化细节而非领域含义的测试
- 缺少针对无效迁移和不变式保护的测试
- 只验证通用管道代码，而核心策略无测试覆盖

---

## 禁止的模式

除非有明确要求且理由充分，不要生成或保留以下模式。

### 被动领域模型
- 在复杂领域中，实体只有字段和 setter 而没有真实行为
- 所有规则都住在应用服务或 UI 处理器里

### 智能 UI
- 由 UI 或应用代码做领域决策
- 由请求处理器来强制执行核心不变式

### 持久化驱动的设计
- 为持久化便利而选择聚合边界
- 依照表结构塑造实体
- 领域类型依赖持久化机制

### 基本类型偏执
- 对有含义的概念到处使用裸的字符串、整数、小数和日期时间
- 对同一原始概念重复编写校验逻辑

### 万物共享模型
- 跨上下文的一个巨型共享领域模型
- 抹平业务区分的公共抽象

### 上帝服务
- 单个 `*Service` 类中包含许多互不相关的策略与工作流
- 用过程式编排取代领域行为

### 无效的构造
- 部分初始化的聚合
- 绕过不变式的公开状态修改
- 因为后续代码会修补就允许不可能的状态存在

### 假 DDD
- 只把 CRUD 分层改个名，而模型毫无变化
- 在没有真实领域需要时添加仓储、工厂和服务
- 对简单的支撑子域过度建模

### 上下文映射盲区
- 没有显式关系策略的集成
- 外部模型被直接引入本地核心
- 把实际上承载了另一个上下文语言的共享代码当作中立代码

### 模式驱动的晦涩
- 让领域语言更难看清的设计模式
- 让简单规则更难验证的框架或 DSL
- 阻碍模型演进的大型结构

## 重构规则

修改既有代码时：

1. 找回通用语言。
2. 在合适之处，把业务规则移入实体、值对象、聚合或领域服务。
3. 在原始类型掩盖含义之处引入值对象。
4. 在不变式不清晰或事务范围过大之处重画聚合边界。
5. 拆分当前相互渗透的限界上下文。
6. 在外部模型泄漏进领域之处加入转换层。
7. 把上帝服务拆解为聚焦的应用服务加上更丰富的领域行为。
8. 从模型中移除持久化和传输层的假设。
9. 从重复的条件判断中抽取出显式的约束、规格和策略。
10. 当集成代码含糊不清时，明确上下文关系。
11. 当战略逻辑被掩埋时，把核心域从支撑性机制中精炼出来。
12. 在增量改进模型的同时保持行为不变。

除非有明确要求，不要一次性重写全部代码。

## 输出预期

被要求实现某个特性时，默认产出：
- 限界上下文的归属
- 领域术语优先
- 在有理由之处给出实体或值对象
- 当不变式需要一致性边界时给出聚合
- 当有名字的规则需要被求值或组合时给出规格或策略
- 用于聚合持久化的仓储
- 当创建过程不平凡时给出工厂
- 用于编排的应用服务
- 在外部边界处的显式转换
- 与其他模型集成时可见的上下文关系选择
- 当不值得丰富建模时，给出更简单的支撑子域或通用子域设计

被要求评审代码时：
- 指出模型与语言的不匹配
- 指出缺失的值对象
- 指出被动数据结构式模型的症状
- 指出糟糕的聚合边界
- 指出上下文泄漏
- 指出基础设施驱动的建模
- 指出缺失的显式约束或规格
- 指出核心域精炼不足
- 指出上下文映射与大型结构的问题
- 提出具体的 DDD 重构方案

被要求修改代码时：
- 在安全的前提下先改进模型
- 不要加深那些削弱领域语言的技术性权宜之计
- 让改动之后的业务含义比改动之前更加显式
- 保持模型的战略优先级

---

## 评审清单

在最终确认任何改动之前，逐项核对：

- 限界上下文是否清晰？
- 代码是否一致地使用通用语言？
- 重要概念是否被显式建模？
- 在原始类型掩盖含义之处是否使用了值对象？
- 实体是否在保护合法的状态迁移？
- 聚合边界是否清晰且足够小？
- 除需要更强一致性的情况外，跨聚合引用是否通过标识进行？
- 仓储是否对齐聚合而非表？
- 在重复规则需要名字之处，是否使用了规格、策略或显式约束？
- 应用服务是否只在编排，而不是拥有全部规则？
- 领域模型是否被保护，免受传输层、持久化和厂商模型的影响？
- 上下文边界是否有显式转换？
- 集成处的上下文映射关系是否清晰？
- 核心域是否可见，并被保护于通用机制之外？
- 大型结构是在帮助模型，还是把模型冻住了？
- 我们是否避免了上帝服务？
- 在领域复杂之处，我们是否避免了被动的领域对象？
- 在领域简单之处，我们是否避免了过度建模？

任何一项答案为「否」，就先修订再交付。

---

## 最终指令

当不确定时，选择那个能够：
1. 让领域语言更锐利
2. 在模型内部保护不变式
3. 让限界上下文保持显式
4. 减少基本类型偏执
5. 让基础设施从属于领域含义

的方案。

拒绝那些让代码更泛化、却让领域更不清晰的改动。
