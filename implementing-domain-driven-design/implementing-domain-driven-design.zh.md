# 遵循《实现领域驱动设计》（Vaughn Vernon）

## 目的

本仓库遵循 Vaughn Vernon 那种务实风格的 **《实现领域驱动设计》**：
把 DDD 落到实际运作层面——显式的限界上下文、有纪律的聚合，以及能在真实系统中存活下来的实现模式。

所有代码生成、编辑和评审都必须以下列目标为优化方向：
- 显式的限界上下文
- 本地的通用语言
- 小的聚合边界
- 用标识取代对象图耦合
- 在恰当之处采用最终一致性
- 用上下文映射取代共享的混沌模型
- 务实的 DDD 实现，而非理论表演

本文件是一份有约束力的工程政策：`MUST`（必须）具有强制力，`SHOULD`（应当）是强默认值，`MUST NOT`（禁止）表示不得为之。

---

## 首要指令

以一种真正能被实现并能持续演进的方式为领域建模。

当不确定时：
1. 识别限界上下文
2. 使用本地的通用语言
3. 保守地界定聚合的一致性边界
4. 以标识引用其他聚合
5. 把基础设施挡在模型之外
6. 通过显式的转换来跨上下文集成

拒绝那些听起来像 DDD、实际行为却是"通用 CRUD 加上改了名的类"的设计。

---

## 战略设计规则

### 限界上下文是强制要求
1. 每一片有分量的领域区域，都必须归属于一个具名的限界上下文。
2. 一个模型只在其限界上下文内部有效。
3. 术语的含义可能跨上下文而变；这是正常的，且必须得到尊重。
4. 默认不要跨上下文共享模型类。

### 上下文映射是一项设计产出物
1. 每一处上下文交互都必须有显式的关系类型。
2. 转换责任必须可见。
3. 上游/下游的影响关系很重要。
4. 外部模型、合作方系统和遗留系统，不得定义本地模型。

### 核心域保护
1. 保护核心域，使其免受泛化抽象和厂商术语的侵蚀。
2. 把最丰富的建模精力投在竞争力或运营复杂度真正所在之处。
3. 让支撑子域保持简单。

反模式（MUST NOT）：
- 一个全公司统一的模型
- 一个横跨所有上下文的共享领域包
- 上下文边界只存在于架构图中、而不存在于代码中
- 通过直接引入彼此的领域类来做上下文集成

---

## 通用语言规则

1. 完全按照当前限界上下文中被理解的方式使用业务术语。
2. 在上下文内部，一个概念只对应一个术语。
3. 在同一个上下文内，一个术语不得承载多种含义。
4. 当理解加深时，重命名代码。
5. 测试、事件、命令、仓储和应用服务，都必须说同一套语言。

必需行为：
- 在类名、方法名、事件名和包名中使用本地的领域术语
- 当存在真实的领域术语时，移除技术性占位名称

---

## 聚合的经验法则

### 聚合就是一致性边界
1. 围绕那些必须立即成立的不变式来设计聚合。
2. 让聚合尽可能小。
3. 小聚合在可理解性和吞吐量两方面都更能扩展。
4. 庞大的对象图不是建模良好的证据。

### 聚合根纪律
1. 只有聚合根可以被外部直接引用。
2. 所有改动不变式的操作都必须经由聚合根。
3. 内部成员不得被外部代码直接修改。
4. 暴露揭示意图的行为，而不是任意的 setter。

### 以标识引用其他聚合
1. 跨聚合边界时，优先使用 ID 而非直接的对象引用。
2. 默认避免加载庞大的互连对象图。
3. 跨聚合的协调通常应当是最终一致的，而非事务性的。

### 默认每个事务一个聚合
1. 一个事务只修改一个聚合，除非有充分理由不这样做。
2. 不要为了方便而把事务拉长到覆盖多个聚合。
3. 当一致性可以是最终一致时，使用事件、策略或流程协调。

反模式（MUST NOT）：
- 为迁就 ORM 导航而确定大小的聚合
- 默认就更新多个聚合的事务
- 聚合根暴露可变的子集合
- 把跨聚合的直接导航固化进模型

---

## 实体与值对象规则

### 实体
1. 在标识和生命周期重要之处使用实体。
2. 实体必须保护有意义的状态转换。
3. 实体方法必须表达领域行为，而非泛化的状态修改。
4. 在行为丰富的领域中，实体不得是被动的 ORM 容器。

### 值对象
1. 当原始类型掩盖了含义时，积极使用值对象。
2. 值对象默认必须不可变。
3. 校验逻辑属于值对象的构造过程。
4. 相等性按值判定，而非按标识。

必需行为：
- 显式建模本地的值概念，而不是为有意义的标识符、数量、区间、名称或描述性整体值传递裸原始类型
- 让不变式的强制执行贴近概念本身

---

## 领域服务与转换服务规则

1. 当某个在领域上有实质意义的操作需要多个领域对象参与、且不适合放进任何单一实体或值对象时，使用领域服务。
2. 用通用语言为领域服务命名。
3. 当领域信息必须被转换、又不应把该行为硬塞给错误的对象时，使用转换服务。
4. 把技术性的转换、序列化、传输和持久化映射，置于领域模型之外。

反模式（MUST NOT）：
- 为了逃避为实体或值对象建模，而把行为塞进服务
- 用一个听起来像领域概念的服务名，掩盖技术性的映射逻辑

---

## 仓储规则

1. 仓储是为聚合根而存在的。
2. 仓储接口必须由需要它的领域代码或应用代码来定义。
3. 仓储负责重建（reconstitute）和持久化聚合。
4. 仓储 API 应当反映聚合的访问需求，而不是通用的表级 CRUD。
5. 仓储必须返回领域对象或面向领域的结果，而不是 ORM 行对象。

反模式（MUST NOT）：
- 巨大的通用仓储抽象
- 不做聚合思考、一张表配一个仓储
- 仓储实现内部包含业务规则
- 仓储把持久化层的实体返回到领域中

---

## 领域事件规则

1. 为有意义的业务事实发布领域事件。
2. 事件名称必须使用过去时。
3. 领域事件是模型的一部分，而不是传输机制。
4. 当不需要即时一致性时，用事件在多个聚合或多个上下文之间做协调。
5. 让事件载荷有实质意义，且局限于本地模型。

### 事件溯源
1. 只有当"存储领域事件序列"确实是该聚合的合适持久化模型时，才使用事件溯源。
2. 让事件流与聚合标识和版本号保持一致。
3. 从事件确定性地重建状态。
4. 当事件含义演进时，为事件加版本，并提供升级器（upcaster）或转换器。
5. 不要仅因为存在领域事件就选择事件溯源。

反模式（MUST NOT）：
- 为每次属性变更都使用事件
- 事件名称描述的是命令而非事实
- 领域事件携带框架请求对象或持久化产物
- 用事件来弥补缺失的聚合设计

---

## 应用服务规则

1. 应用服务负责编排用例。
2. 它们加载聚合、调用领域行为、持久化结果，并发布随之产生的事件。
3. 应用服务不得包含领域模型的核心决策逻辑。
4. 应用服务必须足够薄，使模型仍然举足轻重。
5. 应用服务可以拥有事务边界和集成协调职责。

反模式（MUST NOT）：
- 应用服务包含全部分支式业务规则
- 控制器重复了应用服务的编排逻辑
- 仓储和应用服务各自都在实现同一套不变式

---

## 模块与包规则

1. 包/模块必须首先反映限界上下文。
2. 在一个上下文内部，围绕领域和用例归属来组织，而不只按技术分层。
3. 避免为领域概念设立巨大的 `shared` 或 `common` 包。
4. 让模型在代码结构中保持可见。

推荐的结构示例：
- `identity/domain`
- `identity/application`
- `identity/infrastructure`
- `identity/interfaces`

---

## 上下文集成规则

### 防腐层
在与遗留系统或外来模型集成时使用。

规则（除标注 SHOULD 或 MUST NOT 者外均为 MUST）：
1. 把外来语言翻译成本地上下文的语言。
2. 把外来的 Schema 和状态码挡在本地领域对象之外。
3. 显式地拥有这份转换逻辑。

### 跨上下文的标识
1. 使用显式的标识符和集成消息。
2. 不要把本地聚合直接跨上下文边界传递。
3. 让契约模型与本地模型分离。

反模式（MUST NOT）：
- 引入另一个上下文的领域包
- 跨上下文共享语义不同的枚举
- 上下文之间的直接数据库耦合

---

## 客户端表示与作用域纪律

1. 当客户端需求与聚合形状不一致时，使用 DTO、投影、面向用例的查询、呈现适配器或中介者。
2. 把 REST 资源作为面向应用的表示形式对外暴露，而不是聚合内部结构。
3. 为不同客户端定制表示形式，而不必为每个客户端改动领域模型。
4. 在应用层或集成层组合多个限界上下文，而不是合并它们的模型。
5. 当一致性、性能或表示形式方面的需求足以支撑这种拆分时，让命令行为与查询模型分离。
6. 在上下文或归属关系会影响不变式或访问权限之处，让作用域标识符保持显式。

---

## 务实简约规则

1. 并非每个子域都需要完整的 DDD 仪式。
2. 在复杂度真实存在之处采用更丰富的建模。
3. 在支撑性区域采用更简单的模式。
4. 但一旦不变式和生命周期复杂度出现，就如实地为它们建模。

反模式（MUST NOT）：
- 只用 DDD 词汇而不改变设计
- 对琐碎的 CRUD 子域过度建模
- 以"简单服务就够了"为由，拒绝为真实复杂度建模

---

## 代码生成规则

生成代码时，遵循以下顺序：
1. 识别限界上下文
2. 明确通用语言中的相应术语
3. 判断该概念属于实体、值对象、聚合根、领域事件、仓储还是应用服务
4. 保守地界定聚合边界
5. 以 ID 引用其他聚合
6. 把不变式放在聚合根或本地模型上
7. 围绕聚合访问定义仓储
8. 围绕用例定义应用服务
9. 为上下文边界或基础设施边界定义转换层

默认避免：
- 跨上下文直接复用模型
- 形状被 ORM 左右的聚合
- 无所不能的应用服务
- 通用仓储
- 一个事务触及多个聚合
- 跨上下文的共享领域包

---

## 评审规则

评审或修改代码时，主动寻找：
- 缺失的限界上下文归属
- 上下文渗漏
- 跨不同上下文共享的模型
- 外来词汇污染本地上下文
- 过大的聚合
- 聚合根未保护不变式
- 外部代码修改聚合内部结构
- 跨聚合引用使用了对象而非标识
- 实质上是命令的"事件"
- 形状像表级 CRUD 的仓储契约

---

## 测试规则

1. 直接测试聚合不变式。
2. 测试合法与非法的状态转换。
3. 测试值对象的校验逻辑与行为。
4. 把领域事件作为领域行为的结果来测试。
5. 把仓储作为基础设施，与聚合规则分开测试。
6. 显式测试防腐层与转换层。
7. 测试应用服务的编排逻辑，而不是全部领域决策。

---

## 评审检查清单

在最终定稿任何改动之前，核实：
- 限界上下文是否显式？
- 本地通用语言是否被一致地使用？
- 聚合是否小巧、并以即时不变式为中心？
- 跨聚合的引用是否通过标识？
- 一个事务是否通常只修改一个聚合？
- 仓储接口是否面向聚合？
- 领域事件是事实而非命令吗？
- 应用服务是在编排，而不是拥有模型吗？
- 外来模型是否被显式转换？
- 我们是否避免了跨上下文共享模型的捷径？

如果任何一项答案为否，在交付前先修订。

---

## 最终指令

当不确定时，选择那个能够：
1. 保护限界上下文
2. 让聚合保持小巧
3. 让标识保持显式
4. 保住本地语言
5. 把跨边界的协调推向事件与转换，而不是共享对象图

的方案。

拒绝 DDD 表演，为真实运转的业务领域建模。
