# 遵循《实现领域驱动设计》（Vaughn Vernon）

## 何时使用

当 DDD 的实现选择会影响限界上下文、语言、聚合、仓储、事件、应用服务、包结构或跨上下文集成时使用。

## 需要纠正的首要偏见

务实的 DDD 不是改了名字的 CRUD。要在一个显式的限界上下文内部为真实运转的业务领域建模，使用本地语言、小的不变式边界、跨聚合的标识引用，以及在上下文边界和基础设施边界处的显式转换。

## 决策规则

- 在解读术语、模块、服务、仓储、事件、API、持久化或集成之前，先明确限界上下文；绝不强推一个全公司统一的模型。
- 一致地使用本地通用语言：在该上下文内一个概念只对应一个术语，一个术语不得承载多种含义，且代码、测试、事件、命令、仓储、服务和包都必须说这套语言。
- 保护核心域，使其免受泛化抽象和厂商术语的侵蚀；把更丰富的建模精力花在竞争力或运营复杂度所在之处，让支撑子域保持简单，并避免为琐碎的 CRUD 施加 DDD 仪式。
- 让每一处上下文交互都显式化：在共享数据、术语、模型或集成代码之前，先呈现出关系类型、转换责任，以及上游/下游的影响关系。
- 把外来的、遗留的、合作方的、外部的以及基础设施的模型翻译成本地语言；把外来的 Schema、状态码、契约模型和聚合挡在本地领域对象之外。
- 把聚合当作即时一致性边界：让它保持小巧，只暴露一个聚合根，让所有改动不变式的行为都经由聚合根，隐藏可变的内部结构，并暴露揭示意图的行为而非任意的 setter。
- 以标识引用其他聚合，避免庞大的互连对象图，默认每个事务只处理一个聚合；当一致性可以是最终一致时，使用事件、策略或流程协调。
- 当标识和生命周期重要时使用实体，并让其方法保护有意义的状态转换，而不是提供泛化的状态修改。
- 对有意义的描述性概念使用不可变的值对象；在构造时校验，按值比较，并用它替换那些表示有意义的标识符、数量、区间、名称和整体值的裸原始类型。
- 只把领域服务用于那些在领域上有实质意义、需要多个领域对象参与、且不适合放进任何实体或值对象的操作；把技术性的转换、序列化、传输和持久化映射置于领域模型之外。
- 为聚合根而非数据表提供仓储；按领域或应用的需要定义接口，返回领域对象或面向领域的结果，并把业务规则挡在仓储实现之外。
- 只为有意义的、已完成的业务事实发布领域事件；用过去时命名，让载荷局限于本地模型，不要为每次属性变更都发事件，也不要用事件掩盖糟糕的聚合设计。
- 只有当事件序列本身就是合适的持久化模型时才使用事件溯源；事件流必须与聚合标识和版本号对应，重放必须是确定性的，事件含义的变化需要版本管理、升级器（upcaster）或转换器。
- 让应用服务保持为用例协调者：加载聚合、调用领域行为、持久化结果、发布随之产生的事件、承担事务或集成协调职责，并把核心决策留在领域模型中。
- 模块首先按限界上下文组织，在上下文内部再按领域或用例归属组织；避免为领域概念设立巨大的 `shared` 或 `common` 包。
- 当客户端需求与聚合形状不一致时，使用 DTO、投影、面向用例的查询、呈现适配器或中介者；对外暴露面向应用的表示形式，而不是聚合内部结构。
- 当一致性、性能或表示形式方面的需求足以支撑时，让命令行为与查询模型分离；在上下文或归属关系会影响不变式或访问权限时，让作用域标识符保持显式。
- 生成代码时，按顺序走查模型：上下文、语言术语、战术类型、保守的聚合边界、标识引用、本地不变式、面向聚合的仓储、用例服务，以及边界转换。
- 直接测试领域行为与边界：聚合不变式、合法与非法的状态转换、值对象校验、作为结果的领域事件、作为基础设施的仓储、转换层，以及应用服务的编排逻辑。

## 触发规则

- 当某个术语含义不明、在多个上下文中被复用，或正沦为一个技术性占位符时，先限定、拆分或重命名它，再继续写代码。
- 当代码想要引入另一个上下文的领域包、跨上下文共享枚举，或通过另一个上下文的数据库产生耦合时，改为添加显式的转换层。
- 当遗留系统、厂商、合作方、API、传输、持久化或 UI 的形状出现在本地领域代码中时，先加上防腐层或映射边界，再进行本地建模。
- 当聚合边界发生变化，或一个事务想涵盖多个聚合时，列出要求如此的即时不变式；否则改用标识、领域事件、策略、流程或应用服务来协调。
- 当外部代码修改聚合内部结构，或读取内部结构来决定状态变更时，把该操作移到聚合根的行为之后。
- 当一个仓储沦为通用 CRUD、呈表形状、返回行对象，或开始强制业务规则时，围绕聚合访问重塑它，并把规则搬回模型。
- 当一个事件读起来像命令、暴露了框架或持久化的产物，或描述的只是一次次要属性变更时，重命名、收窄或移除它。
- 当应用服务或控制器里堆积起分支式的业务规则时，把决策移入拥有该概念的实体、值对象、聚合或领域服务中。
- 当客户端渲染、查询速度或表示形式方面的需求给模型形状施压时，使用投影、DTO、面向用例的查询或适配器，而不是扩大或暴露聚合。
- 当一个子域就是简单的 CRUD 时，让它保持简单；当不变式和生命周期复杂度出现时，如实地为它们建模，而不是把它们藏在服务里。

## 最终检查清单

- 在解读命名、模块、事件、仓储、API、持久化或集成之前，限界上下文是否已显式？
- 代码在测试、命令、事件、仓储、服务和包中，是否为每个概念都使用唯一的本地术语？
- 核心域的投入是否受到保护，而支撑性或 CRUD 区域是否保持简单？
- 上下文关系、转换责任，以及上下游的压力传导是否可见？
- 聚合是否小巧、由聚合根保护、由不变式驱动、通过标识关联，且通常每个事务只处理一个？
- 实体是否承载行为，值对象是否不可变、经过校验、按值判等？
- 仓储是否是聚合根的访问入口，而不是通用 DAO 或 ORM 泄漏？
- 领域事件是否是有意义的过去时事实，事件溯源是否只在事件历史确为合适的持久化模型时才使用？
- 应用服务是否只在编排用例，而不拥有领域决策？
- 客户端、外来系统、持久化和基础设施的表示形式，是否都被挡在本地领域模型之外？
