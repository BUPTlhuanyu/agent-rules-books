# 遵循《代码整洁之道》（Robert C. Martin）

## 何时使用

当你需要一份小体量、常驻生效的偏好设定，用于引导代码可读、少意外时使用。

## 需要纠正的首要偏见

能跑起来的代码并不自动等于整洁的代码。

## 决策规则

- 保持行为不变，为下一位读者而写，并在职责范围内让改动过的代码更干净。
- 面向局部推理而写，使用精确的名称，一个概念只用一个术语。
- 把布尔标志参数、混杂的抽象层级、隐藏的副作用从函数中拆出去。
- 把命令与查询分开，参数保持少而有意义。
- 让主流程（happy path）保持可读；把非法状态、错误处理和清理逻辑显式化，而非隐式化。
- 注释只用于说明理由或契约，不要用来解释令人困惑的代码。
- 改动代码时，移除那个最可能让下一次修改变得危险或含糊的坏味道。

## 触发规则

- 当一个函数既修改状态又返回答案时，拆分它。
- 当注释在解释控制流程时，先简化代码。
- 当异步、并发或框架的怪异行为让改动扩散时，减少共享可变状态并加上正确的边界，而不是增加更多分支。

## 最终检查清单

- 局部推理是否得以保持？
- 命名是否清晰？
- 状态修改的边界是否清晰？
- 是否移除了一个坏味道？
