# 遵循《代码整洁之道》（Robert C. Martin）

本文件定义了本仓库强制执行的工作规则。在进行任何代码、测试、重构、评审或文档改动之前，请先遵循这些指令。

## 优先级与行为

- 把本文件中所有未加限定词的规则都视为 `MUST`（必须）；把 `优先`（Prefer）视为 `SHOULD`（应当）；把 `不要`（Do not）、`避免`（Avoid）和 `绝不`（Never）视为 `MUST NOT`（禁止），除非用户显式覆盖。
- 优先考虑可读性、可维护性、正确性和安全的变更，而非精巧写法或速成手段。
- 为下一位人类读者做优化。
- 存在权衡时，选择那个能降低长期复杂度的方案。
- 绝不因为糟糕的结构已经存在就保留它。
- 应用童子军法则：让改动过的代码比你发现它时更干净。

## 整洁代码的核心原则

- 首要为人类而写代码，而不只是为了执行。
- 让代码保持简单、直接、易于修改。
- 避免偶然复杂度。
- 避免令人意外的行为。
- 优先显式的意图，而非隐式的魔法。
- 优先支持局部推理：读者应当能在极少跨文件跳转的情况下理解代码。
- 减少技术债，而不是把它搬来搬去。

## 命名规则

- 使用能揭示意图的名称。
- 名称必须在无需额外注释的情况下说明其用途、角色或行为。
- 避免误导性的名称、被过度重载的含义，以及视觉上容易混淆的标识符。
- 让区分有实际意义。不要创造仅在表面形式上不同的名称。
- 使用可读出声、可被搜索的名称。
- 避免缩写，除非它们是既有的领域标准或平台标准。
- 避免在名称中编码信息，包括类型前缀、实现提示和匈牙利命名法。
- 避免在标识符中加入不必要的上下文。
- 当通过模块、类、命名空间或类型来提供上下文比加长名称更整洁时，采用前者。
- 在整个代码库中，一个概念只用一个词。
- 不要为同一个操作或概念使用多个同义词。
- 不要把一个熟悉的词用于另一种含义。
- 类、类型和模块的名称应当是名词或名词短语。
- 函数和方法的名称应当是动词或动词短语。
- 领域概念使用问题域的名称。
- 技术概念使用解决方案域的名称。
- 不要使用卖萌的、搞笑的、晦涩的或只有自己懂的梗式名称。

## 函数规则

- 让函数保持短小。
- 每个函数必须只做一件事。
- 一个函数应当只有一个明确的变化理由。
- 让每个函数处于同一抽象层级。
- 自上而下组织代码，使读者先看到高层的故事，再看到细节。
- 优先使用描述性的名称，而非短名称。
- 尽量减少参数数量。
- 避免布尔标志参数。改为拆分成多个独立的函数。
- 避免输出参数，除非语言惯例使其成为必需。
- 消除隐藏的副作用。
- 分离命令与查询。
- 一个回答问题的函数，不应同时修改状态。
- 按项目所用语言的惯例，优先使用异常或显式的结果类型，而非临时拼凑的错误码。
- 把错误处理与主逻辑隔离开。
- 积极消除重复。
- 优先采用直白的控制流，而非精巧的控制流。
- 把深层嵌套重构为更清晰的结构。

## 注释规则

- 不要用注释来弥补糟糕的命名或糟糕的结构。
- 先改进代码，再判断是否仍然需要注释。
- 优先写自解释的代码。
- 只有当注释能提供代码难以表达的信息时才使用它。
- 好的注释类别包括：
  - 法律或许可方面的要求
  - 非显而易见的意图
  - 重要的警告或约束
  - 某个令人意外的决策的理由
  - 对外部行为或协议假设的澄清
- 移除冗余的、过时的、显而易见的、嘈杂的和有误导性的注释。
- 不要逐行叙述代码。
- 让注释保持精确，并在代码变化时维护它们。
- 避免 TODO 注释，除非它们可执行、具体且必要。

## 格式与结构

- 在整个仓库中使用一致的格式。
- 通过格式来呈现结构与意图。
- 把相关的概念放在相近的位置。
- 让文件、类和函数保持在合理的规模内。
- 用纵向顺序把故事从高层讲到低层。
- 用缩进来澄清作用域，而不是用它掩盖复杂度。
- 当过长的行损害可读性时，避免这样的行长。
- 避免那种在编辑时容易失效的装饰性对齐。
- 保持一种便于快速扫读的排版。

## 对象、模块与数据结构

- 有意识地把行为丰富的对象与纯数据载体区分开。
- 不要随意混合数据容器与业务行为。
- 把实现细节隐藏在清晰的接口之后。
- 暴露行为，而不是数据表示。
- 在合适的场合，使用 DTO 之类的结构作为简单载体。
- 避免"火车残骸"式的链式调用，以及对内部结构不必要的了解。
- 尊重松耦合和局部边界。
- 不要让持久化、框架和第三方细节掩盖业务行为或核心逻辑。

## 类与模块设计

- 让类和模块保持短小。
- 每个类或模块应当只有一项主要职责。
- 追求高内聚。
- 拆分那些堆积了不相关行为的类。
- 组织代码，使可能发生的变化保持在局部。
- 公开 API 应当短小、显而易见、难以误用。
- 优先使用组合而非复杂的继承，除非继承明显是更简单、更稳定的模型。
- 不要让构造函数和初始化逻辑压过领域行为。

## 错误处理

- 有意识地设计错误处理。
- 让主流程易于阅读。
- 在错误消息中提供足够的诊断上下文。
- 使用能支撑调用方作出决策的错误类型或异常类。
- 当存在更安全的模型时，不要返回 `null` 或等价的"缺失"哨兵值。
- 不要传入 `null` 或等价的非法状态，除非 API 显式地为该情形建模。
- 根据代码库所用语言和惯例，优先使用异常、特例类、空对象或显式的可选类型。
- 让资源清理和关闭路径正确且可见。

## 边界与外部依赖

- 在可行时，把第三方库隔离在本地适配器或包装层之后。
- 避免把核心逻辑直接耦合到不稳定的外部 API 上。
- 围绕依赖创建窄接口。
- 为棘手的外部行为添加学习性测试或聚焦的集成测试。
- 当某个依赖尚不存在时，从本地需求出发定义接口，而不是基于对未来实现的猜测。

## 系统构建规则

- 把系统的构造过程与使用过程分开。
- 把对象图装配、依赖注入、工厂和框架引导逻辑挡在普通业务行为之外。
- 把启动装配放在一个显式的 main 或组合区域中。
- 当构造策略本身有实质意义或较为复杂时，使用工厂。
- 不要让横切关注点掩盖普通的代码流程。
- 只有当规范、框架、代理或 AOP 式机制能带来可证明的价值时才使用它们。
- 用可执行的切片来验证架构决策，而不只靠图表或配置。
- 只有当领域特定语言能让系统意图比通用代码更清晰时才使用它。

## 测试

- 把测试当作生产级质量的代码来对待。
- 让测试保持整洁、可读、确定性和可维护。
- 一个测试应当传达一个主要想法。
- 优先使用简单的初始化和清晰的断言。
- 避免那些耦合到无关实现细节上的脆弱测试。
- 测试应尽可能快。
- 测试应彼此隔离、不依赖执行顺序。
- 测试应能自我校验。
- 为行为变更、缺陷修复和重要重构添加或更新测试。
- 不要在缺乏相称验证的情况下交付代码改动。
- 修复缺陷时，在可行的情况下补上一个原本能捕获该缺陷的测试。

## TDD 与整洁测试规则

- 当行为可以被清晰地描述出来时，优先在写生产代码之前先写一个失败的测试。
- 不要写超出失败测试或明确需求所能证明其必要性的生产行为。
- 让测试小到足以使一次失败只指向一种行为或一个概念。
- 当有助于清晰性时，优先做到每个测试一个断言或一个概念性断言。
- 使用能揭示被测业务行为或技术行为的测试名称和测试数据。
- 当重复的初始化掩盖了意图时，构建一小套测试词汇或辅助 DSL。
- 让测试代码保持整洁；脏乱的测试会削弱你安全修改生产代码的能力。
- 避免那些需要多个手工步骤才能运行的测试。
- 用覆盖率数据来发现未被测试的风险，而不是用它替代有意义的断言。
- 把被忽略的、不稳定的或被跳过的测试都当作尚未解决的疑问。

## 并发与异步工作

- 除非能带来真实收益，否则不要引入并发。
- 当顺序执行的代码已经够用时，优先选择它。
- 尽量减少共享可变状态。
- 优先采用不可变性、消息传递或清晰的所有权边界。
- 让同步块或加锁区间尽可能小。
- 对关闭、取消、超时和清理保持显式。
- 在并发行为重要的地方，仔细地测试它。
- 在修改并发代码之前，先了解其执行模型。
- 避免同步方法之间产生依赖。
- 先让非并发的行为正确，再加入线程。
- 当线程策略或并发级别可能变化时，让多线程代码可插拔、可调节。
- 在可行处，让对并发敏感的测试在不同线程数、不同调度和不同平台下运行。
- 在有证据表明并非如此之前，把偶发的失败都当作可能的并发缺陷。

## 重构规则

- 以小而安全的步子重构。
- 在改进结构的同时保持行为不变。
- 先让它工作，再让它正确。
- 移除重复、死代码、有误导性的抽象和特例带来的杂乱。
- 当名称薄弱时，积极重命名。
- 当提取代码能改善内聚性和清晰度时，就提取。
- 把那些已不值其成本的抽象内联回去。
- 优先采用能通过所有相关测试的最简设计。

## 浮现式设计与逐步精化

- 优先采用这样的设计：能通过所有相关测试、消除了重复、表达了意图，并使用了最少的必要类和方法。
- 通过一版版可运行的草稿来精化代码，而不是期待第一版就是整洁的。
- 当代码起初较为粗糙时，持续改进命名、结构和测试，直到意图清晰。
- 当渐进式精化就能安全地挽回设计时，不要启动一次宏大的重新设计。
- 对改动过的代码应用童子军法则，但让清理量与任务规模相称。

## 需要发现并消除的坏味道

改动代码时，主动寻找并修复以下问题：

- 含义模糊或有误导性的名称
- 重复的逻辑
- 过大的函数
- 过大的类或模块
- 混杂的抽象层级
- 隐藏的副作用
- 用于控制流程的布尔标志
- 过长的参数列表
- 深层嵌套
- 本应被隔离或改为多态的过多条件判断
- 大量依赖注释、本应被重构的代码
- 死代码和未被使用的抽象
- 脆弱的测试
- 无必要地依赖环境的测试
- 不必要的间接层
- 偶然复杂度
- 会让变更大范围扩散的耦合
- 需要多于一个手工步骤的构建或测试
- 处于错误抽象层级的代码
- 基类依赖派生类
- 穿透对象内部的传递式导航
- 不相关概念之间的人为耦合
- 隐藏的逻辑依赖
- 显而易见却未被实现的行为
- 不正确的边界行为
- 被绕过的安全措施
- 没有具名含义的魔数
- 掩盖意图的否定式条件
- 被忽略的测试和不足的边界测试
- 要求读者先看懂算法才能信任其名称的函数

## 变更流程

对每一项非平凡的任务：

1. 理解意图和受影响的行为。
2. 找出最简单的正确改动。
3. 先改进命名，再考虑添加注释。
4. 在可能的情况下让编辑保持局部化。
5. 按需添加或更新测试。
6. 运行相关的验证。
7. 从可读性、重复和不必要的复杂度角度评审 diff。
8. 确保最终代码比之前更干净。

## 实现偏好

- 优先选择显式的、平实的、可维护的方案。
- 优先使用标准库和项目中既有的模式，而非引入新依赖。
- 除非能明显降低整体复杂度，否则不要添加依赖。
- 复用项目既有的约定，除非它们与本文件的规则冲突，或用户显式提出了别的要求。
- 让接口保持窄小。
- 让状态转换显而易见。
- 避免过早优化。
- 只有在有证据或有已知需求时才做优化。

## 评审检查清单

在收尾之前，逐项核实以下内容：

- 命名揭示了意图。
- 函数短小且职责聚焦。
- 类和模块有清晰的职责。
- 注释是必要且准确的。
- 错误处理显式且有用。
- 在合理之处消除了重复。
- 测试恰当地覆盖了发生变化的行为。
- 代码自上而下读起来顺畅。
- 设计比之前更简单，或至少没有变得更复杂。
- 改动遵循了项目既有的约定。

## 输出预期

进行改动时：

- 简要说明改了什么。
- 说明运行了哪些测试或检查。
- 指出任何尚未解决的风险、假设或权衡。
- 如果所要求的改动与本文件规则冲突，遵照用户要求执行，但要显式指出这处冲突。

## 硬性规则

- 不要引入有误导性的名称。
- 没有充分理由，不要保留重复的逻辑。
- 当更好的代码能消除注释的必要性时，不要添加注释。
- 没有充分理由，不要把查询与状态修改混在一起。
- 不要悄悄把范围扩大到所要求的任务之外。
- 不要让改动过的代码比之前更难读。
