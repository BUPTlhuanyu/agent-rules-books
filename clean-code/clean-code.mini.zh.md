# 遵循《代码整洁之道》（Robert C. Martin）

## 何时使用

当可读性、局部推理能力和可维护的代码形态是主要关注点时使用，尤其是在日常实现与代码评审过程中。

## 需要纠正的首要偏见

能跑起来的代码并不自动等于整洁的代码。

## 决策规则

- 把整洁当作交付的一部分。保持行为不变，在职责范围内让改动过的代码更干净，不要因为工期紧或承诺了将来重写就制造混乱。
- 面向局部推理而写。读者应当能够理解执行路径，而不必去重建隐藏状态、跨越大段跳转，或琢磨命名上的琐碎细节。
- 使用精确的名称，一个概念只用一个术语。当词汇掩盖了意图、含义被过度重载，或不得不靠注释来弥补时，就重命名代码。
- 让函数保持短小、职责聚焦，并处于同一抽象层级。自上而下地讲述故事，让意图出现在细节之前。
- 让参数保持少而有意义。避免布尔标志参数、输出参数和大杂烩式的参数列表；应把概念建模出来。
- 分离命令与查询，消除隐藏的副作用。一个负责返回答案的函数，不应该在读者背后偷偷修改状态。
- 保持主流程可读。把错误处理、非法状态处理和清理逻辑隔离出去；在语言支持的情况下，优先使用显式的可选类型或带类型的结果，而不是基于 null 之类哨兵值的控制流。
- 暴露行为而非裸的数据表示。避免"火车残骸"式的链式访问、工具类垃圾场，以及职责混杂的类或模块。
- 把构造、框架、持久化、事务、安全和厂商相关的细节挡在业务行为之外。
- 让公开 API 短小、显式、难以误用。把边界逻辑、必需的调用顺序和可能的变化点编码在读者看得见的地方。
- 注释只用于说明理由、约束、警告或外部契约。不要用叙述代码来代替改进代码。
- 把测试当作生产代码来对待：可读、确定性、与它所保护的行为或契约对齐，并在宣布改动完成之前有相称的验证作为支撑。
- 让设计通过测试、消除重复、增强表达力和最小化结构而自然浮现；不要添加不必要的抽象或基础设施。
- 改动代码时，移除那个最能推高变更成本的坏味道，但不要悄悄把任务范围扩大到超出"让本次改动变安全所需的最小清理"。

## 触发规则

- 当一个函数混杂了初始化、校验、计算和副作用时，把这些阶段拆开。
- 当注释在解释控制流程时，先改进命名或结构，再决定是否保留该注释。
- 当一个函数既修改状态又返回答案，或用一个标志位隐藏了模式切换时，分离这些职责。
- 当出现重复代码、反复出现的 switch 或成堆的原始类型时，用参数对象、多态、特例类或其他小抽象把这个概念命名出来。
- 当某个边界把框架、厂商或持久化的怪异行为泄漏到内部时，添加或强化一个局部适配器。
- 当引入异步或并发时，隔离线程策略、最小化共享可变状态、定义好关闭流程，并测试对时序敏感的行为。
- 当修复缺陷或变更行为时，添加或更新那个保护预期契约的测试。
- 当清理工作开始蔓延到不相关的区域时，收回到"让本次改动保持安全与可读所需的最小重构"。

## 最终检查清单

- 读者能否在局部范围内看懂这次改动？
- 命名和 API 是否无需旁白就能传达含义？
- 状态修改是否显式，主流程是否依然清晰？
- 框架、持久化、厂商和构造细节是否都留在了边界之后？
- 我是否从改动区域移除了至少一个坏味道？
- 测试是否保护了发生变化的行为或契约？
- 我是否真的为这次改动运行了相关的测试或检查？
